🚀 Java 25 (LTS) Interview Questions

Java 25 (September 2025) is the LTS after 21 and 17. It bundles everything finalized in Java 18–25 — virtual threads, pattern matching for switch, record patterns, sequenced collections, stream gatherers — plus new finals in 25 such as scoped values, compact source files and flexible constructor bodies.

Virtual threads & concurrency

What are virtual threads and how do they differ from platform threads?

Virtual threads (Project Loom, final in 21) are lightweight threads managed by the JVM, not the OS. Millions can exist; when a virtual thread blocks on I/O it unmounts from its carrier (a small ForkJoinPool of platform threads) so the carrier can run another one.

🧠 How this works

  1. Executors.newVirtualThreadPerTaskExecutor() creates a new virtual thread for every submitted task, with no pool. Virtual threads were final in Java 21 (JEP 444).
  2. Submitting 10,000 tasks is fine. Each virtual thread is a small heap-allocated object, not an OS thread, and they run on a few carrier platform threads (a ForkJoinPool sized to the CPU cores).
  3. When httpClient.fetch(...) blocks on network I/O, the JVM unmounts the virtual thread: its stack is saved to the heap and the carrier picks up another virtual thread. When the I/O completes, the thread is mounted again and continues.
  4. f.get() blocks the calling thread until each result is ready. The try-with-resources block calls close(), which waits for all submitted tasks to finish before exiting (ExecutorService is AutoCloseable since Java 19).
  5. Thread.ofVirtual().name("worker-", 0) is a builder that names threads worker-0, worker-1, …. Thread.startVirtualThread is the shortcut that creates and starts one virtual thread.
You keep writing simple blocking, thread-per-request code but get the scalability of reactive code.
How do you enable virtual threads in Spring Boot?

Since Spring Boot 3.2 (on Java 21+), one property switches Tomcat/Jetty request handling, @Async, scheduling and messaging listeners to virtual threads:

🧠 How this works

  1. This one property in application.properties tells Spring Boot (3.2+) to use virtual threads where it creates threads itself.
  2. The embedded web server (Tomcat/Jetty) then handles each HTTP request on its own virtual thread instead of a fixed worker pool, so a request that blocks on JDBC or REST calls does not hold an OS thread.
  3. The auto-configured task executor used by @Async and scheduling also switches to virtual threads.
  4. It only takes effect on Java 21+, where virtual threads are final. Downstream limits such as the DB connection pool still apply.
When should you NOT use virtual threads?
  • CPU-bound work — no gain; there are still only as many carriers as cores. Use a fixed platform pool or parallel streams.
  • Pooling them — never pool virtual threads; create one per task. Limit concurrency with a Semaphore instead.
  • Heavy ThreadLocal usage — millions of threads × large thread-locals = memory pressure. Prefer ScopedValue.
  • Pinning — before Java 24, blocking inside synchronized pinned the carrier. JEP 491 (Java 24) fixed this; native frames/JNI calls can still pin.
  • Downstream limits — 10,000 concurrent virtual threads still share a DB pool of, say, 20 connections. Size resources accordingly.

🧠 How this works

  1. "Pinning" means a virtual thread cannot unmount from its carrier while blocked, so the carrier platform thread is stuck too.
  2. -Djdk.tracePinnedThreads=full made older JDKs (21–23) print a stack trace whenever a virtual thread blocked while pinned. It was removed in Java 24, when JEP 491 stopped synchronized from pinning.
  3. The portable way is JFR: the jdk.VirtualThreadPinned event is recorded when a pinned thread blocks for longer than a threshold. jfr print --events ... dumps those events from a recording, with stack traces showing the cause.
  4. The recording must be captured first, e.g. by starting the app with -XX:StartFlightRecording.
What are Scoped Values and how do they compare to ThreadLocal?

ScopedValue (final in 25, JEP 506) shares immutable data with callees for a bounded dynamic scope — ideal for request context (user, tenant, trace id).

ThreadLocalScopedValue
MutabilityMutable (set)Immutable within a scope
LifetimeUntil remove() — easy to leak in poolsEnds automatically with the scope
Child threadsInheritableThreadLocal copiesShared cheaply with structured concurrency subtasks
CostPer-thread mapOptimised for many virtual threads

🧠 How this works

  1. ScopedValue.newInstance() creates a key, usually a static final constant like a ThreadLocal. It holds no value yet.
  2. ScopedValue.where(CURRENT_USER, user).run(...) binds the value only while the lambda runs. Any method called from inside it, at any depth, can read it.
  3. CURRENT_USER.get() returns the bound value; outside a binding it throws NoSuchElementException, so isBound() lets you check first.
  4. When run returns, the binding is gone automatically. There is no set and no remove() to forget, so nothing leaks between requests. A nested where can rebind it for an inner scope only.
  5. Scoped Values became final in Java 25 (JEP 506) and are cheap to use with many virtual threads.
What is Structured Concurrency (preview in 25)?

It treats a group of concurrent subtasks as one unit of work: if one fails the others are cancelled, and the scope cannot exit before its children finish — no leaked threads.

🧠 How this works

  1. Structured concurrency is a preview API in Java 25 (JEP 505), so you must pass --enable-preview (with --release 25) to both javac and java.
  2. StructuredTaskScope.open() creates a scope whose default policy is that all subtasks must succeed. Being in try-with-resources means the scope cannot outlive the method.
  3. Each scope.fork(...) starts the callable in a new virtual thread and returns a Subtask handle right away, so findUser and fetchOrder run in parallel.
  4. scope.join() waits for both. If one throws, the scope cancels (interrupts) the other and join() throws, so you never wait on work whose result is useless.
  5. After a successful join(), user.get() and order.get() return the results. close() guarantees every forked thread has finished, so no thread leaks.

Other joiners: Joiner.anySuccessfulResultOrThrow() (race replicas), Joiner.awaitAll().

Pattern matching & language

Explain pattern matching for switch and record patterns with an example.

Since Java 21, switch works on any type with type patterns, guards (when), case null, and record deconstruction — exhaustively checked for sealed hierarchies.

🧠 How this works

  1. Shape is sealed with three record subtypes, so the compiler knows every possible case. Point is a nested component record.
  2. case Circle(Point(var x, var y), double r) when r > 100 is a nested record pattern. It checks the type, calls the accessors to deconstruct center into x/y and binds r, and the when guard adds a condition.
  3. Order matters: the guarded Circle case must come before the plain case Circle c. Otherwise the unguarded case would dominate it and the compiler reports an error.
  4. Rect is deconstructed two levels deep to compute the area. case Line _ uses the unnamed pattern (Java 22) because the value is not needed.
  5. All three permitted types are covered, so the switch is exhaustive without default. Pattern switch and record patterns are final in Java 21 (JEPs 441, 440). Passing null throws an NPE because there is no case null.
  6. The last line uses a record pattern in instanceof. It deconstructs Point and the binding variables can be used right away in the && x == y condition.
What are unnamed variables and patterns (_)?

Final in Java 22 (JEP 456): use _ for variables or pattern components you must declare but never use.

🧠 How this works

  1. catch (NumberFormatException _): we only care that parsing failed, not about the exception object, so we do not invent an unused name like ignored.
  2. for (var _ : list) count++; only counts iterations; the element itself is never used.
  3. map.forEach((_, v) -> ...) ignores the key. Note that total must be a field here, since a lambda cannot change a local variable.
  4. Circle(Point _, double r) matches any center without binding it, extracting only the radius. _ can be used more than once in the same scope because it never introduces a name.
  5. Final in Java 22 (JEP 456). Since Java 9, _ had been a reserved word, which is what allowed this new meaning.
What are Compact Source Files and Instance Main Methods (JEP 512)?

Final in Java 25. A source file can contain methods and fields without a class declaration (an implicit class), main needs no public static or String[] args, the new java.lang.IO class gives simple console I/O, and the whole java.base module is imported automatically.

🧠 How this works

  1. The file has no class declaration. The compiler wraps its fields and methods in an implicit class named after the file, and that class cannot be referenced by name from other code.
  2. void main() is an instance main method: no public, static or String[] args. The launcher creates an instance and calls it.
  3. IO.readln(prompt) prints the prompt and reads a line, and IO.println prints. IO lives in java.lang, so it needs no import.
  4. Compact source files automatically import the whole java.base module, which is why List works without an import. The last line prints [1, 2, 3] because the stream is sorted before toList().
  5. java Hello.java uses the source launcher to compile in memory and run. Final in Java 25 (JEP 512).
Great for scripts, teaching and quick prototypes; combine with the multi-file source launcher (JEP 458, Java 22) to run small multi-class programs without a build tool.
What are Flexible Constructor Bodies (JEP 513)?

Final in Java 25: statements may appear before super(...) / this(...) — for validation, computing arguments, or initializing the subclass's own fields — as long as they don't use this otherwise.

🧠 How this works

  1. Before Java 25, super(...) had to be the first statement. JEP 513 (final in 25) allows a prologue of statements before it.
  2. The age check runs before Person's constructor, so an invalid object is never partly built.
  3. this.dept = ... before super() is allowed: in the prologue you may assign the subclass's own fields, but you cannot read fields, call instance methods or pass this anywhere.
  4. Because dept is set before super(...) runs, an overridable method called by Person's constructor would see a real dept instead of null.
  5. name.strip() shows computing a constructor argument inline. Previously this needed a static helper method.

Benefit: no more static helper methods just to validate constructor arguments, and superclass constructors that call overridable methods now see initialized subclass fields.

What are Module Import Declarations (JEP 511)?

import module M; imports all public top-level types of every package exported by module M (and its transitive dependencies). Works in ordinary classpath code too.

🧠 How this works

  1. import module java.base; works like a wildcard import of every package the module exports (java.util, java.io, java.time, ...) in one line.
  2. import module java.sql; imports java.sql and javax.sql, plus the packages of modules that java.sql requires transitive (such as java.xml and java.logging).
  3. Both java.util and java.sql export a class named Date, so plain Date would be ambiguous. A single-type import (import java.sql.Date;) takes priority over on-demand imports and resolves the ambiguity.
  4. Your code does not need to be a module itself; it works on the classpath. Final in Java 25 (JEP 511).
What are Markdown documentation comments?

Since Java 23 (JEP 467), Javadoc can be written in Markdown using /// comments.

🧠 How this works

  1. Lines starting with /// are a Markdown doc comment and replace /** ... */ with HTML tags (Java 23, JEP 467).
  2. **net** renders as bold, the - lines become a bullet list and backticks become inline code. A blank /// line separates paragraphs.
  3. [TaxService#rateFor(String)] is a reference link: Javadoc resolves it to that method, just like {@link}.
  4. The method body { ... } is a placeholder; only the comment matters here.
What are Primitive Types in Patterns (preview)?

Preview in Java 25 (JEP 507): primitive types are allowed in all pattern contexts, and instanceof/switch work on all primitive types, testing whether a conversion is exact.

🧠 How this works

  1. This is a preview feature in Java 25 (JEP 507, 3rd preview), so it needs --enable-preview at compile time and run time.
  2. case 200 is a constant label. case int i when i >= 500 is a primitive type pattern with a guard, which was not allowed on an int switch before.
  3. case int i matches every remaining int, so the switch is exhaustive without default.
  4. big instanceof int i tests if the long value converts to int without loss. 42L fits, so it prints fits in int: 42; a value above Integer.MAX_VALUE would make the test false instead of silently truncating.

APIs

What are Sequenced Collections?

Java 21 added SequencedCollection, SequencedSet and SequencedMap giving a uniform API for collections with a defined encounter order (List, Deque, LinkedHashSet, TreeSet, LinkedHashMap…).

🧠 How this works

  1. getFirst() returns "a" and getLast() returns "c". These methods come from the new SequencedCollection interface (Java 21, JEP 431), which List now extends.
  2. addFirst("z") makes the list [z, a, b, c], so reversed() gives [c, b, a, z]. reversed() is a view, not a copy, so later changes to the list show up in it.
  3. On an empty collection, getFirst()/getLast() throw NoSuchElementException. On an unmodifiable list, addFirst throws UnsupportedOperationException.
  4. LinkedHashMap implements SequencedMap: putLast inserts at the end, firstEntry() reads x=1, pollLastEntry() removes and returns the last entry, and sequencedKeySet().reversed() gives the keys in reverse order.
What are Stream Gatherers? Show windowFixed and a custom gatherer.

Final in Java 24 (JEP 485), Stream.gather(Gatherer) is a user-extensible intermediate operation — the counterpart of collect for terminal operations. Built-ins live in Gatherers.

🧠 How this works

  1. windowFixed(3) collects elements into lists of 3 and emits each full list downstream. The leftover 7 is emitted as a final partial window, giving [[1, 2, 3], [4, 5, 6], [7]].
  2. windowSliding(2) emits overlapping windows that move one element at a time, so 4 elements produce 3 windows [[1, 2], [2, 3], [3, 4]].
  3. scan(() -> 0, Integer::sum) starts from 0 and emits the running state after each element: 0+1=1, 1+2=3, 3+3=6, 6+4=10.
  4. mapConcurrent(10, this::fetch) runs fetch on virtual threads with at most 10 in flight, and still emits results in the original stream order.
  5. In the custom gatherer, ofSequential(initializer, integrator) gives each stream a fresh HashSet as state. For each item, if seen.add returns false (duplicate), the || short-circuits and returns true ("keep going") without pushing. Otherwise down.push(item) emits it and returns whether downstream still wants more elements.
  6. Stream Gatherers are final in Java 24 (JEP 485), so they are available on 25 LTS.
What is the Foreign Function & Memory API?

Final in Java 22 (JEP 454), it replaces JNI for calling native libraries and safely managing off-heap memory, with no C glue code.

🧠 How this works

  1. Linker.nativeLinker() gives the linker for the current platform's C calling convention. defaultLookup().find("strlen") finds the symbol in the standard C library.
  2. FunctionDescriptor.of(JAVA_LONG, ADDRESS) describes the C signature size_t strlen(const char*): the return value maps to long and the argument is a pointer. downcallHandle turns it into a Java MethodHandle.
  3. Arena.ofConfined() owns off-heap memory that only the current thread can use. allocateFrom("Hello Java 25") copies the string as UTF-8 with a terminating NUL byte, as C expects.
  4. invokeExact calls the native function. The (long) cast is required because invokeExact needs the exact type. The result is 13, the number of characters in "Hello Java 25".
  5. When the try block ends, the arena closes and frees the memory deterministically; any later access fails safely instead of crashing. Final in Java 22 (JEP 454).
What is the Key Derivation Function API? And what are Stable Values?

KDF API (final in 25, JEP 510) — standard API for algorithms like HKDF (and future post-quantum schemes) to derive keys from a secret.

🧠 How this works

  1. KDF.getInstance("HKDF-SHA256") gets an HKDF implementation using the same provider-based factory pattern as Cipher or MessageDigest.
  2. HKDF has two phases. ofExtract().addIKM(sharedSecret).addSalt(salt) sets up the extract step, which condenses the input key material (e.g. a Diffie-Hellman shared secret) into a strong pseudorandom key.
  3. thenExpand("session-key".getBytes(), 32) adds the expand step: the context "info" label separates keys for different purposes, and 32 is the output length in bytes (256 bits).
  4. deriveKey("AES", params) runs both steps and wraps the 32 bytes as an AES-256 SecretKey. Final in Java 25 (JEP 510).

Stable Values (preview, JEP 502) — lazily initialized, set-at-most-once values that the JIT treats like final constants. Useful for deferred, expensive initialization.

🧠 How this works

  1. Stable Values are a preview API in Java 25 (JEP 502), so compile and run with --enable-preview.
  2. StableValue.of() creates an empty holder; the field is final but its content is set later, at most once.
  3. orElseSet(supplier) returns the value if set; otherwise it runs the supplier once, stores the result and returns it. This is thread-safe, so concurrent first calls still create only one Logger.
  4. Once set, the JIT can treat the value as a constant, like a static final field. You get lazy initialization without double-checked locking or volatile.

JVM & performance

What are Compact Object Headers (JEP 519)?

A product (non-experimental) feature in Java 25 that shrinks the object header from 12–16 bytes to 8 bytes on 64-bit JVMs. Typical heaps shrink 10–20%, with fewer GCs and better cache locality. Opt-in:

🧠 How this works

  1. Every Java object starts with a header: a mark word (hash, lock and GC bits) plus a class pointer, normally 12–16 bytes on 64-bit JVMs.
  2. -XX:+UseCompactObjectHeaders packs the class pointer into the mark word, so the header is 8 bytes. Small objects like Integer or small records shrink noticeably.
  3. In Java 24 it was experimental and also needed -XX:+UnlockExperimentalVMOptions. In Java 25 (JEP 519) it is a product option but still off by default, so you must pass the flag.
  4. No code changes are needed. Measure heap use and GC frequency before and after.
How do the AOT cache features (JEPs 483, 514, 515) improve startup?

Project Leyden: a training run records which classes are loaded/linked and which methods are hot; the resulting AOT cache lets later runs start with classes already loaded and linked, and with profiles ready so the JIT optimizes sooner. Java 25 reduced it to a single step:

🧠 How this works

  1. The first command is a training run: the app runs normally while the JVM records which classes are loaded and linked and which methods are hot. On exit, -XX:AOTCacheOutput=app.aot writes the cache file (JEP 514 made this a single step in Java 25).
  2. In Java 24 the same result needed two commands, one with -XX:AOTMode=record and one with -XX:AOTMode=create.
  3. Production runs pass -XX:AOTCache=app.aot. Classes come from the cache already loaded and linked (JEP 483), and the stored method profiles (JEP 515) let the JIT compile hot code sooner.
  4. The cache is only valid for the same JDK build and a compatible classpath. Make the training run exercise typical startup paths so the cache is useful.

Spring Boot apps commonly see 30–40%+ faster startup with no code changes (unlike GraalVM native image, there are no closed-world restrictions).

What GC options does Java 25 offer?
  • G1 — default; balanced.
  • ZGC — generational only (non-generational mode removed in 24); sub-millisecond pauses on multi-TB heaps.
  • Shenandoah — generational mode is now a product feature (JEP 521).
  • Parallel and Serial — throughput / tiny containers.

🧠 How this works

  1. -XX:+UseZGC selects ZGC. Since Java 24 it is always generational (the old mode was removed), so -XX:+ZGenerational is no longer needed.
  2. Generational ZGC collects short-lived young objects more often and cheaply, while most work stays concurrent with the application, keeping pauses very short.
  3. The second line selects Shenandoah in generational mode. In Java 25 (JEP 521) this is a product feature, so the experimental unlock flag is no longer needed.
  4. With neither flag, the JVM uses G1, the default.
What was removed or disabled by Java 25 that can break upgrades?
  • Security Manager permanently disabled (Java 24, JEP 486) — -Djava.security.manager=allow no longer works.
  • 32-bit x86 port removed (JEP 503).
  • Non-generational ZGC removed (Java 24).
  • sun.misc.Unsafe memory-access methods warn on use (JEP 498) on the path to removal; use VarHandle / FFM API.
  • JNI usage now emits warnings unless --enable-native-access is granted (JEP 472).
  • Default charset is UTF-8 since Java 18 — legacy code relying on platform encoding may behave differently.
What JFR improvements arrived in Java 25?
  • CPU-time profiling on Linux (JEP 509, experimental) — more accurate CPU sampling.
  • Cooperative sampling (JEP 518) — safer, more stable stack sampling.
  • Method timing & tracing (JEP 520) — time specific methods without bytecode agents.

🧠 How this works

  1. -XX:StartFlightRecording starts Java Flight Recorder at JVM startup.
  2. jdk.MethodTiming#filter=com.app.OrderService::placeOrder turns on the method-timing event (JEP 520, Java 25) for that one method. The JVM instruments it at runtime to record invocation counts and execution times, with no bytecode agent or code change.
  3. filename=rec.jfr sets where the recording is saved; open it with the jfr tool or JDK Mission Control.
  4. Narrow filters keep overhead low: only the matched methods are instrumented.

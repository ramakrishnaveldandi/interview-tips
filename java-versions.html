⚖️ Java 8 vs Java 17 vs Java 25

The three LTS releases you are most likely to be asked about: Java 8 (the legacy workhorse), Java 17 (today's enterprise baseline) and Java 25 (the newest LTS). Compare them feature by feature, see the same problem solved in each, and prepare for migration questions.

A simple immutable DTO: class vs record

Java 8 — ~30 lines of boilerplate (or Lombok):

🧠 How this works

  1. In Java 8, an immutable DTO needs everything written by hand: final class, private final fields, a constructor, getters and the three Object methods.
  2. equals, hashCode and toString must be kept in sync with the fields by hand. Adding a field and forgetting one of them is a classic bug (e.g. broken HashMap lookups).
  3. That is why teams used Lombok (@Value) or IDE generation. It works, but adds a dependency or a lot of noise.

Java 17 — one line:

🧠 How this works

  1. The record declares the same data, and the compiler generates the fields, canonical constructor, accessors and value-based equals/hashCode/toString.
  2. Accessors are name() and email(), not getName(). Jackson and most frameworks support this natively.
  3. Records are final in Java 16 (JEP 395), so this works on Java 17. It is shorter, cannot drift out of sync, and clearly says "this is plain data".

Java 25 — same record, plus you can deconstruct it with record patterns:

🧠 How this works

  1. The record is identical. The new part is consuming it: obj instanceof UserDto(String name, String email) is a record pattern.
  2. If obj is a UserDto, the JVM calls the accessors and binds the results to name and email, so type test, cast and field extraction happen in one step.
  3. The bindings are in scope after &&, so email.endsWith("@corp.com") runs only when the pattern matched.
  4. Record patterns are final in Java 21 (JEP 440). In Java 17 you would write instanceof UserDto u and then call u.email().
Type check and cast: instanceof

🧠 How this works

  1. Java 8: test, then declare a new variable and cast it by hand, repeating String three times.
  2. Java 17: obj instanceof String s tests and binds in one step (final in 16). s can be used right away in the && condition because flow analysis knows the match succeeded.
  3. Java 25 (since 21): a pattern switch checks many types in one expression. case null handles null explicitly; without it, a null would throw an NPE.
  4. Cases are tried top to bottom. when i > 0 is a guard, so a non-positive Integer falls to default. List<?> uses a wildcard because generic type arguments are erased at runtime.
  5. default is required here because Object is not sealed, so the compiler cannot prove the cases are exhaustive.
Branching: switch statement → switch expression → pattern switch

🧠 How this works

  1. Java 8: a switch statement. BLOCKED falls through to DELETED on purpose, but forgetting a break elsewhere silently runs the next case. label must be assigned in every path, which the compiler checks only because of default.
  2. Java 17: a switch expression with arrows (final in 14). No fall-through, several labels per case (BLOCKED, DELETED), and the result is assigned directly.
  3. Because all enum constants are listed, the compiler accepts the expression without default. If a constant is added later, the code stops compiling until it is handled, and a compiled class that meets an unknown constant at runtime throws an error instead of returning garbage.
  4. Java 25 (since 21): Event is sealed, so the switch checks it covers every subtype. Record patterns like Purchase(var u, var amt) deconstruct the event, and the when amt > 1000 guard selects the large purchases.
  5. The guarded Purchase case comes before the general one, and Purchase(var u, _) uses the unnamed pattern (Java 22) for the unused amount.
Handling 10,000 concurrent blocking calls

🧠 How this works

  1. Java 8/17: a fixed pool of 200 platform threads. Each one is an OS thread with its own stack, so you cannot create 10,000. At most 200 fetches run at once and the rest wait in the queue.
  2. While a pool thread waits on fetch(url), it sits idle but stays busy for the pool, so throughput is limited by pool size, not by CPU.
  3. Java 25 (virtual threads final since 21): newVirtualThreadPerTaskExecutor() gives each URL its own virtual thread. When fetch blocks, the virtual thread unmounts from its carrier, so all 10,000 can wait at once on a handful of OS threads. Leaving the try block waits for all tasks.
  4. The last form uses Gatherers.mapConcurrent(100, ...) (Java 24). It runs fetches on virtual threads but caps concurrency at 100, protecting the remote service, and returns results in input order.
Hello World / small script

🧠 How this works

  1. Java 8: you must declare a public class and a public static void main(String[] args), then compile with javac and run with java.
  2. Java 11 added the source launcher (java Hello.java), which compiles in memory and runs, but the class/static-main boilerplate remained.
  3. Java 25 (JEP 512, final): a compact source file needs no class. void main() is an instance main method, and the compiler wraps the file in an implicit class.
  4. IO.println is a new java.lang.IO helper, so beginners and scripts avoid System.out. The output is the same.
Multi-line strings: concatenation vs text blocks

🧠 How this works

  1. Java 8: each line is a separate literal with an explicit \n, joined with +. It is noisy and easy to break by missing a newline or a space.
  2. Java 17/25: a text block (final in 15). The compiler removes the common leading indentation and turns line breaks into \n.
  3. Because the closing """ is on its own line, the text block also ends with \n, so both versions produce the same string.
  4. Single quotes and even double quotes need no escaping inside a text block, which makes SQL and JSON readable.
String Templates (STR."...") were previewed in 21–22 but withdrawn — they are not in Java 25. Use formatted() or MessageFormat.
Working with first/last elements and immutable collections

🧠 How this works

  1. Java 8: Arrays.asList wrapped in Collections.unmodifiableList gives a read-only view. The last element needs list.get(list.size() - 1), and Collectors.toList() returns a list whose mutability is not guaranteed (in practice an ArrayList).
  2. Java 17: List.of (Java 9) creates a truly immutable list that also rejects nulls, and stream.toList() (Java 16) returns an unmodifiable list with less code.
  3. Java 25 (since 21, JEP 431): List implements SequencedCollection, so getFirst(), getLast() and reversed() express intent directly and work the same across lists, deques and ordered sets.
  4. reversed() returns a view, not a copy. For an immutable List.of, the view is read-only as well.

Most useful features per version

Top 5 Java 8 features and why they matter
  1. Lambdas & method references — behaviour as data; concise callbacks.
  2. Stream API — declarative collection processing, easy parallelism.
  3. Optional — explicit "may be absent" return types.
  4. java.time — immutable, thread-safe date/time.
  5. CompletableFuture — composable async pipelines.

🧠 How this works

  1. employees.stream() starts a lazy pipeline; nothing runs until the terminal collect.
  2. filter keeps employees whose join date is within the last year, using immutable java.time.LocalDate arithmetic (minusYears(1) returns a new date).
  3. groupingBy(Employee::getDept, counting()) uses a method reference as the key function and a downstream collector to count each group.
  4. The result type is Map<String, Long> because counting() always produces Long. This is the declarative style that lambdas and streams brought in Java 8.
Top 5 Java 17 features and why they matter
  1. Records — DTOs, value objects, projections in one line.
  2. Sealed classes — closed domain hierarchies the compiler can reason about.
  3. Switch expressions — no fall-through bugs, returns a value.
  4. Text blocks — readable SQL, JSON, HTML in code.
  5. Pattern matching for instanceof + helpful NPEs — less casting, faster debugging.

🧠 How this works

  1. sealed interface Result<T> permits Ok, Err says a result is exactly one of two shapes, success or failure, and no other implementation can be added.
  2. Ok and Err are records, so they are implicitly final and immutable, and get equals/toString for free.
  3. Err<T> declares T even though it holds only a message, so it can implement Result<T> for any T.
  4. Sealed classes are final in Java 17 (JEP 409). From Java 21, switch (result) { case Ok<T> ok -> ...; case Err<T> err -> ...; } is checked for exhaustiveness with no default.
Top 5 Java 25 features and why they matter
  1. Virtual threads — massive concurrency with plain blocking code (and no synchronized pinning since 24).
  2. Pattern matching for switch + record patterns — data-oriented programming with exhaustive checks.
  3. Scoped Values — safe, cheap request context for virtual threads.
  4. Stream Gatherers — custom intermediate ops: windows, scans, concurrent mapping.
  5. Startup & footprint — AOT cache and compact object headers lower cloud cost.

🧠 How this works

  1. TENANT is a ScopedValue key (final in Java 25, JEP 506), declared once as a constant.
  2. The executor starts one virtual thread per request (final in Java 21), so each request gets its own cheap thread. Closing the executor waits for all of them to finish.
  3. Inside each task, ScopedValue.where(TENANT, req.tenant()).run(...) binds that request's tenant only for the call to process(req). Any code it calls can read it with TENANT.get().
  4. Each binding belongs to its own thread and scope, so tenants never leak between requests. Unlike ThreadLocal, there is no remove() to forget.

Migration

What problems do you hit migrating from Java 8 to 17?
  • Removed Java EE modules (Java 11): JAXB, JAX-WS, JavaBeans Activation, CORBA — add jakarta.xml.bind-api etc. as dependencies.
  • Strong encapsulation (JEP 403): reflection into JDK internals fails with InaccessibleObjectException — upgrade Lombok, Mockito, ByteBuddy, Spring, Hibernate; use --add-opens only as a stop-gap.
  • javax → jakarta: moving to Spring Boot 3 / Hibernate 6 renames javax.persistence, javax.servlet, javax.validation to jakarta.*. OpenRewrite automates it.
  • Removed/deprecated APIs: Nashorn, Thread.stop, applets, RMI activation; finalize() deprecated.
  • Build tooling: upgrade Maven compiler plugin (use <release>17</release>), Surefire, Gradle 7.3+, JaCoCo, and your Docker base image.
  • GC change: default moved from Parallel to G1 — re-check heap settings and remove obsolete flags like -XX:PermSize and CMS options.

🧠 How this works

  1. jdeps --jdk-internals scans the JAR and its lib/* dependencies for uses of internal JDK APIs (e.g. sun.misc), which strong encapsulation blocks on 17, and suggests replacements. --multi-release 17 tells it which version of multi-release JARs to analyse.
  2. jdeprscan --release 17 reports uses of APIs that are deprecated or removed as of Java 17.
  3. The OpenRewrite Maven plugin runs the UpgradeToJava17 recipe, which rewrites source and build files automatically. The recipe comes from the rewrite-migrate-java artifact, usually supplied with -Drewrite.recipeArtifactCoordinates.
  4. The trailing \ is just a shell line continuation. Run the scanners first to size the work, then use OpenRewrite for the mechanical changes.
What should you check when migrating from Java 17 to 25?
  • Security Manager is permanently disabled (Java 24) — remove System.setSecurityManager and policy files.
  • 32-bit x86 builds are gone; non-generational ZGC removed (-XX:-ZGenerational is obsolete).
  • Default charset UTF-8 (Java 18) — check file/console encoding assumptions, especially on Windows.
  • Virtual-thread readiness — if you enable them, review ThreadLocal usage, connection pool sizes and native calls; pinning on synchronized is fixed in 24+.
  • Warnings for sun.misc.Unsafe memory access and JNI (--enable-native-access), and dynamically loaded agents (JEP 451) — Mockito/ByteBuddy need -javaagent configured in tests.
  • Tooling — Maven 3.9+, compiler plugin 3.13+, Gradle 9.x (Gradle 8.14+ runs on 25), recent Lombok, Jacoco 0.8.13+, ASM-based libraries that must understand class file version 69.
  • Framework versions — Spring Boot 3.5+/4.x and Hibernate 6.6+/7 officially support Java 25.

🧠 How this works

  1. java.version is the property Spring Boot's parent POM reads to configure the Java level.
  2. maven.compiler.release is read directly by maven-compiler-plugin and becomes javac --release 25.
  3. --release compiles against the exact Java 25 API and emits class-file version 69. Unlike -source/-target, it also stops you from accidentally using APIs that do not exist in that release.
  4. The JDK running Maven must itself be 25 or newer, and plugins and bytecode libraries must understand class version 69.
Can you jump directly from Java 8 to Java 25?

Yes — you don't have to install each intermediate release. But treat it as two logical steps: first fix everything that breaks on 17 (modules, encapsulation, jakarta), then address the 18–25 changes. Run the test suite on both, and enable new features (records, virtual threads) only after the platform upgrade is green.

Compile with --release 25 but keep a CI job on the old JDK until cut-over so you can roll back.
Does code compiled on Java 8 run on Java 25?

Generally yes — the JVM is backward compatible for bytecode (class version 52 runs on a 25 JVM). Failures come from runtime behaviour: removed APIs/modules, encapsulated internals, old libraries that parse class files (ASM, cglib) or rely on sun.* classes. The reverse is not true: class version 69 (Java 25) won't load on older JVMs (UnsupportedClassVersionError).

Choosing a version

Which Java version should a new project choose in 2026?

Java 25 for new projects: newest LTS, virtual threads production-ready, best startup/footprint, and supported by Spring Boot 3.5/4.x. Choose Java 21 or 17 only if a platform, vendor or library you depend on is not yet certified for 25. Avoid starting anything new on Java 8.

Why do enterprises still run Java 8, and how would you justify upgrading?

Reasons: legacy app servers, frozen libraries, risk aversion, paid extended support. The business case for upgrading:

  • Cost — lower memory and faster startup reduce cloud bills; compact headers and better GCs compound this.
  • Security — modern TLS, crypto APIs, faster patch availability.
  • Ecosystem — Spring Boot 2.x is out of OSS support; Boot 3/4 require 17+.
  • Productivity & hiring — records, pattern matching and virtual threads mean less code and fewer bugs.
What is the Java release cadence and how often are LTS releases?

A feature release every 6 months (March and September) since Java 10. LTS releases are now every 2 years: 11 (2018), 17 (2021), 21 (2023), 25 (2025), with 27 expected in September 2027. Non-LTS releases get updates only until the next release, so production systems usually stay on LTS.

Fundamentals

What is the difference between JPA, Hibernate and Spring Data JPA?

What are the requirements for a class to be an entity?
  • Annotated with @Entity and has a primary key (@Id or @EmbeddedId).
  • A public or protected no-arg constructor.
  • Class must not be final, and persistent methods/fields not final (needed for lazy proxies).
  • Top-level class (not an enum, interface or record).

🧠 How this works

  1. @Entity tells the provider to map the class to a table; @Table renames it to employees and, when the schema is generated, creates a unique index on email.
  2. SEQUENCE + allocationSize = 50: Hibernate calls nextval('emp_seq') once and hands out the next 50 ids from memory (pooled optimizer), so the DB sequence must be defined with INCREMENT BY 50. Ids are known before the INSERT, which keeps JDBC batching possible.
  3. @Column(nullable = false, length = 100) mainly affects generated DDL (name varchar(100) not null); the database constraint is what actually enforces it.
  4. @Enumerated(EnumType.STRING) stores the enum name ('ACTIVE') instead of its position, so adding or reordering constants never changes the meaning of existing rows.
  5. The protected no-arg constructor is what Hibernate calls via reflection when it turns a result-set row back into an Employee (and when it creates lazy proxy subclasses).

What are the entity lifecycle states?
  • New / Transient — created with new, not associated with a persistence context.
  • Managed / Persistent — tracked by the persistence context; changes are flushed automatically (dirty checking).
  • Detached — was managed, but the context was closed/cleared; changes are not tracked.
  • Removed — scheduled for deletion on flush.

🧠 How this works

  1. new Employee(...) is just a Java object — the persistence context knows nothing about it, so no SQL is possible yet.
  2. persist(e) makes it managed and assigns an id. With SEQUENCE the INSERT is queued until flush/commit; with IDENTITY it runs immediately to obtain the id.
  3. setName() on a managed entity needs no save call: at flush Hibernate compares the entity with its snapshot (dirty checking) and generates the INSERT/UPDATE for you.
  4. detach(e) stops tracking — further changes, and any not-yet-flushed changes for that entity, are not synchronized.
  5. merge(e) loads (SELECT) or reuses the managed instance with that id, copies e's state onto it and returns that managed copy m; e itself stays detached, which is why you must use the return value.
  6. remove(m) only works on a managed instance; it schedules a DELETE FROM employees WHERE id = ? that executes at flush/commit.
What is the persistence context (first-level cache)?

The persistence context is the set of managed entity instances for an EntityManager — typically scoped to one transaction in Spring. It guarantees:

  • Identity — within one context, the same row is always the same Java object.
  • Caching — repeated find() for the same id hits memory, not the DB.
  • Write-behind — SQL is batched and executed on flush/commit.
  • Dirty checking — modified managed entities are updated automatically.
Loading thousands of entities in one transaction bloats the context. In batch jobs call em.flush(); em.clear(); periodically.
Explain persist, merge, remove, find and getReference.
  • persist(e) — makes a new entity managed; returns void. Throws if detached.
  • merge(e) — copies state of a detached entity onto a managed instance and returns it. Use the returned object.
  • remove(e) — marks a managed entity for deletion.
  • find(Class, id) — hits the DB immediately (or cache); returns null if not found.
  • getReference(Class, id) — returns a lazy proxy without a query; throws EntityNotFoundException on first access if missing. Great for setting foreign keys.

🧠 How this works

  1. getReference(Customer.class, customerId) returns an uninitialized proxy that only knows its id — no SELECT is executed.
  2. Setting it on o is all the owning @ManyToOne needs: at flush Hibernate writes INSERT INTO orders (..., customer_id) VALUES (..., ?) using the proxy's id.
  3. Compared with find(), this saves one SELECT per association you set — handy when you only have an id from a request.
  4. If the id doesn't exist, the proxy throws EntityNotFoundException only when you touch a non-id property; otherwise the foreign-key constraint fails at INSERT time.

Relationships

Explain owning side and mappedBy in a bidirectional @OneToMany.

The owning side holds the foreign key and controls the DB column — in one-to-many it is always the @ManyToOne side. The inverse side declares mappedBy and is ignored for writes, so keep both sides in sync with helper methods.

🧠 How this works

  1. Employee.department (the @ManyToOne) is the owning side: its value is what Hibernate writes into the employees.department_id column.
  2. mappedBy = "department" marks Department.employees as the inverse side — Hibernate ignores this list when deciding the FK. Adding to the list without calling e.setDepartment(this) would save the employee with department_id = NULL.
  3. The helper addEmployee keeps both sides in sync in memory and in the DB. Persisting the department with CascadeType.ALL issues INSERT INTO department followed by one INSERT INTO employee (..., department_id) per child.
  4. removeEmployee + orphanRemoval = true: the dereferenced employee gets a DELETE at flush rather than just having its FK nulled.
  5. FetchType.LAZY on the @ManyToOne means loading an employee gives a department proxy; the department SELECT runs only when you access it.
A unidirectional @OneToMany without @JoinColumn creates an extra join table — usually not what you want.
How do you map @ManyToMany? When should you use an explicit join entity?

🧠 How this works

  1. Student.courses is the owning side: @JoinTable defines a student_course(student_id, course_id) table, and adding a course to this set causes INSERT INTO student_course at flush.
  2. Course.students uses mappedBy, so changes made only to that set write nothing — update both sides (helper methods) to keep memory and DB consistent.
  3. Why Set: for a List (a "bag") Hibernate can't identify an individual row, so removing one element deletes all of the student's join rows and re-inserts the rest. With a Set it issues a single DELETE ... WHERE student_id = ? AND course_id = ?.
  4. Both collections are LAZY by default; reading student.getCourses() fires one SELECT joining student_course and course.

As soon as the link needs its own data (enrolled date, grade), replace it with an entity Enrollment having two @ManyToOnes. Never use CascadeType.REMOVE on many-to-many.

What cascade types exist? What's the difference between CascadeType.REMOVE and orphanRemoval?

Cascade types: PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL. They propagate an EntityManager operation from parent to children.

  • REMOVE — deletes children when the parent is deleted.
  • orphanRemoval = true — additionally deletes a child when it is removed from the collection (dereferenced).
Cascade only from aggregate root to its owned parts (Order → OrderLines). Never cascade from child to parent.

Queries

JPQL vs Criteria API vs native SQL — when to use each?
  • JPQL — object-oriented, portable, queries entities and fields. Default choice.
  • Criteria API — type-safe, programmatic; good for dynamic filters (or use Specifications / Querydsl).
  • Native SQL — DB-specific features (window functions, CTEs, JSON operators, hints).

🧠 How this works

  1. JPQL is written against entity and field names (Employee, e.salary); Hibernate translates it into SQL against the mapped table and columns, e.g. SELECT ... FROM employees e WHERE e.salary > ? ORDER BY e.salary DESC.
  2. :min becomes a JDBC bind parameter, so the value is never concatenated into SQL — this prevents SQL injection and lets the DB reuse the statement plan.
  3. The Criteria version builds the same query as an object tree; in Hibernate 6 both JPQL and Criteria go through the same SQM model, so they produce the same SQL.
  4. The native query is sent as-is; because a result class is given, Hibernate maps the returned columns onto managed Employee entities.
  5. All three return managed entities, so changes to the results are dirty-checked and flushed like any loaded entity.
What are Spring Data derived query methods? Show @Query and @Modifying.

🧠 How this works

  1. At startup Spring Data parses each method name into a query (and fails startup if a property doesn't exist). findByDepartmentNameAndStatusOrderByNameAsc resolves DepartmentName to department.name, producing roughly ... JOIN department d WHERE d.name = ? AND e.status = ? ORDER BY e.name ASC.
  2. IgnoreCase wraps both sides in upper(); existsBy runs a lightweight select limited to one row and returns boolean; countBy runs SELECT count(...); Top5 + GreaterThan becomes WHERE salary > ? with a 5-row limit.
  3. join fetch e.department loads the employee and its department in one SELECT with a JOIN, so accessing the department later costs no extra query.
  4. @Modifying marks the JPQL as an UPDATE: it executes a single UPDATE employees SET status = ? WHERE last_login < ? directly in the DB and returns the affected row count.
  5. Because that bulk UPDATE bypasses the persistence context, already-loaded entities would show old values; clearAutomatically = true clears the context afterwards so the next read hits the DB.
Bulk @Modifying queries skip lifecycle callbacks, @Version checks and cascades, and leave the context stale — hence clearAutomatically = true.
CrudRepository vs PagingAndSortingRepository vs JpaRepository — what does each give you?

Spring Data generates the implementation of a repository interface at startup, so you write no DAO boilerplate. You pick the interface that exposes the operations you need:

InterfaceAdds
Repository<T, ID>Marker only — expose just the methods you declare
CrudRepository / ListCrudRepositorysave, saveAll, findById, findAll, existsById, count, deleteById, delete (the List variant returns List instead of Iterable)
PagingAndSortingRepositoryfindAll(Sort), findAll(Pageable) — since Spring Data 3 it no longer extends CrudRepository
JpaRepositoryAll of the above plus JPA-specific flush, saveAndFlush, saveAllAndFlush, deleteAllInBatch, getReferenceById, and Query by Example

🧠 How this works

  1. Spring creates a proxy for the interface at startup; inherited methods like save/findAll are implemented by SimpleJpaRepository, and the declared methods are derived from their names.
  2. findByDept → WHERE dept = ?; findByEmailIgnoreCase → WHERE upper(email) = upper(?); existsByEmail returns true/false without loading the full entity list.
  3. PageRequest.of(0, 20, Sort.by("name").ascending()) asks for the first page (pages are zero-based) of 20 rows: Hibernate adds ORDER BY name ASC and a dialect-specific limit/offset.
  4. Returning Page also triggers a SELECT count(*) so getTotalElements() is known; Spring Data skips it when the first page already holds fewer rows than the page size.
To keep a repository read-only, extend Repository and declare only findById/findAll — callers then can't delete or save by accident.
What are projections? Compare interface and DTO (record) projections.

Projections fetch only the columns you need instead of full managed entities — faster and no dirty checking overhead.

🧠 How this works

  1. Interface projection: for a closed projection like EmployeeSummary, Spring Data selects only name and email and wraps each row in a generated proxy whose getters return those values.
  2. DTO projection: select new com.acme.hr.EmployeeDto(...) calls the record's constructor once per row; the fully qualified class name is required in JPQL.
  3. e.department.id uses the FK column department_id directly, so Hibernate 6 doesn't need a join for it.
  4. Projections are not managed entities — no snapshots, no dirty checking, and no accidental UPDATEs — which is why they're faster for read-only screens.
  5. The dynamic projection picks the result shape per call: findByDepartmentId(id, EmployeeSummary.class) or findByDepartmentId(id, Employee.class).
How do pagination and sorting work in Spring Data?

🧠 How this works

  1. Page runs two queries: the data query with limit/offset and a SELECT count(*) with the same WHERE, so it can report total elements and pages.
  2. Slice skips the count: Spring Data fetches size + 1 rows, and if the extra row exists, hasNext() is true.
  3. Sort.by("name").ascending().and(Sort.by("id")) becomes ORDER BY name ASC, id ASC — the id tie-breaker gives a stable order so rows don't repeat or vanish between pages.
  4. Offset paging makes the DB read and discard all skipped rows, so deep pages get slower — which is why keyset/scroll paging exists.

In controllers, accept Pageable directly: GET /employees?page=0&size=20&sort=name,asc. For very large tables prefer keyset (seek) pagination — Spring Data 3.1+ supports ScrollPosition / Window<T>.

How do you build dynamic queries with Specifications?

🧠 How this works

  1. JpaSpecificationExecutor adds methods like findAll(Specification, Pageable); Spring Data turns the specification into a Criteria query at call time.
  2. Each Specification is a lambda receiving root, query and cb and returning a Predicate. root.get("department").get("name") navigates the association, which adds a join to the department table.
  3. Returning null means "no restriction", so combining with .and() puts only the supplied filters in the WHERE clause — e.g. with only min set: WHERE salary > ?.
  4. The pageable adds ORDER BY and a limit, plus a count query for the Page result — all built from one reusable set of predicates.

Locking, auditing & advanced mapping

Optimistic vs pessimistic locking — how and when?

Optimistic: add a @Version column. Every UPDATE includes where version = ?; if 0 rows change, JPA throws OptimisticLockException (Spring: ObjectOptimisticLockingFailureException). Best when conflicts are rare — no DB locks held.

🧠 How this works

  1. When an Account is loaded, Hibernate remembers its version (say 3).
  2. On flush the UPDATE includes the version check and bumps it: UPDATE account SET balance = ?, version = 4 WHERE id = ? AND version = 3.
  3. If another transaction committed first, the version is already 4, so 0 rows are updated; Hibernate treats that as a conflict and throws OptimisticLockException (wrapped by Spring), and the transaction rolls back.
  4. No row lock is held between read and write, so the usual recovery is to reload and retry. Never set version yourself — the provider manages it.

Pessimistic: takes a DB row lock (SELECT … FOR UPDATE). Use when conflicts are frequent and retrying is expensive (seat booking, inventory).

🧠 How this works

  1. @Lock(PESSIMISTIC_WRITE) makes Hibernate append the dialect's row-lock clause, e.g. SELECT ... FROM account WHERE id = ? FOR UPDATE.
  2. The row stays locked until the surrounding transaction commits or rolls back, so this must run inside @Transactional; other writers (and other FOR UPDATE readers) block until then.
  3. The jakarta.persistence.lock.timeout hint (milliseconds) asks the DB to wait at most about 3 seconds for the lock; how it's applied depends on the database, and if the wait is exceeded a lock-timeout exception is thrown instead of hanging.
  4. Unlike @Version, conflicts are prevented up front rather than detected at commit, at the cost of blocking concurrent transactions.
How do you implement auditing (created/modified by & date)?

🧠 How this works

  1. @EnableJpaAuditing activates Spring Data's auditing, and auditorAwareRef points to the bean that answers "who is the current user?" — here the Spring Security principal's name (empty if no one is logged in).
  2. AuditingEntityListener hooks the JPA @PrePersist and @PreUpdate callbacks: on persist it fills createdAt/createdBy (and by default the modified fields too); on update it refreshes updatedAt/updatedBy.
  3. Because the callbacks run just before the INSERT/UPDATE SQL is generated, the values end up in the same statement — no extra query.
  4. @Column(updatable = false) leaves the created columns out of every UPDATE statement, so they can't be overwritten.
  5. @MappedSuperclass copies these columns into each subclass entity's own table. Bulk JPQL updates skip entity callbacks, so they won't touch these fields.

For full change history (who changed what), use Hibernate Envers (@Audited).

🧠 How this works

  1. SINGLE_TABLE stores every subclass in one payment table with all columns: id, type, amount, last4, vpa.
  2. Persisting a CardPayment generates INSERT INTO payment (amount, last4, type, id) VALUES (?, ?, 'CARD', ?); vpa stays NULL — which is why subclass columns must be nullable.
  3. A polymorphic query select p from Payment p is a single SELECT with no joins; Hibernate reads the type column of each row to decide whether to instantiate CardPayment or UpiPayment.
  4. Querying a subclass adds the discriminator filter automatically, e.g. ... WHERE type = 'UPI'.
What are @Embeddable types and composite keys?

An @Embeddable is a value object without its own identity whose fields are stored in the owning entity's table. Since JPA 3.2 (Jakarta EE 11) / Hibernate 6.2+, a record can be an embeddable.

🧠 How this works

  1. Address has no table or id of its own: its fields become columns of customer (street, city, zip).
  2. @AttributeOverride renames just the city column to billing_city; the same embeddable could be embedded twice (billing/shipping) with different overrides.
  3. When loading, Hibernate builds the record from those columns via its constructor; if all of them are NULL, billingAddress is null.
  4. OrderLineId as @EmbeddedId makes (order_id, line_no) the composite primary key of order_line. A record gives you the required value-based equals()/hashCode() for free, which the persistence context relies on to identify rows.
  5. There's no generator: you assign the key yourself and look rows up with em.find(OrderLine.class, new OrderLineId(orderId, lineNo)).

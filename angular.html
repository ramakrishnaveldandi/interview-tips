What makes up an Angular component?

A TypeScript class decorated with @Component providing a selector, a template, optional styles and its imports (other components, directives, pipes). Since v19, components are standalone by default.

🧠 How this works

  1. input.required<string>() and input(0) create signal inputs: the parent's binding value is read by calling name() / price().
  2. While rendering, Angular tracks every signal the template reads. When the parent passes a new price, that signal changes and only this component's view is marked dirty and refreshed — this works with OnPush and zoneless apps.
  3. onSale is a computed: it re-evaluates only when price() changes and caches the result, so price = 400 shows the Sale badge, price = 900 hides it.
  4. Clicking the button calls add.emit(name()); the parent receives the name via (add)="onAdd($event)". CurrencyPipe must be in imports because standalone components only see what they import.

Explain the component lifecycle hooks in order.
  1. constructor — DI only; inputs not yet set.
  2. ngOnChanges — whenever a decorator-based @Input changes (gets SimpleChanges).
  3. ngOnInit — once, after first inputs; fetch initial data here.
  4. ngDoCheck — every change-detection run (custom checks; use sparingly).
  5. ngAfterContentInit / ngAfterContentChecked — projected <ng-content> ready / checked.
  6. ngAfterViewInit / ngAfterViewChecked — the component's view and children ready / checked.
  7. ngOnDestroy — cleanup (or use DestroyRef.onDestroy()).

With signals, many hooks become unnecessary: use computed() instead of ngOnChanges, and afterNextRender() / afterRenderEffect() for DOM work after rendering.

Standalone components vs NgModules — what changed?

Standalone components declare their own dependencies in imports, so no @NgModule is needed. Apps bootstrap with bootstrapApplication() and configure providers through functions like provideRouter() and provideHttpClient(). Since v19 standalone: true is the default.

🧠 How this works

  1. bootstrapApplication starts the app from a standalone root component — no root NgModule; the providers array creates the root (environment) injector.
  2. provideZonelessChangeDetection() removes Zone.js-driven checking: Angular now re-renders when signals change, template event handlers fire, the async pipe emits or markForCheck() is called.
  3. provideRouter(routes, withComponentInputBinding()) registers the routes and lets route params, query params, data and resolver results flow straight into component input()s.
  4. provideHttpClient(withInterceptors([authInterceptor])) makes HttpClient injectable and wraps every request in the listed functional interceptors, in order.
Benefits: less boilerplate, clearer dependencies, better tree-shaking and simpler lazy loading. NgModules still work for legacy code.
Structural vs attribute directives — and what replaced *ngIf/*ngFor?
  • Structural directives change DOM structure (add/remove elements) — *ngIf, *ngFor, or custom ones using TemplateRef + ViewContainerRef.
  • Attribute directives change the look/behaviour of an existing element — ngClass, ngStyle, or custom ones.

Since v17 the built-in control flow (@if, @for, @switch) replaces the structural directives: it is faster, needs no imports and @for requires track.

🧠 How this works

  1. @if (user(); as u) reads the signal once, and if it is truthy stores it in the local alias u; otherwise the @else branch (Sign in link) renders.
  2. Because user() is a signal read in the template, setting the user (e.g. after login) automatically swaps the branch on the next change detection.
  3. @for requires track: Angular uses item.id as each row's identity, so when the list is re-fetched it reuses the existing DOM rows with the same id instead of destroying and re-creating them.
  4. $index is a built-in loop variable (0-based, hence i + 1); @empty renders when the array has zero items.

Pure vs impure pipes?

A pure pipe (default) re-runs only when its input reference or primitive value changes — cheap and cacheable. An impure pipe (pure: false) runs on every change-detection cycle, needed when it depends on mutable data (e.g. async) but costly.

🧠 How this works

  1. @Pipe({ name: 'initials' }) makes the class usable in templates as {{ fullName | initials }}.
  2. Walk-through: 'asha rao' → split(' ') gives ['asha','rao'] → first letters ['a','r'] → join('') = 'ar' → 'AR'.
  3. Pipes are pure by default: Angular calls transform again only when the input value changes (by === for primitives, by reference for objects), so it is cheap even in big lists.
  4. That is why mutating an array passed to a pure pipe does not re-run it — the reference is the same.
Mutating an array (list.push()) won't re-trigger a pure pipe — create a new array instead.

Signals & Change Detection

What are signals? Explain signal, computed and effect.

A signal is a reactive value wrapper that notifies consumers when it changes, letting Angular update exactly the views that read it.

🧠 How this works

  1. signal(0) holds a value; reading count() inside a reactive context (template, computed, effect) registers a dependency.
  2. double is lazy and memoised: it is computed on first read and recomputed only after count changes — reading it 10 times does the work once.
  3. effect runs once initially, then again whenever a signal it read (count) changes. Effects are scheduled, so several quick updates may result in a single run with the latest value.
  4. inc() uses update(c => c + 1) to derive the new value from the old; this notifies double, the effect and any template that reads them.
  • computed is read-only and recalculates only when a dependency changes.
  • effect is for side effects (logging, localStorage, DOM sync) — not for deriving state.
  • linkedSignal is writable state that resets when a source changes (e.g. selected item when the list changes).
  • resource() / httpResource() load async data into signals (still experimental in v20).

How does change detection work and what does OnPush do?

With Default strategy, Angular checks the whole component tree after any async event (triggered by zone.js). With OnPush, a component is checked only when:

  • an input reference changes,
  • an event fires in the component or its children,
  • an async pipe emits or a signal read in the template changes,
  • markForCheck() is called manually.

🧠 How this works

  1. With ChangeDetectionStrategy.OnPush, Angular skips checking this component on every app-wide tick.
  2. It is checked only when an input changes reference (a new items array), an event fires in its template, a signal it reads changes, an async pipe emits, or markForCheck() is called.
  3. So items.push(x) on the parent's existing array is not detected through the input — pass a new array ([...items, x]) instead.
  4. Because items is a signal input, reading items() in the template also ties the view to that signal for precise updates.
Combine OnPush with immutable data and signals for predictable, fast rendering.
zone.js vs zoneless change detection?

zone.js monkey-patches browser APIs (setTimeout, events, XHR) and triggers change detection after each. It is convenient but adds bundle size, overhead and confusing stack traces.

Zoneless (stable since v20 via provideZonelessChangeDetection()) schedules change detection only when Angular is notified: signal updates, template events, async pipe, markForCheck(), or input changes.

  • Remove zone.js from polyfills in angular.json.
  • Code that mutates plain fields inside setTimeout or third-party callbacks won't refresh the view — use signals.
  • Gains: smaller bundles, fewer checks, better Core Web Vitals, easier debugging.

Subject vs BehaviorSubject vs ReplaySubject vs AsyncSubject?
  • Subject — multicast, no initial value; late subscribers miss past values.
  • BehaviorSubject — needs an initial value and replays the latest value to new subscribers (classic state holder).
  • ReplaySubject(n) — replays the last n values.
  • AsyncSubject — emits only the final value on completion.

🧠 How this works

  1. providedIn: 'root' makes one shared instance for the whole app, so every component injecting CartService sees the same cart.
  2. BehaviorSubject always holds a current value (starting with []) and replays it immediately to each new subscriber — a late-loading header still gets the current count.
  3. add() pushes a new array via next([...value, item]); immutability keeps OnPush components and comparisons working.
  4. count$ is derived with map, so it emits 0, then 1, 2… automatically every time items$ emits. Keeping the subject private means only the service can change state.

🧠 How this works

  1. valueChanges emits on every keystroke. debounceTime(300) waits until the user pauses typing for 300 ms and emits only the latest value.
  2. distinctUntilChanged() drops a value equal to the previous one (e.g. typing a then deleting it back to the same term), and filter ignores terms of 2 characters or fewer.
  3. switchMap maps each term to an HTTP call and unsubscribes from the previous one when a new term arrives, cancelling the stale request — so results for lap never overwrite results for laptop.
  4. catchError is inside the inner pipe on purpose: a failed request becomes [] and the outer stream stays alive. Placed outside, one error would complete the whole search stream.
  5. Nothing runs until something subscribes, typically results$ | async in the template, which also unsubscribes on destroy.
How do you avoid memory leaks from subscriptions?
  • async pipe — subscribes and unsubscribes automatically.
  • toSignal() — converts to a signal and cleans up with the injection context.
  • takeUntilDestroyed() — completes the stream when the component is destroyed.
  • HTTP observables complete on their own, but long-lived ones (intervals, store selections, websockets, form valueChanges) do not.

🧠 How this works

  1. inject(ApiService) in a field initializer works because fields are initialized inside the injection context during construction.
  2. toSignal subscribes to stats$ immediately, exposes the latest value as a signal (null until the first emission) and unsubscribes automatically when the component is destroyed.
  3. interval(5000) emits every 5 s; takeUntilDestroyed() (called in the constructor, so it can find DestroyRef) completes the stream when the component is destroyed — no manual ngOnDestroy and no leak.

Routing

How do you lazy load routes?

🧠 How this works

  1. The router matches paths in array order and the first match wins, which is why the wildcard '**' must be last.
  2. loadComponent uses a dynamic import(), so the bundler emits a separate chunk that is downloaded only when /profile/42 is first visited.
  3. canMatch: [adminGuard] runs before the route is matched: if it returns false the router keeps looking at other routes and the admin chunk is never downloaded.
  4. loadChildren lazily loads a whole array of child routes (ADMIN_ROUTES) under /admin.

Each lazy route becomes a separate chunk downloaded on first navigation, reducing the initial bundle.

How do you write a route guard in modern Angular?

Class-based guards are deprecated in favour of functional guards that use inject(). Return true, false, a UrlTree (redirect), or an Observable/Promise of those.

🧠 How this works

  1. A functional guard runs in an injection context, so it can call inject() directly.
  2. Return values: true allows navigation; a UrlTree cancels it and redirects (here to /login?returnUrl=/orders), which is preferred over calling router.navigate inside a guard. Observables or Promises of these are also allowed.
  3. roleGuard('ADMIN') is a factory: calling it returns a new CanActivateFn that closes over role, so one function serves many roles.
  4. In canActivate: [authGuard, roleGuard('ADMIN')] every guard must allow navigation; if any returns false or a UrlTree, the route is not activated.
Guards are UX only — always enforce authorization on the backend.
What are resolvers and how do you read route params as inputs?

A resolver fetches data before the route activates. With withComponentInputBinding(), path params, query params and resolved data bind directly to component inputs.

🧠 How this works

  1. When navigating to /users/7, the router runs userResolver before activating the route and waits for the returned Observable to emit.
  2. route.paramMap.get('id') reads '7'; the ! tells TypeScript it is not null because the path declares :id.
  3. With withComponentInputBinding(), the router binds the path param to the id input and the resolved value under key user to the user input, so the component renders with data ready.
  4. Trade-off: navigation waits for the request, so slow APIs delay the page — show a global loading indicator or load inside the component instead.

HTTP & Interceptors

Write an interceptor that adds a JWT bearer token and handles 401.

🧠 How this works

  1. Each HttpClient call passes through the interceptor chain: req is the outgoing request and next(req) forwards it to the next interceptor or the backend, returning the response Observable.
  2. Requests are immutable, so req.clone({ setHeaders }) creates a copy with the Authorization header — only for URLs starting with /api, so tokens never go to third-party hosts.
  3. catchError on the response stream sees server errors: on 401 it logs out and redirects, then re-throws with throwError so the calling code still gets the error.
  4. inject() works because functional interceptors run in an injection context. withFetch() makes HttpClient use the Fetch API instead of XMLHttpRequest (recommended for SSR).
Requests are immutable — always clone(). Only attach tokens to your own API origin to avoid leaking them to third parties. For refresh-token flows, queue requests while one refresh call is in flight.
How do you call a REST API with HttpClient and handle errors?

🧠 How this works

  1. http.get returns a cold Observable: no request is sent until someone subscribes, and each subscription sends its own request.
  2. params: { page, size: 20 } is serialized into the URL as /api/employees?page=0&size=20.
  3. retry({ count: 2, delay: 500 }) resubscribes on error, i.e. re-sends the request up to 2 more times with a 500 ms pause (3 attempts total).
  4. catchError comes after retry, so it runs only if all attempts fail, and replaces the error with an empty page so the UI still renders.
  5. create() is also cold: calling it without .subscribe() sends nothing — a common interview gotcha.

🧠 How this works

  1. NonNullableFormBuilder creates controls typed as string (not string | null) and makes reset() return them to their initial values.
  2. Each control lists synchronous validators; Angular runs them on every value change and sets errors, e.g. { email: true } or { minlength: {...} }.
  3. passwordMatch is attached at group level, so it can read both controls; it returns null when they match and { mismatch: true } on the group otherwise.

🧠 How this works

  1. [formGroup]="form" connects the DOM form to the component's FormGroup; formControlName links each input to a control by key, syncing value both ways.
  2. The email error shows only when the control is touched (blurred once) and has the email error, so users are not shouted at while typing.
  3. form.hasError('mismatch') checks the group, because that is where the cross-field validator puts its error.
  4. (ngSubmit) fires on submit (button click or Enter), and [disabled]="form.invalid" re-evaluates on every change detection pass.

Architecture & Performance

Explain Angular's dependency injection hierarchy.
  • Environment injectors: platform → root (providedIn: 'root', bootstrapApplication providers) → lazy route injectors (providers on a route).
  • Element injectors: providers / viewProviders on components and directives — a new instance per component.
  • Resolution walks up the element tree, then the environment tree. Modifiers: { optional, self, skipSelf, host }.

🧠 How this works

  1. InjectionToken gives a unique DI key for values that have no class, like a URL string or a config object.
  2. { provide: API_URL, useValue: '...' } registers the value; inject(API_URL) looks it up starting at the current element injector, walking up to parents, then the environment/root injector.
  3. If no provider is found, Angular throws NullInjectorError; with { optional: true } it returns null instead, so logger may be null and should be used as this.logger?.log(...).
  4. inject() must be called in an injection context: field initializers, constructors, factory functions, guards or interceptors.
providedIn: 'root' services are singletons and tree-shakable if unused.
Smart vs presentational (dumb) components? How do you manage state?

Smart (container) components inject services, fetch data and own state. Presentational components receive data via inputs, emit outputs and use OnPush — easy to reuse and test.

State options, from simple to complex:

  • Signals in a component or a service ("signal store" pattern).
  • NgRx SignalStore — lightweight, signal-based store with withState, withComputed, withMethods.
  • NgRx Store — Redux pattern (actions, reducers, effects, selectors) for large teams and auditability.

🧠 How this works

  1. _todos is a private writable signal; asReadonly() exposes a read-only view, so components can read todos() but only the store can change it.
  2. update(l => [...l, newTodo]) creates a new array; signals compare with Object.is, so a new reference notifies dependents (pushing into the old array would not).
  3. remaining recomputes only when _todos changes and caches the count — adding 2 todos to an empty list makes it 2.
  4. Any template reading todos() or remaining() is re-rendered automatically, with no subscriptions to manage.
How do you optimise an Angular app's performance?
  • Rendering: OnPush / signals / zoneless; track by a stable id in @for (formerly trackBy); avoid function calls in templates (use computed or pure pipes).
  • Loading: lazy routes, @defer blocks, NgOptimizedImage (ngSrc, priority, lazy images).
  • Bundle: production build (esbuild), budgets in angular.json, remove unused libraries, import RxJS operators properly, analyse with source-map-explorer.
  • Lists: virtual scrolling (cdk-virtual-scroll-viewport), pagination.
  • Server: SSR/SSG with hydration, HTTP caching, CDN.

🧠 How this works

  1. The @defer block's component and its dependencies are split into a separate chunk (when they are standalone and not used eagerly elsewhere in the same file).
  2. Initially only @placeholder renders. prefetch on idle downloads the chunk when the browser is idle; on viewport renders the real content when the placeholder scrolls into view (via IntersectionObserver).
  3. If the chunk is still downloading at trigger time, @loading shows; minimum 300ms keeps the spinner visible at least that long to avoid a flicker.
  4. If loading fails, @error renders. On the server (SSR), the placeholder is rendered and the trigger runs in the browser.
What are SSR, hydration and incremental hydration?

SSR renders HTML on the server (ng add @angular/ssr) for faster first paint and SEO. Hydration (provideClientHydration()) reuses that server DOM on the client instead of re-rendering it, avoiding flicker. Incremental hydration (withIncrementalHydration(), stable in v20) keeps @defer blocks dehydrated until a trigger such as hydrate on viewport or hydrate on interaction.

Code using window/document directly breaks on the server — guard it with afterNextRender() or isPlatformBrowser().

Testing

How do you unit test a component and a service that calls HTTP?

🧠 How this works

  1. provideHttpClient() plus provideHttpClientTesting() replaces the real backend, so no network calls happen; HttpTestingController lets the test answer requests.
  2. subscribe triggers the cold POST; expectOne asserts exactly one request went to that URL and returns it so its method can be checked.
  3. req.flush(...) delivers the fake response synchronously, which runs the expect(e.id).toBe(1) inside the subscribe callback.
  4. http.verify() in afterEach fails the test if any unexpected request is still pending.
  5. In the component test, componentRef.setInput('name', 'Laptop') sets the signal input and detectChanges() renders the template so the h3 contains the text.
Karma is deprecated; new projects use Jest or Vitest for unit tests and Playwright or Cypress for end-to-end tests.

Spring Security fundamentals

What is the difference between authentication and authorization?
  • Authentication — who are you? Verifying identity (password, token, certificate). Result: an Authentication object stored in the SecurityContext.
  • Authorization — what are you allowed to do? Checking the authenticated principal's authorities against a resource (URL rules, @PreAuthorize).

Failures map to different HTTP codes: 401 Unauthorized (not authenticated) vs 403 Forbidden (authenticated but not permitted).

Explain the Spring Security filter chain: DelegatingFilterProxy, FilterChainProxy and SecurityFilterChain.
  1. DelegatingFilterProxy — a plain servlet Filter registered with the container that delegates to a Spring bean (named springSecurityFilterChain), bridging servlet and Spring lifecycles.
  2. FilterChainProxy — that bean. It holds one or more SecurityFilterChains and picks the first whose request matcher matches.
  3. SecurityFilterChain — an ordered list of security filters, e.g. CorsFilter, CsrfFilter, BearerTokenAuthenticationFilter, UsernamePasswordAuthenticationFilter, ExceptionTranslationFilter, AuthorizationFilter.

🧠 How this works

  1. The servlet container only knows plain Filters, so it calls DelegatingFilterProxy, which looks up the Spring bean springSecurityFilterChain and hands the request to it.
  2. That bean is FilterChainProxy. It checks each SecurityFilterChain's matcher in order and runs only the first that matches: /api/** goes to chain #1, and anything else falls through to the catch-all chain #2.
  3. Inside a chain the filters run in a fixed order. CorsFilter answers preflights, CsrfFilter checks tokens, BearerTokenAuthenticationFilter turns a JWT into an Authentication, and AuthorizationFilter makes the access decision.
  4. ExceptionTranslationFilter sits just before AuthorizationFilter and turns its exceptions into responses: an anonymous user gets the entry point (401 or a login redirect), and an authenticated user who lacks permission gets 403.
  5. Only when every filter calls chain.doFilter() does the request reach DispatcherServlet and your @Controller.
Enable logging.level.org.springframework.security=TRACE to see which filters run for each request.
How do you configure security in Spring Boot 3+ now that WebSecurityConfigurerAdapter is gone?

Declare a SecurityFilterChain @Bean using the lambda DSL. antMatchers/mvcMatchers were replaced by requestMatchers, and authorizeRequests by authorizeHttpRequests.

🧠 How this works

  1. @EnableWebSecurity plus the SecurityFilterChain bean replaces the old WebSecurityConfigurerAdapter. http.build() creates the ordered filter list.
  2. AuthorizationFilter checks the rules top to bottom and the first match wins. /public/** and health are open to everyone. A DELETE on /api/** needs ROLE_ADMIN, because hasRole("ADMIN") adds the ROLE_ prefix for you.
  3. Other /api/** calls need USER or ADMIN, and anyRequest().authenticated() is the deny-by-default safety net for everything else.
  4. httpBasic reads an Authorization: Basic header, and formLogin serves /login and processes the form POST. Both send the credentials to the AuthenticationManager.
  5. Not logged in: a browser is redirected (302) to /login, while a non-browser client gets 401 with WWW-Authenticate: Basic. Logged in but with the wrong role: 403.
Rule order matters — the first matching rule wins, so put specific matchers before general ones.
What are UserDetailsService and PasswordEncoder? Why use DelegatingPasswordEncoder?

UserDetailsService.loadUserByUsername() loads a user (username, hashed password, authorities) from your store. DaoAuthenticationProvider uses it together with a PasswordEncoder to verify credentials.

🧠 How this works

  1. On login, DaoAuthenticationProvider calls your lambda loadUserByUsername(username), which here looks the user up by email.
  2. If the user is found, it is turned into a Spring User with the stored hash and roles. .roles() adds the ROLE_ prefix to each one.
  3. If nobody matches, it throws UsernameNotFoundException. Spring reports that as a generic BadCredentialsException, so attackers can't tell "unknown user" from "wrong password".
  4. The provider then calls passwordEncoder.matches(raw, stored). DelegatingPasswordEncoder reads the {id} prefix (for example {bcrypt}) and sends the check to that algorithm, so old and new hash formats can live side by side.
  5. New passwords are always encoded with the default (BCrypt). You can re-hash a user with a stronger algorithm the next time they log in.

DelegatingPasswordEncoder prefixes the hash with an algorithm id, so you can migrate to a stronger algorithm (e.g. Argon2) without invalidating existing hashes. Never store plain or reversibly-encrypted passwords; BCrypt/Argon2/scrypt are slow by design, which defeats brute force.

How does method-level security work? Explain @EnableMethodSecurity and @PreAuthorize.

@EnableMethodSecurity (replaces the old @EnableGlobalMethodSecurity) enables @PreAuthorize/@PostAuthorize/@PreFilter/@PostFilter by default. Checks run in an AOP proxy, using SpEL.

🧠 How this works

  1. @EnableMethodSecurity wraps beans that have these annotations in an AOP proxy. Every call through the proxy is checked before or after the real method runs.
  2. @PreAuthorize runs its SpEL before the method. #userId is the method argument and authentication.name is the logged-in principal, so users can read only their own orders unless they are ADMIN.
  3. @PostAuthorize runs after the method and checks returnObject. That is useful when ownership is known only once the entity has been loaded, but the method still runs, so avoid side effects in it.
  4. hasAuthority('SCOPE_orders.write') checks an OAuth2 scope exactly as written, with no ROLE_ prefix added.
  5. A failed check throws AccessDeniedException, and ExceptionTranslationFilter turns it into 403 (or 401 if the user is anonymous).
Because it is proxy-based, calling a secured method from another method in the same class (self-invocation) bypasses the check.
What is CSRF, how does Spring protect against it, and when is it safe to disable?

Cross-Site Request Forgery tricks a logged-in browser into sending a state-changing request to your site, because the browser attaches cookies automatically. Spring's CsrfFilter requires a secret token (header or form field) on unsafe methods (POST, PUT, DELETE, PATCH).

  • Keep it enabled when authentication relies on cookies (session login, BFF).
  • Safe to disable for stateless APIs that authenticate only with an Authorization: Bearer header, since browsers never attach that automatically.

🧠 How this works

  1. The attack: a malicious site submits a hidden form to your API. The browser attaches your session cookie automatically, so without a CSRF check the request would succeed.
  2. CsrfFilter requires a secret token on POST/PUT/PATCH/DELETE that the attacker's page cannot read, because the same-origin policy blocks it. A missing or wrong token gives 403.
  3. csrf.spa() (Spring Security 7) stores the token in an XSRF-TOKEN cookie that JavaScript can read. Angular copies it into the X-XSRF-TOKEN header, and the filter compares the two.
  4. The 6.x lines do the same by hand: CookieCsrfTokenRepository.withHttpOnlyFalse() creates the readable cookie, and a custom request handler accepts the raw header value.
  5. For pure bearer-token APIs, CSRF can be disabled. Browsers never add an Authorization header on their own, so a forged cross-site request carries no credentials.
How do you configure CORS in Spring Security?

CORS must be handled before authentication, otherwise browser preflight OPTIONS requests get a 401. Enable http.cors() and provide a CorsConfigurationSource.

🧠 How this works

  1. Before a cross-origin call with an Authorization header, the browser sends a preflight OPTIONS request. That request carries no credentials.
  2. http.cors(withDefaults()) adds CorsFilter early in the chain and uses your CorsConfigurationSource bean. A valid preflight is answered right away, before authentication can reject it with 401.
  3. Only https://app.example.com gets Access-Control-Allow-Origin. Other origins get no CORS headers (a preflight from them is rejected with 403), so the browser hides the response from their scripts.
  4. setAllowCredentials(true) lets cookies or auth headers flow. The spec forbids pairing it with the * origin, which is why the origin is listed explicitly.
  5. The config is registered only for /api/**. CORS is a browser rule, not authentication: tools like curl ignore it, so the API still needs its own auth.
How do you make a REST API stateless?

🧠 How this works

  1. SessionCreationPolicy.STATELESS tells Spring Security never to create an HttpSession and never to read the SecurityContext from one. Each request starts out anonymous.
  2. With no session cookie there is nothing for CSRF to abuse, so csrf is disabled.
  3. oauth2ResourceServer().jwt() adds BearerTokenAuthenticationFilter, which re-authenticates every request from its Authorization: Bearer JWT.
  4. No header on a protected URL gives 401 with WWW-Authenticate: Bearer. A bad or expired token gives 401 with error="invalid_token". A valid token without enough scope gives 403.

STATELESS means Spring never creates an HttpSession; every request must carry its own credentials (usually a JWT). Benefits: horizontal scaling without sticky sessions or a session store.

JWT

What is the structure of a JWT?

Three Base64URL-encoded parts separated by dots: header.payload.signature.

🧠 How this works

  1. The header says how the token was signed (RS256). kid tells the verifier which public key in the issuer's JWKS to use.
  2. The payload holds the claims. iss is who issued the token, sub is the user, and aud is the API it is meant for. exp/iat are Unix timestamps for expiry and issue time, and scope becomes SCOPE_* authorities in Spring.
  3. The signature is computed over the exact base64url(header).base64url(payload) bytes with the issuer's private key. Changing even one character of the payload breaks it.
  4. The verifier recomputes the check with the public key, rejects the token if it doesn't match, and then checks exp, iss and aud. Base64URL is only encoding, so anyone can read the claims.
A signed JWT (JWS) is encoded, not encrypted — anyone can read the payload. Never put secrets or sensitive PII in it. Use JWE if confidentiality is needed.
Implement JWT authentication end to end in Spring Boot (login endpoint, JWT filter, role-based access).

This is the "self-issued JWT" approach many projects use (for a separate identity provider, use the OAuth2 resource-server configuration above instead). The flow:

🧠 How this works

  1. Steps 1–2: the login endpoint passes the username and password to AuthenticationManager. DaoAuthenticationProvider loads the user and checks the BCrypt hash. Wrong credentials throw BadCredentialsException.
  2. Step 3: on success the server signs a short-lived JWT. From now on the server keeps no session, and the token itself is the proof.
  3. Step 4: the client stores the token and sends it in the Authorization header on every call.
  4. Step 5: the custom filter verifies the signature and expiry and builds an Authentication from the roles claim for this request only.
  5. Step 6: AuthorizationFilter and @PreAuthorize compare those authorities with the rules. A good token and the right role gives 200. A missing or invalid token leaves the user anonymous (the 401 path). The wrong role gives 403.

🧠 How this works

  1. JwtService builds an HMAC key from a base64 secret, which must be at least 256 bits for HS256. signWith(key) picks the HS algorithm from the key size. parseSignedClaims checks the signature and exp and throws JwtException on tampering, expiry or an unsigned (alg: none) token.
  2. JwtAuthFilter (a OncePerRequestFilter, added before UsernamePasswordAuthenticationFilter) strips the Bearer prefix and parses the token. It turns the roles claim (for example ROLE_ADMIN) into authorities and puts an authenticated token in the SecurityContextHolder for this request.
  3. If the token is invalid, the context is cleared and the request continues as anonymous. AuthorizationFilter then denies any protected URL. With no httpBasic/formLogin configured, Spring's default entry point would answer 403 — that's why the config sets authenticationEntryPoint(new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)), so a missing or invalid token gets a proper 401.
  4. Rules: /auth/login is open, DELETE /api/** needs ADMIN, reports need ADMIN or MANAGER, and everything else just needs a valid token. An authenticated user with the wrong role gets 403.
  5. /auth/login calls authManager.authenticate(), which uses UserDetailsService and BCrypt. On success it returns a fresh token. On failure it throws BadCredentialsException, so map that to 401 in your error handling.
  6. CSRF is off and sessions are STATELESS because the only credential is a header that browsers never send automatically.

Store roles with the ROLE_ prefix so hasRole("ADMIN") matches. Keep access tokens short-lived (5–15 min) with refresh tokens, sign with a strong secret or RS256 keys, always use HTTPS, and never put sensitive data in the payload — it's only Base64-encoded, not encrypted.

What must a resource server validate in a JWT?
  • Signature using the key matching kid from the issuer's JWKS; reject alg: none and unexpected algorithms.
  • iss equals the trusted issuer; aud contains this API.
  • exp / nbf with a small clock-skew allowance (Spring default 60s).
  • Required scopes/roles for the endpoint.

🧠 How this works

  1. JwtDecoders.fromIssuerLocation() reads the issuer's metadata (/.well-known/openid-configuration) to find its jwks_uri. NimbusJwtDecoder then fetches and caches the public keys and picks one by kid.
  2. setJwtValidator replaces the default validators. That is why JwtValidators.createDefaultWithIssuer() is added back: it checks exp/nbf (60s clock skew) and requires iss to match exactly.
  3. The extra JwtClaimValidator requires aud to contain orders-api. Without it, a token the same issuer minted for a different API would be accepted here (token confusion).
  4. DelegatingOAuth2TokenValidator runs all validators, and any one failing rejects the token. BearerTokenAuthenticationFilter then answers 401 with error="invalid_token".
Spring Boot 3.2+ can do the audience check with just spring.security.oauth2.resourceserver.jwt.audiences.
How do refresh tokens work and why are access tokens short-lived?

JWT access tokens are self-contained and usually not checked against a database, so they are hard to revoke — keep them short (5–15 min). A long-lived refresh token is sent only to the authorization server's token endpoint to get a new access token.

🧠 How this works

  1. The client calls the authorization server's /oauth2/token endpoint directly, never the API. The body is form-encoded, as the OAuth2 spec requires.
  2. grant_type=refresh_token tells the server which grant to use. It looks up the refresh token, checks it isn't expired or revoked, and checks it belongs to client_id. A confidential client would also authenticate, for example with HTTP Basic and its secret.
  3. On success it returns a new short-lived access token, and with rotation also a new refresh token while the old one is invalidated.
  4. If the refresh token is invalid or revoked, the response is 400 invalid_grant. The user has to log in again.

Best practice: refresh token rotation — each use issues a new refresh token and invalidates the old one; reuse of an old token signals theft and revokes the whole family.

How can you revoke or invalidate a JWT before it expires?
  • Keep access tokens very short-lived and revoke the refresh token (RFC 7009 revocation endpoint).
  • Maintain a deny-list of jti values (e.g. in Redis, TTL = token's remaining life) checked by a custom validator.
  • Store a per-user "token version" / "valid after" timestamp and reject tokens with older iat.
  • Use opaque tokens + introspection when instant revocation is a hard requirement.
  • Rotate signing keys in an emergency (invalidates every token).

OAuth2 & OpenID Connect

What are the four roles in OAuth2?
  • Resource owner — the user who owns the data.
  • Client — the application requesting access (Angular SPA, mobile app, backend service).
  • Authorization server — authenticates the user and issues tokens (Keycloak, Okta, Entra ID, Spring Authorization Server).
  • Resource server — the API that accepts access tokens (your Spring Boot service).
OAuth2 is an authorization (delegation) framework. OpenID Connect adds an identity layer (ID token, /userinfo) for authentication.

Walk through the Authorization Code flow with PKCE.

PKCE (Proof Key for Code Exchange) binds the authorization code to the client that started the flow, so an intercepted code is useless.

🧠 How this works

  1. Steps 1–2: the client creates a random code_verifier and keeps it secret. It sends only its SHA-256 hash, the code_challenge.
  2. Step 3: the browser is redirected to /authorize. state is a random value the client remembers (CSRF protection), and the challenge is attached to the authorization request.
  3. Steps 4–5: the user logs in and consents at the authorization server, which redirects back to the pre-registered redirect_uri with a one-time code and the same state.
  4. Steps 6–7: the client checks state, then POSTs the code plus the original code_verifier. The server hashes the verifier and compares it with the stored challenge. An attacker who stole only the code has no verifier, so the exchange fails with invalid_grant.
  5. Step 8: the server returns the tokens. With openid scope this includes an ID token, whose nonce the client validates.
  6. Steps 9–10: the API receives the access token as a bearer token and checks it locally with the JWKS public keys. Its signature, iss, aud and exp decide between 200, 401 and 403.
  • state protects against CSRF on the redirect; nonce (OIDC) protects against ID-token replay.
  • Always use S256, never plain.

What is the difference between scopes and roles?

Scopes describe what the client is allowed to do on the user's behalf (orders.read), granted by user consent. Roles describe what the user is allowed to do in the business domain (ADMIN). Effective access = intersection of both.

In Spring, scopes become authorities prefixed SCOPE_ by default: hasAuthority('SCOPE_orders.read'); roles use ROLE_ and hasRole('ADMIN').

OAuth2 with Spring Boot

How do you configure a Spring Boot resource server and map roles from the JWT?

🧠 How this works

  1. Adding spring-boot-starter-oauth2-resource-server with jwt.issuer-uri makes Boot auto-configure a JwtDecoder and a filter chain that requires a bearer token.
  2. From the issuer URI, Boot discovers the jwks_uri (signing keys) and validates that each token's iss matches exactly. For Keycloak that means the realm URL.
  3. audiences (Boot 3.2+) adds an aud check, so tokens issued for other APIs are rejected with 401.
  4. This config affects only incoming requests to your API. It does nothing for logging users in or calling other services.

🧠 How this works

  1. .oauth2ResourceServer(o -> o.jwt(...)) adds BearerTokenAuthenticationFilter. It decodes and validates the JWT, then calls your converter to build a JwtAuthenticationToken.
  2. By default the converter reads scope/scp and adds SCOPE_. Here setAuthoritiesClaimName("roles") + setAuthorityPrefix("ROLE_") turns "roles": ["ADMIN"] into ROLE_ADMIN, so hasRole("ADMIN") matches.
  3. setPrincipalClaimName("preferred_username") makes authentication.getName() return the username instead of the sub UUID.
  4. Result: no token or a bad token on /api/admin/** gives 401. A valid token without ROLE_ADMIN gives 403. Any valid token passes everywhere else.
Keycloak puts realm roles under the nested claim realm_access.roles — write a custom Converter<Jwt, Collection<GrantedAuthority>> for that.
How do you add "Login with Google/Keycloak" using oauth2Login?

🧠 How this works

  1. Each entry under registration is one login option, and its key (google, keycloak) becomes the {registrationId}.
  2. Google is a built-in provider (CommonOAuth2Provider), so only the client id and secret are needed. Keycloak needs a provider entry, and its issuer-uri lets Spring discover the authorize, token, userinfo and JWKS endpoints.
  3. scope: openid turns the flow into OIDC, so the token response contains an ID token that Spring validates (signature, iss, aud, exp, nonce).
  4. redirect-uri is where the IdP sends the user back: /login/oauth2/code/keycloak. It must exactly match the URI registered in the IdP, or login fails with invalid redirect_uri.

🧠 How this works

  1. An unauthenticated browser request is redirected to a login page. With two registrations, Spring's default page links to /oauth2/authorization/google and /oauth2/authorization/keycloak. With only one, it would redirect to that IdP directly.
  2. OAuth2AuthorizationRequestRedirectFilter handles /oauth2/authorization/{id}. It saves state/nonce (and PKCE if used) in the session, then sends a 302 to the IdP.
  3. On return, OAuth2LoginAuthenticationFilter at /login/oauth2/code/{id} checks state, swaps the code for tokens, validates the ID token, and loads the user into an OidcUser.
  4. The authenticated user is stored in the HTTP session (session ID rotated to prevent fixation). Later requests use the session cookie and never go back to the IdP until the session ends.

The spring-boot-starter-oauth2-client handles the redirect, code exchange, state/nonce and PKCE (enabled automatically for public clients, configurable for confidential ones).

How does a service call another service using the client credentials grant?

🧠 How this works

  1. This is the client side: orders-service identifies itself, and no user is involved.
  2. authorization-grant-type: client_credentials means Spring POSTs grant_type=client_credentials with the id and secret straight to Keycloak's token endpoint, which issuer-uri discovers.
  3. scope: inventory.read asks for just the permission needed. The inventory API can enforce it with hasAuthority('SCOPE_inventory.read').
  4. Keep the secret in an environment variable or vault (${ORDERS_SECRET}), never in git.

🧠 How this works

  1. OAuth2ClientHttpRequestInterceptor runs before each outgoing request. The resolver says to use the inventory registration from the YAML.
  2. It asks the OAuth2AuthorizedClientManager for a token. If a cached token is still valid, it is reused. If not, the manager fetches a new one from the token endpoint with the client credentials grant.
  3. The interceptor adds Authorization: Bearer <token>, and the inventory service validates it as a normal resource server.
  4. Your business code just calls inventoryClient.get()... with no token handling, and the token endpoint is hit only about once per token lifetime.

The OAuth2AuthorizedClientManager caches the token until it expires, so you don't hit the token endpoint on every call. In WebFlux use ServerOAuth2AuthorizedClientExchangeFilterFunction with WebClient.

What is Spring Authorization Server and how do you set up a minimal one?

Spring Authorization Server is the official Spring project implementing OAuth 2.1 and OIDC 1.0 (authorization code + PKCE, client credentials, device code, refresh tokens, token introspection/revocation, JWKS, dynamic client registration). Since Spring Boot 3.1 there is a starter spring-boot-starter-oauth2-authorization-server, and in Spring Security 7 it is merged into the Spring Security codebase.

🧠 How this works

  1. issuer becomes the iss claim in every token and the base of the discovery document. Resource servers must be configured with exactly this URL.
  2. angular-spa is registered as a public client (client-authentication-methods: none), because a browser app cannot keep a secret.
  3. It may use only the authorization code and refresh token grants, and only the exact redirect-uris listed. Any other redirect is refused, which stops codes leaking to an attacker's URL.
  4. require-proof-key: true forces PKCE. A /oauth2/authorize request without a code_challenge is rejected, so a stolen code alone can't be exchanged.
  5. scopes limits what the client can request. openid enables ID tokens and the OIDC endpoints.

For production, store clients with JdbcRegisteredClientRepository, persist authorizations, and supply a stable RSA JWKSource instead of a generated key.

What is the Backend-for-Frontend (BFF) pattern and why is it recommended for SPAs?

A server-side component (e.g. Spring Cloud Gateway or a small Spring Boot app) acts as a confidential OAuth2 client for the SPA. It runs the authorization code flow, keeps tokens in the server session, and gives the browser only an HttpOnly; Secure; SameSite session cookie. API calls go through the BFF, which attaches the access token (TokenRelay filter).

🧠 How this works

  1. Angular → BFF: the browser sends only an HttpOnly session cookie, so no token ever reaches JavaScript.
  2. BFF ↔ authorization server: the BFF runs oauth2Login as a confidential client (code + PKCE + client secret) and stores the tokens in its server-side session.
  3. BFF → resource servers: TokenRelay looks up the session's access token, refreshes it if needed, and adds Authorization: Bearer to the proxied call.
  4. Resource servers validate the JWT as usual. Because the browser uses cookie auth with the BFF, the BFF needs CSRF protection.
  • Tokens are never exposed to JavaScript → XSS can't steal them.
  • Client secret can be used (confidential client) and refresh tokens stay server-side.
  • Trade-off: you need CSRF protection (cookie auth) and a stateful/sticky or shared session store.

How do you secure Spring Boot Actuator endpoints?

🧠 How this works

  1. exposure.include limits which actuator endpoints are available over HTTP. Everything else (env, heapdump, loggers) is not mapped at all, so requests for it get 404.
  2. show-details: when-authorized means anonymous callers see only {"status":"UP"}, while authenticated users also see component details such as DB and disk.
  3. management.server.port: 8081 runs actuator on a separate port that you can keep off the public load balancer or ingress.

🧠 How this works

  1. securityMatcher(EndpointRequest.toAnyEndpoint()) limits this chain to actuator URLs, and @Order(1) puts it ahead of your app chain. FilterChainProxy picks it first for /actuator/**.
  2. Health and info are permitAll() so load balancers and Kubernetes probes work without credentials.
  3. Every other exposed endpoint needs ROLE_OPS. With httpBasic, a missing or wrong password gives 401 + WWW-Authenticate: Basic, and the right password without OPS gives 403.
  4. Requests that don't match actuator skip this chain and go to the next one.
Never expose /actuator/env, /heapdump or /loggers publicly — they can leak secrets or allow runtime changes.
You discover passwords are accidentally stored in plain text. What would you do?

Treat it as a security incident, not just a bug: plain-text passwords may already have leaked through backups, logs, replicas or exports, and users reuse passwords on other sites.

  1. Contain: inform your lead/security team immediately; restrict access to the table, backups and any logs or exports containing passwords.
  2. Fix the code: hash new passwords with a slow adaptive algorithm (BCrypt/Argon2) via Spring Security's PasswordEncoder — never encrypt and never use MD5/SHA-256 alone.
  3. Migrate existing data: hash every stored plain-text password in place (you have the plain text, so you can hash it directly), then verify no plain text remains.
  4. Clean up copies: logs, backups, analytics exports, caches — wherever the plain text may live.
  5. Assess exposure: if there's any chance the data was accessed, follow the incident/disclosure process — force password resets, notify users as policy and law require.
  6. Prevent recurrence: code review checklist, a static-analysis rule, and tests that assert stored passwords are hashes.

🧠 How this works

  1. createDelegatingPasswordEncoder() hashes with BCrypt and prefixes the result with {bcrypt}, so the stored value records which algorithm produced it; matches() reads that prefix when users log in.
  2. Because the plain text is still in the table, the migration can hash it directly — no user action needed. Values without a {…} prefix are treated as not yet migrated.
  3. Running it inside @Transactional makes JPA dirty checking write the hashed values on commit. For millions of users, process in batches (paging) instead of findAll().
  4. After this, login keeps working: users type the same password, and matches() compares it against the new BCrypt hash.
Your application suddenly starts returning many 401 Unauthorized errors. What would you investigate?

A 401 means the request is not authenticated (missing, invalid or expired credentials) — unlike 403, where the user is known but not allowed. A sudden spike usually has a single cause that changed for everyone:

CheckTypical cause
Recent deployments / config changesChanged issuer-uri, audience, JWT secret or public-key settings; new security rules
Signing keysThe identity provider rotated its keys and the service can't fetch the new JWKS (network/firewall) or caches the old one
Token expiry & refreshAccess tokens expire and the frontend's refresh flow is broken; token lifetime was shortened
Clock skewServer clocks drifted, so valid tokens look expired or "not yet valid"
Identity providerKeycloak / Okta / Entra ID outage or certificate problem
ClientsOne client stopped sending the Authorization header (proxy stripping it, CORS preflight issue, expired API key or client secret)

🧠 How this works

  1. A JWT's middle part is Base64URL-encoded JSON; the jq filter takes that part, converts -/_ to +//, decodes it (jq 1.7+ accepts the missing = padding) and parses the claims. If exp is below the current epoch seconds, the token really is expired; a wrong iss/aud means a configuration mismatch.
  2. The resource server validates signatures with the keys from the provider's JWKS endpoint. If the token header's kid isn't in that list, or the endpoint is unreachable, every token fails with 401.
  3. Spring Security's DEBUG logs name the exact reason (e.g. "Jwt expired at …", "The iss claim is not valid"), which turns guessing into a one-line diagnosis — switch it back off afterwards.
Look at who gets the 401s: all users → a server-side or IdP cause; one client or app version → that client's token handling.

A01 Broken Access Control — what is IDOR and how do you fix it in Spring?

Users can act outside their permissions: view other users' data by changing an ID (IDOR), call admin endpoints, elevate privileges, or make the server fetch internal URLs (SSRF, now part of A01).

🧠 How this works

  1. The attack: user A calls GET /api/orders/123, sees their own order, then tries 124, 125 and so on. The vulnerable code loads any row by ID, so authentication passes and other users' data leaks.
  2. The fix adds the owner to the query: findByIdAndOwnerId(id, jwt.getSubject()) becomes WHERE id = ? AND owner_id = ?. The owner comes from the validated token, which the user can't forge, not from the request.
  3. Someone else's order simply isn't found, so the code returns 404 and doesn't reveal that the ID exists. A 403 would confirm it.
  4. The @PreAuthorize version calls a bean (@orderSecurity.isOwner) before the method runs. A false result throws AccessDeniedException and gives 403.
  • Enforce authorization on the server for every request — hiding a button in Angular is not access control.
  • Deny by default: .anyRequest().authenticated() or denyAll() as the last rule.
  • Use unguessable IDs (UUIDs) as defence in depth, not as the fix.
  • Configure CORS narrowly; disable directory listing; rate-limit; log access-control failures.
A01 (SSRF) — how do you prevent Server-Side Request Forgery?

The app fetches a URL supplied by the user, and an attacker points it at internal systems — e.g. the cloud metadata endpoint http://169.254.169.254/ to steal credentials.

🧠 How this works

  1. The attack: the server fetches whatever URL it is given, from inside your network. Sending http://169.254.169.254/... (cloud metadata) or http://localhost:8081/actuator/env makes the server read internal data and return it.
  2. The fix requires https and an exact host allow-list, so arbitrary hosts, IP literals and odd schemes like file: are rejected before any connection is made.
  3. It then resolves the hostname and rejects loopback, private (10/172.16/192.168), link-local (169.254) and wildcard addresses, in case an allowed name points at an internal IP.
  4. Remaining gaps: DNS can change between the check and the fetch, and a redirect could bounce to an internal URL. So disable redirects in the HTTP client and add egress firewall rules as a second layer.
Also enforce at the network level (egress firewall), and use IMDSv2 on AWS, which requires a session token the attacker cannot easily obtain.
A02 Security Misconfiguration — what are typical examples in a Spring Boot app?
  • All Actuator endpoints exposed publicly (/actuator/env, /heapdump leak secrets).
  • Stack traces and framework versions in error responses.
  • Default credentials, sample apps, H2 console enabled in production.
  • Missing security headers, permissive CORS (* with credentials), verbose logging of tokens.
  • Unpatched containers, public S3 buckets, open database ports.

🧠 How this works

  1. exposure.include keeps actuator to the minimum. Never use *, because it would publish env (secrets) and heapdump (memory with tokens).
  2. show-details: when-authorized hides internal component info from anonymous callers.
  3. server.error.include-stacktrace: never and include-message: never keep exception details out of Boot's error JSON, so attackers can't learn class names, SQL or library versions.
  4. spring.h2.console.enabled: false makes sure the H2 web console, a database UI, is never reachable in production.

🧠 How this works

  1. The CSP header restricts where scripts and other resources can load from and blocks framing (frame-ancestors 'none'), which limits XSS and clickjacking.
  2. HSTS makes browsers use HTTPS only for one year, including subdomains, preventing protocol downgrade attacks. It is sent only over HTTPS.
  3. Referrer-Policy: strict-origin-when-cross-origin sends only the origin (not the full path and query) to other sites, so IDs or tokens in URLs don't leak through the Referer header.
  4. HeaderWriterFilter adds all of these to every response. Spring already sends sensible defaults like X-Content-Type-Options: nosniff.
A03 Software Supply Chain Failures — what are the risks and how do you defend against them?

Compromise anywhere in the chain of code you don't write: vulnerable or abandoned dependencies (Log4Shell), malicious packages (typosquatting, hijacked npm maintainers), compromised build tools or CI pipelines, and unverified container images.

  • Inventory: generate an SBOM (CycloneDX Maven/Gradle plugin, syft).
  • Scan continuously: OWASP Dependency-Check, Dependabot / Renovate, Snyk, npm audit, Trivy for images.
  • Pin and verify: lock files (package-lock.json), Maven checksums, signed artifacts (Sigstore/cosign), trusted registries only.
  • Harden CI/CD: least-privilege tokens, pinned GitHub Action SHAs, protected branches, required reviews.
  • Remove unused dependencies; prefer well-maintained libraries.

🧠 How this works

  1. The OWASP Dependency-Check Maven plugin lists every direct and transitive dependency and matches each one against public vulnerability databases (CVEs from the NVD).
  2. failBuildOnCVSS 7 fails the build if any dependency has a vulnerability scoring 7.0 or higher (high/critical), so a Log4Shell-type library can't ship silently.
  3. You run it with mvn dependency-check:check, or by binding the check goal in an <executions> block (not shown) so CI runs it on every build. An NVD API key makes updates much faster.

🧠 How this works

  1. A tag like @v4 can be moved. If the action's repository or a maintainer account is compromised, the attacker can point the tag at malicious code, and your pipeline runs it with your secrets.
  2. A full 40-character commit SHA can't be changed, so the code you reviewed is exactly the code that runs.
  3. The trailing comment keeps the human-readable version. Tools like Dependabot can raise PRs that update the SHA when a new release comes out.
A04 Cryptographic Failures — how should passwords, data and secrets be protected?
  • Passwords: a slow adaptive hash (BCrypt, Argon2, PBKDF2) — never MD5/SHA-1/SHA-256 alone, never encryption.
  • Data in transit: TLS 1.2+ everywhere, HSTS; data at rest: AES-GCM with keys in a KMS/Vault, not in code.
  • Use SecureRandom for tokens, never Random/Math.random().
  • Don't build your own crypto or use ECB mode; classify data and don't store what you don't need.

🧠 How this works

  1. MD5 is fast and unsalted. GPUs try billions of guesses per second, identical passwords give identical hashes, and precomputed tables crack common ones instantly.
  2. new Random().nextInt(999999) has two flaws. There are under a million possible values, so it can be brute-forced. And java.util.Random is a predictable generator, so its next outputs can be predicted from past ones.
  3. The fix uses DelegatingPasswordEncoder, which stores {bcrypt}$2a$10$<salt><hash>. Each password gets a random salt, and the work factor makes each guess deliberately slow.
  4. matches(raw, stored) reads the algorithm, salt and cost from the stored string, re-hashes the input and compares, so you never decrypt anything.
  5. SecureRandom with 32 bytes gives 256 bits of unpredictable entropy. URL-safe Base64 makes it safe to put in a reset link.
A05 Injection — SQL, JPQL and command injection. Show the fix.

🧠 How this works

  1. The attack: with name = x' OR '1'='1, string concatenation builds WHERE name = 'x' OR '1'='1'. The quote ends the string literal early, the OR becomes SQL code, and the always-true condition returns every user. JPQL concatenation has the same problem.
  2. The fix uses ? / :name placeholders. The SQL text is compiled first and the value is sent separately as data, so the database treats quotes in it as ordinary characters, never as syntax.
  3. Spring Data @Query with :name and derived queries always bind parameters, so they are safe by default unless you build the query string yourself.
  4. Column names in ORDER BY can't be bound as parameters, so the code allow-lists them. Anything not in SORTABLE is rejected before it reaches SQL.
  5. ProcessBuilder with separate arguments runs the program directly with no shell, so ;, && or | in a filename stay part of the argument and are never run as commands.
Also covers LDAP, NoSQL, expression-language (SpEL) and log injection. Validate input with Bean Validation (@Pattern, @Size), but parameterisation is the real fix.
A05 (XSS) — how do you prevent cross-site scripting in Angular and Spring?
  • Angular escapes interpolation {{ }} and sanitises [innerHTML] by default. The danger is bypassing it: bypassSecurityTrustHtml(userInput), or touching nativeElement.innerHTML directly.
  • Server-side templates (Thymeleaf): use th:text (escaped), not th:utext for user content.
  • Send a strict Content-Security-Policy as a second layer, and cookies with HttpOnly.
  • Return JSON with Content-Type: application/json so browsers never render it as HTML.

🧠 How this works

  1. The attack: a stored comment such as <img src=x onerror=...> is rendered as HTML. Its event handler runs in other users' browsers with their session, so it can steal data or act as them.
  2. bypassSecurityTrustHtml() tells Angular "this HTML is safe", which turns off its built-in sanitizer for that value. That is why it is the vulnerable line.
  3. [innerHTML] without the bypass still renders HTML, but Angular strips <script>, on* handlers and javascript: URLs first.
  4. {{ }} interpolation inserts the value as a text node, so < shows up as a literal character and nothing runs. This is the safest option for user content.
A06 Insecure Design — what is it, and how is it different from an implementation bug?

A flaw in the design itself, which perfect code cannot fix: no rate limit on OTP verification (brute-force 6 digits), a password reset that reveals whether an email exists, "security questions", trusting the client to send the price, or a checkout flow that lets you skip the payment step.

  • Threat-model during design (STRIDE), write abuse cases next to user stories.
  • Limit business flows: attempts per OTP, per-user quotas, idempotency keys for payments.
  • Recompute anything security-relevant on the server (prices, totals, roles).
  • Use secure-by-default libraries and reference architectures; segregate tiers and tenants.

🧠 How this works

  1. The design flaw: if the request carried a price field, an attacker could change it to 0.01 in DevTools or a proxy. Validation can't help, because the value is well-formed but untrustworthy.
  2. The fixed design takes only the SKU and quantity from the client and looks up the price on the server from catalog.priceOf(sku).
  3. The total is computed with BigDecimal (no floating-point rounding errors), and the user ID comes from the authenticated principal, not the body.
  4. Also validate that qty is positive and capped. A negative quantity is another way to manipulate the total.
A07 Authentication Failures — what are they and how do you prevent them?
  • Credential stuffing / brute force → rate limiting, account lockout with backoff, breached-password checks, MFA.
  • Weak session handling → regenerate the session ID on login (Spring does this by default), short idle timeouts, invalidate on logout.
  • JWT mistakes → accepting alg: none, not validating iss/aud/exp, long-lived tokens, secrets in code.
  • User enumeration → identical messages and timing for "unknown user" and "wrong password".

🧠 How this works

  1. fromIssuerLocation() discovers the IdP's JWKS URL, so only tokens signed by the IdP's published keys are accepted. Unsigned tokens (alg: none) or ones signed with an unexpected key fail.
  2. createDefaultWithIssuer() rejects expired or not-yet-valid tokens (exp/nbf) and tokens from any other issuer or realm.
  3. The audience validator rejects tokens issued for a different API, even from the same IdP, so a token leaked from another service can't be replayed here.
  4. Every rejected token makes BearerTokenAuthenticationFilter return 401 before your controller runs.
A08 Software or Data Integrity Failures — what is insecure deserialization and how do you fix it?

Trusting code or data without verifying integrity: deserialising untrusted objects (Java serialization gadget chains → remote code execution), auto-updates without signature checks, unsigned JWTs or cookies, CI pipelines that pull unverified artefacts.

🧠 How this works

  1. The attack: readObject() creates objects of whatever class the byte stream names, as long as it is on the classpath. It also runs their deserialization hooks. Attackers chain such classes from common libraries ("gadget chains") to execute code, and this happens before your cast is even checked.
  2. The fix uses Jackson to bind JSON to one fixed class, OrderRequest. The input can supply only field values, never class names, so no unexpected code runs.
  3. activateDefaultTyping lets JSON include class names, which brings back the same class-choosing problem. Keep it off for untrusted input.
  4. If you must use Java serialization, ObjectInputFilter checks every class before it is created. com.acme.dto.*;java.base/*;!* allows your DTOs and core JDK types and rejects everything else (!*).
Verify signatures of anything you load (JWTs with strong algorithms, signed releases), and use Subresource Integrity (integrity="sha384-...") for CDN scripts.
A09 Security Logging & Alerting Failures — what should you log, and what must you never log?
  • Log: logins (success and failure), access-control denials, input-validation failures, admin actions, token refresh failures — with user ID, IP, timestamp and correlation ID.
  • Never log: passwords, tokens, session IDs, full card numbers, PII beyond what's needed.
  • Alert on patterns (many 401s from one IP, privilege changes), centralise logs (ELK, Loki, Splunk), protect them from tampering, and have an incident-response runbook.
  • Prevent log injection: strip CR/LF from user input, or log in structured JSON.

🧠 How this works

  1. Spring Boot publishes authentication events. Whenever the AuthenticationManager succeeds or fails, an AuthenticationSuccessEvent or AbstractAuthenticationFailureEvent is fired.
  2. The @EventListener methods receive them and write to a dedicated AUDIT logger, which you can send to a SIEM and alert on (for example, many failures from one user).
  3. Only the username and the exception type (for example BadCredentialsException) are logged, never the password, token or full exception message.
  4. The attack sanitize() blocks is log injection. A username containing a newline followed by login_success user=admin would create a fake log line. Replacing CR/LF keeps each event on exactly one line.
A10 Mishandling of Exceptional Conditions — what does "failing open" mean? Give examples and fixes.

New in 2025: the system behaves insecurely when something unexpected happens — exceptions swallowed, errors leaking internals, partial transactions, or a security check that allows access when it fails ("fail open").

🧠 How this works

  1. The vulnerable version returns true on any exception. If an attacker can make the permission service time out or fail (overload, malformed input), every delete is allowed.
  2. The fixed version fails closed: the error is logged with context for alerting, and the answer is "no". An outage then causes denied requests (403 or 503) rather than a security breach.
  3. @Transactional wraps transfer in one database transaction. If credit throws a runtime exception after debit, Spring rolls back both, so money can't vanish halfway.
  4. Note that by default only unchecked exceptions trigger rollback (use rollbackFor for checked ones), and the method must be called through the Spring proxy, not from inside the same class.
  • A global @RestControllerAdvice returning generic ProblemDetail messages (no stack traces).
  • Handle nulls, timeouts, resource exhaustion and unexpected input explicitly; set timeouts on every remote call.
  • Use transactions and idempotency so failures leave consistent state.

API3 — what is mass assignment / excessive data exposure, and how do DTOs fix it?

🧠 How this works

  1. The attack: Jackson copies every JSON property onto the User entity, including fields the UI never shows. Sending "role":"ADMIN" or another user's id lets save() grant privileges or overwrite someone else's row.
  2. Returning the entity also serializes passwordHash and internal flags (excessive data exposure).
  3. The fix uses UpdateProfileRequest, which has only displayName and email. Extra fields have nowhere to go: they are ignored by default, or rejected if you enable fail-on-unknown. @Valid returns 400 on bad input.
  4. The user to update comes from jwt.getSubject(), not from an ID in the body, and only the two allowed fields are copied.
  5. UserView sets exactly what goes out, so new sensitive entity fields can't leak by accident.
Set spring.jackson.deserialization.fail-on-unknown-properties=true to reject unexpected fields instead of silently ignoring them.
API4 — how do you protect an API from unrestricted resource consumption?
  • Rate limiting per user/IP/API key at the gateway (Spring Cloud Gateway RequestRateLimiter with Redis) or in-app (Bucket4j, Resilience4j RateLimiter).
  • Cap page sizes and payload sizes; reject huge uploads early.
  • Timeouts on every outbound call and query; bounded thread pools and queues.
  • Limit expensive operations (exports, password resets, SMS sending) — they cost real money.

🧠 How this works

  1. max-page-size: 100 caps Spring Data Pageable requests, so ?size=1000000 is silently reduced to 100 rows instead of loading the whole table into memory.
  2. multipart.max-file-size / max-request-size reject oversized uploads early with an error (MaxUploadSizeExceededException) before they fill the disk or heap.
  3. server.tomcat.max-swallow-size limits how many bytes of an aborted upload Tomcat will keep reading. Beyond that it closes the connection instead of reading a huge body for nothing.

🧠 How this works

  1. The limiter allows 5 permits per 1-minute window (limitForPeriod + limitRefreshPeriod), and the permits reset at the start of each window.
  2. timeoutDuration(ZERO) means a caller never waits for a permit. acquirePermission() returns false immediately once the 5 are used.
  3. The code then throws ResponseStatusException(TOO_MANY_REQUESTS), which gives HTTP 429, so brute-forcing login is limited to 5 tries per minute.
  4. As written there is one shared limiter for everyone. In practice, keep one limiter per user or IP (for example in a RateLimiterRegistry keyed by the client) so one attacker can't lock out all users.
API5 — broken function-level authorization: how do you secure admin endpoints?

🧠 How this works

  1. Rules are checked top to bottom. GET /api/products/** is public, but the matcher is limited to GET, so DELETE /api/products/1 skips that rule.
  2. /api/admin/** needs ROLE_ADMIN whatever the method, which closes the "guess the admin URL" attack.
  3. DELETE /api/** needs ADMIN, so switching a request from GET to DELETE doesn't get around authorization.
  4. anyRequest().authenticated() is the deny-by-default catch-all. A missing or invalid JWT gives 401, and a valid JWT without the role gives 403.

Attackers guess endpoints (/api/v1/users → /api/v1/admin/users) or switch HTTP methods (GET → DELETE). Check roles per method and path, and back it up with @PreAuthorize on service methods.

API6, API9 and API10 — business-flow abuse, API inventory, and unsafe consumption of third-party APIs.
  • API6 — Sensitive business flows: scalpers buying all concert tickets, bots creating accounts, referral-bonus abuse. Fix: CAPTCHA / device fingerprinting, per-account purchase limits, anomaly detection.
  • API9 — Improper inventory: forgotten /v1 endpoints without the new auth, staging APIs reachable from the internet, undocumented debug endpoints. Fix: OpenAPI docs generated from code (springdoc), an API gateway as the single entry point, deprecation and retirement policy.
  • API10 — Unsafe consumption: trusting data from partner APIs more than user input. Fix: validate responses against a schema, enforce TLS, set timeouts and response-size limits, don't follow redirects blindly, wrap calls in circuit breakers.

🧠 How this works

  1. The partner's JSON is bound to a typed record (PartnerRate) instead of being passed through as-is, so unexpected fields don't spread into your system.
  2. validator.validate() runs the Bean Validation rules on the record (for example @NotNull, @Size), just as it would for user input.
  3. A business check (rate must be > 0) catches values that are well-formed but wrong. An IllegalStateException stops the bad data before it is used in pricing.
  4. Combine this with timeouts, response-size limits and a circuit breaker on partnerClient, so a slow or compromised partner can't take your service down.

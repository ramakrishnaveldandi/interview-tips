Stream fundamentals

What is a Stream? How is it different from a Collection?

A stream is a sequence of elements that supports declarative, pipelined, aggregate operations. It does not store data — it carries values from a source (collection, array, I/O, generator) through a pipeline of operations.

CollectionStream
Stores elements in memoryStores nothing; computes on demand
Eagerly constructedLazy — nothing runs until a terminal operation
External iteration (for loop)Internal iteration (the library loops for you)
Can be traversed many timesCan be consumed once
FiniteCan be infinite (Stream.iterate, generate)
Modifiable (add/remove)Never modifies its source
SequentialSequential or parallel with one call
Explain the structure of a stream pipeline and laziness.

A pipeline = source → zero or more intermediate operations (return a new stream, lazy) → exactly one terminal operation (produces a result or side effect, triggers execution). Elements flow through the pipeline one at a time (vertically), not stage by stage.

🧠 How this works

  1. Stream.of(...) is the source, and filter, map and limit are lazy intermediate ops. Nothing runs until the terminal toList() starts pulling elements.
  2. Each element goes through the whole pipeline before the next one starts. "one" and "two" have length 3, so they fail length() > 3 and never get to map. That is why you see "filter one", "filter two" with no map line after them.
  3. "three" passes the filter, gets mapped to "THREE", and reaches limit(1). The limit is now full, so it short-circuits and the stream stops pulling. "four" is never filtered.
  4. The last line prints nothing. peek is an intermediate op, and with no terminal operation the pipeline never runs.
What are the ways to create a stream?

🧠 How this works

  1. Every line only builds a stream. Nothing is evaluated until a terminal op is called.
  2. Arrays.stream(int[]), IntStream.range and String.chars() give primitive IntStreams, so the numbers are never boxed. range(0, 5) excludes the end (0..4). rangeClosed includes it.
  3. Stream.iterate(seed, f) and Stream.generate are infinite, so you need a short-circuit like limit(5). The 3-arg iterate (Java 9) stops once the condition fails, giving 1, 3, 9, 27, 81.
  4. Files.lines holds an open file handle, so use it in try-with-resources. Stream.ofNullable returns an empty stream for null instead of throwing an NPE.

What is the difference between map and flatMap?

map transforms each element into exactly one element. flatMap transforms each element into a stream and flattens all those streams into one.

🧠 How this works

  1. map(List::stream) turns each inner list into exactly one Stream. You get a list of 3 stream objects, not numbers.
  2. flatMap(List::stream) also makes one stream per inner list, but then joins them into a single stream: 1, 2 → 3 → 4, 5, giving [1, 2, 3, 4, 5].
  3. In the word example each line is split into an array, Arrays.stream turns the array into a stream, and flatMap merges the words of both lines in encounter order.
How does reduce() work? Explain identity, accumulator and combiner.

🧠 How this works

  1. reduce(0, Integer::sum) starts with the identity 0 and then folds: 0+1+2+3+4+5 = 15.
  2. reduce(Integer::max) has no identity, so on an empty stream it has nothing to return. That is why it returns an Optional, here Optional[5].
  3. For the product the identity is 1, because multiplying by 1 changes nothing: 1·1·2·3·4·5 = 120.
  4. The 3-arg form takes Strings in and gives an int out. The accumulator adds each length (4 + 6 + 3 = 13), and the combiner Integer::sum merges partial sums when the stream runs in parallel.
  • Identity must be a neutral value: 0 for sum, 1 for product. A wrong identity (e.g. 10) gives wrong answers in parallel because it is applied once per chunk.
  • The accumulator must be associative — (a - b) is not, so subtraction gives different results in parallel.
  • For building collections, use collect (mutable reduction) instead of reduce.
Why can't a stream be reused?

🧠 How this works

  1. A stream is a one-shot pipeline. The first count() is a terminal op, and it marks the stream as consumed.
  2. The second count() on the same object throws IllegalStateException, because the elements have already been used up.
  3. A Supplier<Stream> builds a new stream every time you call get(), so each terminal op gets its own fresh pipeline.

What are primitive streams and why use them?

IntStream, LongStream and DoubleStream avoid boxing every number into Integer/Long/Double objects, and add numeric terminals: sum(), average(), summaryStatistics(), range().

🧠 How this works

  1. mapToInt(Integer::intValue) unboxes each Integer into an IntStream. sum() only exists on primitive streams: 4 + 8 + 15 = 27.
  2. average() returns OptionalDouble because an empty stream has no average. Here 27 / 3 = 9.0.
  3. summaryStatistics() works out count, sum, min, average and max in one pass, so you see all five values in the output.
  4. boxed() turns the IntStream 1..3 back into a Stream<Integer> so it can be collected into a List.
What are the rules for lambdas in streams (side effects, non-interference)?
  • Non-interference: never modify the source collection during the pipeline → ConcurrentModificationException or wrong results.
  • Stateless & side-effect-free behaviour: don't add to an external list inside map/forEach; use collect.
  • Lambdas can only capture effectively final local variables.
  • peek is for debugging; since Java 9 it may not even run if the result can be computed without it (e.g. count() on a sized source).

🧠 How this works

  1. The bad version filters and then calls forEach(out::add), which writes into an outside ArrayList. ArrayList is not thread-safe, so in a parallel stream elements can be lost or an exception can be thrown.
  2. The good version lets the terminal op toList() build the result. The stream handles accumulation, and the result is correct in parallel too.
How do you handle checked exceptions inside stream lambdas?

Functional interfaces like Function cannot throw checked exceptions. Options: catch inside the lambda and wrap, extract a helper method, or return a result type.

🧠 How this works

  1. Files.readString throws the checked IOException, but Function.apply cannot declare checked exceptions. Writing it directly would not compile.
  2. The lambda catches the exception and wraps it in the unchecked UncheckedIOException. That exception propagates out of toList() and stops the pipeline at the first failing path.

Predicate vs Function vs Consumer vs Supplier — which stream operations use them, and how do you compose them?

All four are functional interfaces in java.util.function (Java 8). Each has exactly one abstract method, so a lambda or method reference can implement it. Stream operations are typed by these interfaces, which is why knowing them tells you what each lambda must return.

InterfaceMethodUsed byComposition
Predicate<T>boolean test(T)filter, anyMatch/allMatch/noneMatch, takeWhile, removeIfand, or, negate, Predicate.not (11)
Function<T,R>R apply(T)map, flatMap, groupingBy, toMap, Comparator.comparingandThen, compose, Function.identity()
Consumer<T>void accept(T)forEach, peek, Optional.ifPresentandThen
Supplier<T>T get()Stream.generate, collect/toCollection, Optional.orElseGet/orElseThrow—

Variants: BiFunction/BiPredicate/BiConsumer take two arguments; UnaryOperator<T> and BinaryOperator<T> are Function/BiFunction whose input and output types are the same (used by reduce, Stream.iterate, replaceAll); primitive versions like IntPredicate and ToIntFunction avoid boxing.

🧠 How this works

  1. nonBlank.and(longerThan3) builds a new Predicate that is true only when both are true (and short-circuits like &&). " " fails nonBlank and "sql" fails the length check, so only java and spring pass. negate() flips the result, keeping exactly the other two.
  2. length.andThen(doubled) runs length first, then doubled on its result: "java" → 4 → 8. length.compose(trim) runs in the opposite order — trim first, then length — so " hi " → "hi" → 2.
  3. print.andThen(printLen) is one Consumer that performs both side effects for each element, in order: [a]1 [bb]2.
  4. A Supplier is a factory: every get() runs ArrayList::new again, so l1 and l2 are two different lists and == is false. This is the same reason collect(Collectors.toCollection(ArrayList::new)) takes a supplier.
  5. BinaryOperator.maxBy turns a Comparator into a two-argument "pick the larger" function, which is exactly what reduce(BinaryOperator.maxBy(...)) expects.
Iterable.forEach() vs a for-each loop — when does the difference matter?

Both visit every element, but they are not interchangeable. The for-each loop is a language construct (it compiles to an Iterator loop); Iterable.forEach(Consumer) (Java 8) is a method that calls a lambda for each element, and the collection controls the iteration.

for-each loopIterable.forEach(lambda)
break / continueYesNo — return only ends the current call (acts like continue)
return from the enclosing methodYesNo
Checked exceptionsCan be thrownMust be caught/wrapped (Consumer.accept declares none)
Modify local variablesYesNo — captured locals must be effectively final
Who iteratesCaller, via IteratorThe collection; e.g. Collections.synchronizedList(...).forEach holds the lock for the whole traversal, while a for-each loop over it needs a manual synchronized (list) block

🧠 How this works

  1. In the loop, break exits as soon as "Meena" is reached, so only Asha Ravi is printed.
  2. Inside forEach, return returns from the lambda, not from the loop. ArrayList.forEach simply moves on to the next element, so Meena is skipped and John is still printed. There is no way to stop early except throwing an exception — if you need early exit, use a loop or a short-circuiting stream (anyMatch, takeWhile, findFirst).
  3. Removing "Ravi" during a for-each loop changes the list's modCount. The next iterator.next() sees the change and throws ConcurrentModificationException (fail-fast).
  4. ArrayList.forEach is also fail-fast: it checks modCount while looping and after the loop, so modifying the list from the lambda throws the same exception. Neither style lets you structurally modify the list you are iterating.
  5. removeIf (Java 8) is the safe, idiomatic way to remove matching elements — it handles the iteration internally. With an explicit Iterator, it.remove() also works.
Rule of thumb: use forEach for a simple full traversal with a side effect (list.forEach(System.out::println)); use a loop when you need break, checked exceptions or local-variable updates. Stream.forEach on a parallel stream does not even guarantee order — use forEachOrdered when order matters.

What are the pitfalls of Collectors.toMap()?
  • Duplicate keys throw IllegalStateException: Duplicate key — pass a merge function.
  • Null values throw NullPointerException (it uses Map.merge).
  • The map type is unspecified (a HashMap today) — pass a supplier like LinkedHashMap::new to keep order.

🧠 How this works

  1. Each word is a key (Function.identity()) and its length is the value.
  2. The second "java" is a duplicate key. Without the merge function (first, second) -> first, toMap would throw IllegalStateException. With it, the first value is kept.
  3. The LinkedHashMap::new supplier keeps the order in which keys were first inserted, so the output is {java=4, sql=3}.
groupingBy vs partitioningBy?
  • groupingBy — any number of groups, keyed by the classifier result. Groups with no elements simply don't appear.
  • partitioningBy — exactly two groups, keyed by true/false. Both keys are always present, even if empty.
  • Both accept a downstream collector (counting(), mapping(...), averagingDouble(...)…) to post-process each group.

Parallel streams

How do parallel streams work internally?
  • Created with collection.parallelStream() or stream.parallel() (the whole pipeline becomes parallel; the last parallel()/sequential() call wins).
  • The source's Spliterator recursively splits the data into chunks.
  • Chunks are processed as fork/join tasks on the shared ForkJoinPool.commonPool() (parallelism = cores − 1, plus the calling thread).
  • Partial results are merged (the combiner in reduce/collect).

🧠 How this works

  1. IntStream.rangeClosed splits cleanly (it is a sized, indexed range). parallel() splits it into chunks that run on ForkJoinPool.commonPool().
  2. Each chunk filters and counts its own multiples of 3, and the partial counts are added together at the end. The result (3,333,333) is the same as sequential.
  3. In the forEach example, elements run on different threads at the same time, including the calling main thread. That is why both the order and the thread names change from run to run.
When should you use a parallel stream, and when not?
Good fit ✅Bad fit ❌

Always measure (JMH) — parallel is frequently slower. Also: each element should be independent, and the operations must be thread-safe.
What are common parallel stream bugs?

🧠 How this works

  1. Bug 1: many threads call ArrayList.add at once. It does an unsynchronised "write slot, then bump size", so updates get lost (size < 10000) or an internal resize races and throws. boxed().toList() lets each thread build its own part and merges them safely.
  2. Bug 2: parallel forEach prints elements in whatever order the threads finish. forEachOrdered keeps encounter order (12345), but some of the parallel speed-up is lost.
  3. Bug 3: the identity 10 is used once per chunk, so with k chunks you get 10·k + 10 instead of 20. Use a neutral identity (0) and add the 10 outside the stream.
How do you run a parallel stream in a custom thread pool instead of the common pool?

A parallel stream started from inside a ForkJoinPool task uses that pool. This is an implementation detail, but widely used to isolate heavy batch work from the shared common pool.

🧠 How this works

  1. pool.submit(...) runs the lambda as a task inside the custom 4-thread ForkJoinPool.
  2. A parallel stream started from inside a ForkJoinPool thread forks its subtasks into that same pool, so the prime check uses those 4 threads instead of the shared common pool.
  3. get() blocks until the count is ready. shutdown() in finally stops the pool's threads even if an exception was thrown.
For I/O fan-out, don't use parallel streams at all — use an executor or virtual threads (see Core Java → Virtual threads), or Java 24's Gatherers.mapConcurrent(n, fn).
Do findAny, unordered() and Collectors.groupingByConcurrent help in parallel?
  • findAny() can return whichever element is found first by any thread — cheaper than findFirst(), which must respect encounter order.
  • unordered() tells the stream order doesn't matter, so distinct()/limit() become much cheaper in parallel.
  • groupingByConcurrent / toConcurrentMap build one ConcurrentMap shared by all threads instead of merging per-chunk maps.

🧠 How this works

  1. words.parallelStream() splits the list across threads.
  2. groupingByConcurrent has all threads write into one shared ConcurrentMap keyed by word length, instead of building a map per chunk and merging them. counting() adds up each group as a Long.
  3. The result is unordered, which is fine here. Use it when the order of elements inside a group doesn't matter.

Coding: duplicates, frequency & counting

Find duplicate elements in a list (3 ways).

🧠 How this works

  1. Way 1: Set.add returns false for a value it has already seen, so !seen.add(n) keeps only the 2nd and later occurrences of 3, 5 and 8. The result is a HashSet, which happens to print small Integers in ascending order. O(n), but the stateful lambda is not safe in parallel.
  2. Way 2: groupingBy(identity, counting()) builds {1=1, 2=1, 3=2, 5=2, 7=1, 8=2, 9=1}. Then a second stream over the entries keeps counts > 1 and maps each entry to its key. O(n) and side-effect free.
  3. Way 3: Collections.frequency scans the whole list for each element, so it is O(n²). Collecting with toSet() removes the repeated 3, 5 and 8.
Remove duplicates while keeping the original order.

🧠 How this works

  1. distinct() uses equals/hashCode and keeps the first occurrence of each value in encounter order: 5, 3, 8, 1, 9, 7, 2. The second 3, 5 and 8 are dropped.
  2. distinct().sorted() removes duplicates first and then sorts the 7 unique values in natural order.
  3. For "unique by property", toMap uses salary as the key. The merge function (a, b) -> a keeps the first employee on a clash, so Kiran (95000, same as Ravi) is dropped. LinkedHashMap keeps the original order, and values() returns the 6 remaining employees.
Count the occurrences of each word (group by + count), most frequent first.

🧠 How this works

  1. groupingBy(Function.identity(), counting()) uses each word as its own key and counts it: java=3, spring=2, angular=1, sql=1. counting() returns a Long. The default map is a HashMap, which is why the first print looks unordered.
  2. The entry stream is sorted by value descending, then by key ascending to break ties. That puts angular before sql, since both have count 1. Collecting into a LinkedHashMap keeps this sorted order. A plain toMap would lose it.
  3. For the sentence, toLowerCase() makes "Java" and "java" the same word, and split("\\W+") splits on runs of non-word characters. TreeMap::new as the map factory puts the keys in alphabetical order: and, fun, is, java, powerful.
Count each character in a string; find the first non-repeated and first repeated character.

🧠 How this works

  1. chars() gives an IntStream of code points, and mapToObj(c -> (char) c) boxes each one into a Character so it can be a map key.
  2. LinkedHashMap::new keeps keys in the order they first appear in "programming": p, r, o, g, a, m, i, n. r, g and m appear twice.
  3. Both "first" queries stream the ordered entries and use findFirst(), which short-circuits. The first count of 1 is p and the first count above 1 is r. This is O(n) overall.
  4. For "Hello World", it lowercases first, then filter(Character::isLetter) drops the space before boxing. TreeMap sorts the keys: l=3, o=2.
LinkedHashMap is the key detail: with a plain HashMap "first" would be meaningless because order is lost.
Find the most frequent element.

🧠 How this works

  1. The first stream builds the frequency map {java=3, spring=2, angular=1, sql=1}.
  2. A second stream over its entries uses max(Map.Entry.comparingByValue()) to find the entry with the largest count, java=3.
  3. max returns an Optional. map(Map.Entry::getKey) extracts "java", and orElseThrow() unwraps it. If counts tie, which key wins depends on HashMap order. O(n) overall.
Count elements matching a condition; check if any / all / none match.

🧠 How this works

  1. filter(n -> n > 4).count() keeps 5, 8, 9, 5, 7, 8, so the count is 6. count() returns a long.
  2. anyMatch short-circuits at the first match. Asha (120000) is the first element and is above 110000, so it returns true right away.
  3. allMatch has to check everyone unless it finds a failure. All ages are 23 or more, so the result is true.
  4. noneMatch is true because no employee is in "Sales". It had to look at all 7 elements to be sure.

Coding: grouping & partitioning

Group employees by department (names only), and count employees per department.

🧠 How this works

  1. groupingBy(Employee::dept, TreeMap::new, ...) uses the department as the key. TreeMap sorts the keys alphabetically: Finance, HR, IT.

Average, total, and max salary per department; highest-paid employee per department.

Which department has the highest average salary?

Multi-level grouping: by department, then by gender.

  2. Its downstream is another groupingBy on gender, also a TreeMap, so F comes before M inside each department.

Group employees into age bands (custom classifier) and filter within groups.

🧠 How this works

  1. The classifier lambda maps each age to a label: Ravi 28, Kiran 25 and Arjun 23 go to "20s". Asha 32 and John 35 go to "30s". Meena 41 and Priya 45 go to "40+".
  2. TreeMap sorts the labels as strings, so "20s" < "30s" < "40+", which matches the output order.
  3. Collectors.filtering filters inside each group after the group has been created. HR has no one above 90000, so it still shows up as HR=[]. A filter() before groupingBy would have dropped the HR key completely.

Partition numbers into even and odd; partition employees by salary.

🧠 How this works

  1. partitioningBy always creates exactly two keys, false and true, and prints false first. Odd numbers keep their original order [5, 3, 3, 1, 9, 5, 7], and the evens are [8, 8, 2].
  2. With the counting() downstream, each side becomes a Long. Asha, Ravi, Kiran and Priya earn more than 90000 (true=4). Meena, John and Arjun don't (false=3).
Group strings by length, and group anagrams together.

🧠 How this works

  1. distinct() first reduces words to java, spring, angular, sql. Then groupingBy(String::length, TreeMap::new, ...) uses the length as key, sorted numerically: 3, 4, 6, 7.
  2. For anagrams, the classifier sorts each word's characters (chars().sorted()) and rebuilds them into a String with the 3-arg collect on a StringBuilder. listen, silent and enlist all become "eilnst", so they share a key.

Coding: sorting & reversing

Sort numbers and strings ascending and descending.

🧠 How this works

  1. sorted() uses natural order, and Comparator.reverseOrder() flips it. Duplicates are kept, so 3, 3 and 8, 8 both stay. Sorting is O(n log n) and has to read every element before it outputs anything.
  2. String natural order compares Unicode values, and uppercase (A=65, S=83) comes before lowercase (j=106, s=115). That gives [Angular, Spring, java, sql].
  3. CASE_INSENSITIVE_ORDER ignores case, so the result is alphabetical: angular, java, spring, sql.
  4. comparingInt(String::length) sorts by length first (3, 4, 6, 7), and thenComparing would only break ties. There are no ties here, so you get [sql, java, Spring, Angular].
Natural order of String is by Unicode value, so uppercase letters come before lowercase.
Sort employees by salary (desc), then by name; and by multiple fields.

🧠 How this works

Reverse a list using streams.

🧠 How this works

  1. Way 1 streams the indexes 0..4 and maps each index i to list.get(size - 1 - i), so it reads 5, 4, 3, 2, 1. That is O(n) on a random-access list.
  2. Way 2 collects into a mutable ArrayList (needed, because toList() is unmodifiable). collectingAndThen then calls Collections.reverse on it in place.
  3. Way 3 (Java 21) is reversed(), which returns a reversed view of the list in O(1) without copying.
"Sort in reverse" and "reverse" are different: sorted(Comparator.reverseOrder()) sorts descending; reversing keeps the original order backwards.
Reverse a string, reverse each word, and reverse the order of words.

🧠 How this works

  1. chars() plus mapToObj turns each character into a one-letter String. reduce("", (acc, ch) -> ch + acc) puts each new character in front, so the string comes out reversed. Every step builds a new String, so it is O(n²).
  2. To reverse each word, split on spaces, reverse every word with StringBuilder.reverse(), and glue them back with joining(" "). The word order stays the same: avaJ smaertS kcoR.
  3. To reverse the word order, stream the indexes backwards over the parts list (the same trick as reversing a list) and join them: Rock Streams Java.
In an interview, mention that the reduce string version is O(n²) (new string each step) — new StringBuilder(text).reverse() is the practical answer.

Generate Fibonacci numbers and prime numbers with streams.

🧠 How this works

  1. For Fibonacci, each stream element is a pair [current, next]. iterate moves the pair forward to [next, current + next]. The stream is infinite, so limit(10) stops it, and map(f -> f[0]) keeps the first number of each pair.
  2. For primes, each n from 2 to 30 is kept only if no d from 2 to √n divides it (noneMatch short-circuits on the first divisor). For 2 and 3 the inner range is empty, and noneMatch on an empty stream is true, so they count as prime.
  3. For the factorial, LongStream avoids int overflow, and identity 1 times 1·2·…·10 = 3628800.

Coding: parallel streams

Sum 1 to 10 million with a parallel stream, and show that it gives the same result as sequential.

🧠 How this works

  1. LongStream.rangeClosed is a sized source that splits cleanly, so the parallel version divides it into chunks and sums each chunk on a different thread.
  2. Addition is associative, so the partial sums add up to the same total in any grouping: n(n+1)/2 = 10,000,000 · 10,000,001 / 2 = 50,000,005,000,000. That is why seq == par.
  3. reduce(0, Long::sum) is also correct in parallel, because 0 is a true identity (each chunk starts at 0) and Long::sum is associative.
Demonstrate a race condition in a parallel stream and fix it.

🧠 How this works

  1. counter[0]++ is a read-modify-write, not an atomic step. Two threads can read the same value and both write value+1, so increments are lost. That is why the count is usually less than 100000. The line prints true because it only checks <= 100_000.
  2. AtomicInteger.incrementAndGet() uses an atomic compare-and-set, so no update is lost and the result is exactly 100000. All threads still compete for one variable, though, which slows it down.
  3. The best fix is to have no shared state. count() lets each chunk count by itself and adds the results together, and you always get 100000.
Group and count in parallel safely.

🧠 How this works

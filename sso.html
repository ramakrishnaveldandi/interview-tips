SSO concepts

What is Single Sign-On and what are its benefits?

SSO lets a user authenticate once with a central Identity Provider (IdP) and then access many applications without logging in again. Each app trusts the IdP's signed assertion/token instead of managing passwords itself.

  • Users: one set of credentials, fewer password resets.
  • Security: MFA, password policy and lockout enforced in one place; apps never see passwords.
  • Operations: central onboarding/offboarding — disable one account and access is revoked everywhere.
  • Compliance: centralized audit logs of who logged in where.
Trade-off: the IdP becomes a single point of failure and a high-value target — it needs high availability and strong protection.
SSO vs OAuth2 vs OpenID Connect vs SAML — what's the difference?

SSO is the user experience/goal; OIDC and SAML are protocols that implement it. OAuth2 alone is for authorization, not login.

What are Identity Provider, Service Provider and Relying Party?
  • Identity Provider (IdP) — authenticates users and issues assertions/tokens (Keycloak, Okta, Microsoft Entra ID, Ping, ADFS, Google).
  • Service Provider (SP) — SAML term for the application that relies on the IdP.
  • Relying Party (RP) — the OIDC term for the same thing (the OAuth2 "client").

Trust is established up front: in SAML by exchanging metadata XML (entity IDs, certificates, endpoints); in OIDC by registering a client (client_id, secret, redirect URIs) and using the IdP's discovery document.

Explain Keycloak concepts: realms, clients, roles, groups and identity brokering.
  • Realm — an isolated tenant with its own users, clients, roles and settings. The issuer is https://host/realms/{realm}.
  • Client — an app registered in a realm (confidential with secret, or public with PKCE).
  • Realm roles (global, in realm_access.roles) vs client roles (app-specific, in resource_access.{client}.roles).
  • Groups — assign roles to many users at once; often synced from LDAP/AD.
  • Client scopes & mappers — control which claims go into tokens.
  • Identity brokering — delegate login to Google, GitHub, another SAML/OIDC IdP; User federation — read users from LDAP/AD.

OpenID Connect

Describe the OIDC login flow and the discovery document.

OIDC uses the OAuth2 Authorization Code flow (with PKCE) plus the openid scope. The token response then includes an ID token.

🧠 How this works

  1. Steps 1–2: the app finds no local session and redirects to the IdP. scope=openid makes it OIDC. state (CSRF protection), nonce (replay protection) and the PKCE code_challenge are remembered for later checks.
  2. Steps 3–4: the user logs in at the IdP, which sets its own session cookie on the IdP domain and redirects back with a one-time code.
  3. Step 5: the app exchanges the code, plus its code_verifier and secret, at the token endpoint, server to server, and receives the ID, access and refresh tokens.
  4. Step 6: the app validates the ID token's signature (JWKS), iss, aud (its own client_id), exp and nonce, then creates its own session.
  5. Step 7 is the SSO part: a second app redirects to the same IdP, the IdP session cookie is already there, so a code is issued immediately with no password prompt.

The discovery document at {issuer}/.well-known/openid-configuration lists all endpoints, so clients configure themselves from just the issuer URL:

🧠 How this works

  1. Spring reads this document from {issuer}/.well-known/openid-configuration, so you configure only the issuer URL.
  2. authorization_endpoint is where the browser is redirected. token_endpoint is where the backend exchanges the code. userinfo_endpoint returns profile claims.
  3. jwks_uri serves the public keys used to verify token signatures. Keys are chosen by kid, which makes key rotation easy.
  4. end_session_endpoint is used for RP-initiated logout. issuer must match the iss claim in every token exactly.
  5. code_challenge_methods_supported includes plain, but clients should always use S256.

How do you configure Spring Boot OIDC login with Keycloak?

🧠 How this works

  1. registration.keycloak defines the client and its id becomes {registrationId} = keycloak. The client id and secret must match the confidential client in the Keycloak realm.
  2. authorization-grant-type: authorization_code with scope: openid ... selects OIDC login. Spring will require and validate an ID token.
  3. redirect-uri resolves to https://app/login/oauth2/code/keycloak, the callback URL that OAuth2LoginAuthenticationFilter listens on. It must match the Keycloak setting exactly.
  4. issuer-uri lets Spring discover all endpoints and keys. user-name-attribute: preferred_username makes principal.getName() return the username instead of the sub UUID.

🧠 How this works

  1. / and /public/** are open. Any other URL from an anonymous browser gets a 302 to /oauth2/authorization/keycloak, and from there to Keycloak. Spring goes straight to the IdP because only one registration is configured.
  2. After login, Keycloak redirects to /login/oauth2/code/keycloak. Spring checks state, exchanges the code, validates the ID token, and stores the authenticated OidcUser in the HTTP session.
  3. @AuthenticationPrincipal OidcUser injects that user. getFullName() / getEmail() read the standard name / email claims.
  4. getAuthorities() holds OIDC_USER and SCOPE_* by default. IdP roles appear only if you map them (see the role-mapping question).

In Keycloak create a confidential client with Standard flow enabled and valid redirect URI https://app.example.com/login/oauth2/code/keycloak.

How would you configure Okta or Microsoft Entra ID (Azure AD)?

Same Spring config — only the issuer and credentials change. Vendor starters exist but plain Spring Security is enough.

🧠 How this works

  1. Two registrations, okta and entra, live side by side. Spring's default login page offers both, and each gets its own callback /login/oauth2/code/{id}.
  2. Each provider.issuer-uri points Spring at that IdP's discovery document. Okta's /oauth2/default is its default authorization server, and Entra's /{tenant}/v2.0 issuer pins login to one tenant.
  3. groups in the Okta scope asks for group membership, which appears as a claim if a groups claim is configured in Okta.
  4. user-name-attribute: preferred_username makes the Entra principal name the user's UPN or email instead of an opaque ID. Secrets come from environment variables.
Entra ID sends app roles in the roles claim and group object IDs in groups (if enabled in "Token configuration"). Multi-tenant apps use /common or /organizations and must validate the tid claim themselves.
How do you map IdP roles/groups to Spring Security authorities?

By default, oauth2Login grants OIDC_USER plus SCOPE_* authorities. To use IdP roles with hasRole(), register a GrantedAuthoritiesMapper or a custom OidcUserService.

🧠 How this works

  1. After OIDC login, Spring builds the default authorities (OIDC_USER, SCOPE_*) and then passes them through your GrantedAuthoritiesMapper bean, which oauth2Login picks up automatically.
  2. The mapper keeps the originals and looks for the OidcUserAuthority, which carries the validated ID token.
  3. It reads Keycloak's nested realm_access claim (a map) and its roles list, and adds ROLE_<role> for each, so hasRole("admin") works. Role names are case-sensitive.
  4. The mapped set is stored in the session's Authentication. A user missing the role then gets 403 from URL rules or @PreAuthorize.

Alternative: wrap OidcUserService, call super.loadUser(), look the user up in your own database for app-specific permissions, then return a DefaultOidcUser with merged authorities.

In Keycloak, realm roles appear in the ID token only if the "roles" client scope mapper is configured to add them — check with a token decoder.

SAML 2.0

What is a SAML assertion? Explain SP-initiated vs IdP-initiated SSO.

A SAML assertion is a signed (optionally encrypted) XML document from the IdP containing: Issuer, Subject/NameID, Conditions (NotBefore, NotOnOrAfter, AudienceRestriction), AuthnStatement and AttributeStatement (email, groups…).

  • SP-initiated — user visits the app first; SP sends an AuthnRequest to the IdP; IdP POSTs a Response back to the SP's Assertion Consumer Service (ACS) URL. Includes InResponseTo, so it is more secure. Preferred.
  • IdP-initiated — user starts at the IdP portal (e.g. Okta dashboard) and clicks the app tile; an unsolicited Response is POSTed to the SP. Convenient, but more exposed to replay/login-CSRF.

🧠 How this works

  1. Issuer says which IdP made the assertion. The SP accepts it only if it matches the asserting party in its configuration.
  2. ds:Signature is checked against the IdP certificate from the metadata. Any change to the XML (for example adding a group) breaks the signature, and the login is rejected.
  3. Conditions limit when and where the assertion is valid. It must be used between NotBefore and NotOnOrAfter (a short window, to resist replay), and Audience must equal this SP's entity ID, so an assertion meant for another app is refused.
  4. NameID becomes the principal name (the user's email here). AttributeStatement values such as groups=HR-Admins can be mapped to authorities.
How do you configure SAML SSO in Spring Boot?

Add spring-security-saml2-service-provider (it uses OpenSAML; check the Spring docs for the required OpenSAML version and repository). Configure a relying-party registration pointing at the IdP metadata.

🧠 How this works

  1. registration.corp-idp creates one relying-party registration, and corp-idp becomes the {registrationId} in every SAML URL.
  2. entity-id is the SP's unique name. The IdP puts it in the assertion's Audience, and Spring checks that it matches.
  3. signing.credentials is the SP's own private key and certificate, used to sign AuthnRequest and logout messages. The IdP verifies them with the certificate in your SP metadata.
  4. assertingparty.metadata-uri downloads the IdP's metadata: its entity ID, SSO/SLO endpoints and the verification certificates used to check assertion signatures.

🧠 How this works

  1. saml2Login: an anonymous request is redirected to /saml2/authenticate/corp-idp. That builds an AuthnRequest and sends the browser to the IdP (redirect or POST binding).
  2. The IdP POSTs a signed SAMLResponse to the ACS URL /login/saml2/sso/corp-idp. Spring's OpenSAML-based provider checks the signature, issuer, audience, time window and InResponseTo, then creates a Saml2Authentication session.
  3. saml2Logout handles /logout by sending a signed LogoutRequest to the IdP, and also processes logout requests the IdP sends. This is why signing credentials are required.
  4. saml2Metadata publishes an SP metadata XML (entity ID, ACS URL, signing certificate) that the IdP admin imports to set up trust.

The ACS URL is {baseUrl}/login/saml2/sso/{registrationId}. The principal is a Saml2AuthenticatedPrincipal; read attributes with getFirstAttribute("email").

Logout & sessions

How does Single Logout (SLO) work? RP-initiated vs back-channel logout?

Logging out of the app only clears the local session — the IdP session still exists, so the next login is silent. Real logout must also end the IdP session and notify other apps.

  • RP-initiated logout — app redirects the browser to the IdP's end_session_endpoint with id_token_hint and post_logout_redirect_uri.
  • Front-channel logout — IdP loads each app's logout URL in hidden iframes (fragile: third-party cookie blocking).
  • Back-channel logout — IdP POSTs a signed logout token (with sid/sub) server-to-server to every app. Most reliable.

🧠 How this works

  1. When a user POSTs to /logout, LogoutFilter invalidates the local session and clears the SecurityContext. Only the app is logged out at this point.
  2. OidcClientInitiatedLogoutSuccessHandler then sends a 302 to the IdP's end_session_endpoint (from discovery) with id_token_hint and post_logout_redirect_uri=https://app/goodbye. The IdP ends its SSO session and redirects back.
  3. Make sure /goodbye is permitAll(). Here anyRequest().authenticated() would send the logged-out user straight back into a login.
  4. oidcLogout().backChannel() exposes /logout/connect/back-channel/{registrationId}. When the user logs out elsewhere, the IdP POSTs a signed logout token there, and Spring validates it and ends the matching local sessions by sid/sub.

Back-channel endpoint: /logout/connect/back-channel/{registrationId} — register it in the IdP client settings.

How are sessions managed across multiple SSO applications?

There are two layers of session:

  1. IdP session — a cookie on the IdP domain; makes subsequent logins silent. Has its own idle/max lifetimes.
  2. Application session — each app's own session (e.g. JSESSIONID) created after token validation.
  • Use Spring Session with Redis/JDBC so a horizontally scaled app shares sessions.
  • Keep app session timeout ≤ IdP session timeout; use refresh tokens or re-authentication with prompt=none to extend.
  • Limit concurrent sessions via sessionManagement(s -> s.maximumSessions(1)) if required.
  • Protect against session fixation — Spring changes the session id on login by default.

SPA, MFA & troubleshooting

How do you implement SSO for an Angular SPA with a Spring Boot API?

Option A — public client in the browser (e.g. angular-auth-oidc-client): Angular runs Authorization Code + PKCE, holds the access token and sends it as a bearer header; Spring Boot is a resource server.

🧠 How this works

  1. authority is the IdP issuer. The library reads its discovery document, generates PKCE values, and redirects to the authorize endpoint with responseType: 'code'.
  2. After login, the IdP returns to redirectUrl. The library exchanges the code plus verifier for tokens (a public client, so no secret) and validates the ID token.
  3. offline_access + useRefreshToken + silentRenew renew the access token with the refresh token before it expires, so the user isn't sent back to the login page.
  4. The authInterceptor attaches Authorization: Bearer only to URLs in secureRoutes, so tokens never leak to third-party hosts. Spring Boot validates them as a resource server (401 or 403).

Option B — BFF (recommended): Spring Cloud Gateway is a confidential OAuth2 client with oauth2Login; the SPA only has a session cookie and the gateway forwards the token downstream with TokenRelay.

🧠 How this works

  1. The gateway is also configured with oauth2Login (not shown), so the browser logs in through it and holds only a session cookie.
  2. TokenRelay= on every route takes the logged-in user's access token from the gateway's authorized-client store, refreshing it if needed, and adds it as Authorization: Bearer to the downstream request.
  3. SaveSession forces the WebSession to be saved before forwarding, so token and session updates are persisted. This matters with Spring Session or Redis.
  4. The orders route forwards /api/orders/** to orders-service, which validates the relayed JWT as a normal resource server.
How do MFA and social login fit into SSO?
  • MFA is configured in the IdP (TOTP, WebAuthn/passkeys, push). Apps don't implement it; they can require it by requesting acr_values and checking the acr/amr claims (step-up authentication for sensitive actions).
  • Social login (Google, GitHub, Microsoft) is done either directly in Spring via multiple oauth2Login registrations, or — better for SSO — via identity brokering in Keycloak/Okta/Auth0, so apps still trust only one IdP.
  • Link accounts by verified email or explicit linking; never trust an unverified email claim (email_verified).

What are SSO security best practices?
  • Use OIDC Authorization Code + PKCE; never implicit flow. Prefer the BFF pattern for SPAs.
  • Validate state, nonce, signature, iss, aud and exp — let the framework do it.
  • Register exact redirect URIs; no wildcards.
  • Enforce MFA / phishing-resistant passkeys at the IdP; short IdP session lifetimes for privileged users.
  • Implement back-channel logout and deprovision users promptly (SCIM for user sync).
  • Store client secrets in a vault; prefer private_key_jwt client authentication over shared secrets.
  • HTTPS everywhere; HttpOnly, Secure, SameSite cookies.
  • For SAML: require signed assertions, validate audience and time window, prefer SP-initiated flow.

SSO concepts

What is Single Sign-On and what are its benefits?

SSO lets a user authenticate once with a central Identity Provider (IdP) and then access many applications without logging in again. Each app trusts the IdP's signed assertion/token instead of managing passwords itself.

  • Users: one set of credentials, fewer password resets.
  • Security: MFA, password policy and lockout enforced in one place; apps never see passwords.
  • Operations: central onboarding/offboarding — disable one account and access is revoked everywhere.
  • Compliance: centralized audit logs of who logged in where.
Trade-off: the IdP becomes a single point of failure and a high-value target — it needs high availability and strong protection.
SSO vs OAuth2 vs OpenID Connect vs SAML — what's the difference?

SSO is the user experience/goal; OIDC and SAML are protocols that implement it. OAuth2 alone is for authorization, not login.

What are Identity Provider, Service Provider and Relying Party?
  • Identity Provider (IdP) — authenticates users and issues assertions/tokens (Keycloak, Okta, Microsoft Entra ID, Ping, ADFS, Google).
  • Service Provider (SP) — SAML term for the application that relies on the IdP.
  • Relying Party (RP) — the OIDC term for the same thing (the OAuth2 "client").

Trust is established up front: in SAML by exchanging metadata XML (entity IDs, certificates, endpoints); in OIDC by registering a client (client_id, secret, redirect URIs) and using the IdP's discovery document.

Explain Keycloak concepts: realms, clients, roles, groups and identity brokering.
  • Realm — an isolated tenant with its own users, clients, roles and settings. The issuer is https://host/realms/{realm}.
  • Client — an app registered in a realm (confidential with secret, or public with PKCE).
  • Realm roles (global, in realm_access.roles) vs client roles (app-specific, in resource_access.{client}.roles).
  • Groups — assign roles to many users at once; often synced from LDAP/AD.
  • Client scopes & mappers — control which claims go into tokens.
  • Identity brokering — delegate login to Google, GitHub, another SAML/OIDC IdP; User federation — read users from LDAP/AD.

OpenID Connect

Describe the OIDC login flow and the discovery document.

OIDC uses the OAuth2 Authorization Code flow (with PKCE) plus the openid scope. The token response then includes an ID token.

How do you configure Spring Boot OIDC login with Keycloak?

In Keycloak create a confidential client with Standard flow enabled and valid redirect URI https://app.example.com/login/oauth2/code/keycloak.

How would you configure Okta or Microsoft Entra ID (Azure AD)?

Same Spring config — only the issuer and credentials change. Vendor starters exist but plain Spring Security is enough.

Entra ID sends app roles in the roles claim and group object IDs in groups (if enabled in "Token configuration"). Multi-tenant apps use /common or /organizations and must validate the tid claim themselves.
How do you map IdP roles/groups to Spring Security authorities?

By default, oauth2Login grants OIDC_USER plus SCOPE_* authorities. To use IdP roles with hasRole(), register a GrantedAuthoritiesMapper or a custom OidcUserService.

Alternative: wrap OidcUserService, call super.loadUser(), look the user up in your own database for app-specific permissions, then return a DefaultOidcUser with merged authorities.

In Keycloak, realm roles appear in the ID token only if the "roles" client scope mapper is configured to add them — check with a token decoder.

SAML 2.0

What is a SAML assertion? Explain SP-initiated vs IdP-initiated SSO.

A SAML assertion is a signed (optionally encrypted) XML document from the IdP containing: Issuer, Subject/NameID, Conditions (NotBefore, NotOnOrAfter, AudienceRestriction), AuthnStatement and AttributeStatement (email, groups…).

  • SP-initiated — user visits the app first; SP sends an AuthnRequest to the IdP; IdP POSTs a Response back to the SP's Assertion Consumer Service (ACS) URL. Includes InResponseTo, so it is more secure. Preferred.
  • IdP-initiated — user starts at the IdP portal (e.g. Okta dashboard) and clicks the app tile; an unsolicited Response is POSTed to the SP. Convenient, but more exposed to replay/login-CSRF.
How do you configure SAML SSO in Spring Boot?

Add spring-security-saml2-service-provider (it uses OpenSAML; check the Spring docs for the required OpenSAML version and repository). Configure a relying-party registration pointing at the IdP metadata.

The ACS URL is {baseUrl}/login/saml2/sso/{registrationId}. The principal is a Saml2AuthenticatedPrincipal; read attributes with getFirstAttribute("email").

Logout & sessions

How does Single Logout (SLO) work? RP-initiated vs back-channel logout?

Logging out of the app only clears the local session — the IdP session still exists, so the next login is silent. Real logout must also end the IdP session and notify other apps.

  • RP-initiated logout — app redirects the browser to the IdP's end_session_endpoint with id_token_hint and post_logout_redirect_uri.
  • Front-channel logout — IdP loads each app's logout URL in hidden iframes (fragile: third-party cookie blocking).
  • Back-channel logout — IdP POSTs a signed logout token (with sid/sub) server-to-server to every app. Most reliable.

Back-channel endpoint: /logout/connect/back-channel/{registrationId} — register it in the IdP client settings.

How are sessions managed across multiple SSO applications?

There are two layers of session:

  1. IdP session — a cookie on the IdP domain; makes subsequent logins silent. Has its own idle/max lifetimes.
  2. Application session — each app's own session (e.g. JSESSIONID) created after token validation.
  • Use Spring Session with Redis/JDBC so a horizontally scaled app shares sessions.
  • Keep app session timeout ≤ IdP session timeout; use refresh tokens or re-authentication with prompt=none to extend.
  • Limit concurrent sessions via sessionManagement(s -> s.maximumSessions(1)) if required.
  • Protect against session fixation — Spring changes the session id on login by default.

SPA, MFA & troubleshooting

How do you implement SSO for an Angular SPA with a Spring Boot API?

Option A — public client in the browser (e.g. angular-auth-oidc-client): Angular runs Authorization Code + PKCE, holds the access token and sends it as a bearer header; Spring Boot is a resource server.

Option B — BFF (recommended): Spring Cloud Gateway is a confidential OAuth2 client with oauth2Login; the SPA only has a session cookie and the gateway forwards the token downstream with TokenRelay.

How do MFA and social login fit into SSO?
  • MFA is configured in the IdP (TOTP, WebAuthn/passkeys, push). Apps don't implement it; they can require it by requesting acr_values and checking the acr/amr claims (step-up authentication for sensitive actions).
  • Social login (Google, GitHub, Microsoft) is done either directly in Spring via multiple oauth2Login registrations, or — better for SSO — via identity brokering in Keycloak/Okta/Auth0, so apps still trust only one IdP.
  • Link accounts by verified email or explicit linking; never trust an unverified email claim (email_verified).

What are SSO security best practices?
  • Use OIDC Authorization Code + PKCE; never implicit flow. Prefer the BFF pattern for SPAs.
  • Validate state, nonce, signature, iss, aud and exp — let the framework do it.
  • Register exact redirect URIs; no wildcards.
  • Enforce MFA / phishing-resistant passkeys at the IdP; short IdP session lifetimes for privileged users.
  • Implement back-channel logout and deprovision users promptly (SCIM for user sync).
  • Store client secrets in a vault; prefer private_key_jwt client authentication over shared secrets.
  • HTTPS everywhere; HttpOnly, Secure, SameSite cookies.
  • For SAML: require signed assertions, validate audience and time window, prefer SP-initiated flow.

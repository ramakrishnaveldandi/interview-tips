Core

What is Spring Boot and how is it different from the Spring Framework?

Spring Framework provides the core (IoC container, AOP, MVC, transactions, data access). Spring Boot is an opinionated layer on top that removes boilerplate:

  • Auto-configuration — configures beans based on the classpath and properties.
  • Starters — curated dependency sets with compatible versions.
  • Embedded server — Tomcat/Jetty/Undertow inside an executable "fat" JAR; no WAR deployment needed.
  • Production features — Actuator, metrics, health checks, externalized configuration.
One-liner: Spring is the engine; Spring Boot is the car that's ready to drive.
What does @SpringBootApplication do?

It is a meta-annotation combining three annotations:

  • @SpringBootConfiguration — a specialised @Configuration.
  • @EnableAutoConfiguration — loads auto-configuration classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports.
  • @ComponentScan — scans the package of the annotated class and sub-packages.

🧠 How this works

  1. SpringApplication.run() prepares the Environment (properties, profiles) and creates an ApplicationContext — a servlet web context because Spring MVC is on the classpath.
  2. @ComponentScan registers every @Component/@Service/@RestController found in the main class's package and its sub-packages as a bean definition.
  3. @EnableAutoConfiguration imports the classes listed in AutoConfiguration.imports; each one is kept only if its @Conditional checks pass. exclude removes DataSourceAutoConfiguration, so no DataSource is created even if a JDBC driver is present.
  4. The context refresh then creates all non-lazy singletons, starts the embedded server and publishes ApplicationReadyEvent — the app is now serving requests.
Put the main class in a root package — beans outside its package tree are not scanned.
How does auto-configuration work? Explain @Conditional annotations.

Each auto-configuration class is a @AutoConfiguration guarded by conditions. Beans are created only when conditions match, and your own beans take precedence (@ConditionalOnMissingBean).

🧠 How this works

  1. Boot finds this class through the AutoConfiguration.imports file (not component scanning), and processes auto-configurations after your own configuration, so it already knows which beans you defined.
  2. @ConditionalOnClass(ObjectMapper.class) is checked first: if Jackson isn't on the classpath the whole class is skipped.
  3. @ConditionalOnProperty reads app.audit.enabled: true or missing (matchIfMissing = true) passes; false switches the feature off.
  4. @ConditionalOnMissingBean on the method makes it back off if you already declared an AuditService bean — that's how "your beans win" works.
  5. If all conditions match, Spring calls auditService(), injecting the auto-configured ObjectMapper. Every decision is listed in the condition evaluation report (--debug).

Common conditions: @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnBean, @ConditionalOnProperty, @ConditionalOnWebApplication. Run with --debug or hit /actuator/conditions to see the condition evaluation report.

What are starters? Name a few.

Starters are dependency descriptors that pull in everything needed for a capability, with versions managed by the Boot BOM (spring-boot-dependencies).

  • spring-boot-starter-web — Spring MVC + Jackson + embedded Tomcat
  • spring-boot-starter-webflux — reactive stack on Netty
  • spring-boot-starter-data-jpa — Hibernate + Spring Data JPA + HikariCP
  • spring-boot-starter-security, spring-boot-starter-oauth2-resource-server
  • spring-boot-starter-actuator, spring-boot-starter-validation, spring-boot-starter-test
How do you change or replace the embedded server?

Change the port with server.port=8081 (0 = random). To switch to Jetty, exclude Tomcat and add the Jetty starter:

🧠 How this works

  1. The Maven <exclusion> removes spring-boot-starter-tomcat (and the embedded Tomcat jars) from the classpath.
  2. The Jetty starter adds Jetty's server classes instead.
  3. At startup the embedded-server auto-configuration uses @ConditionalOnClass: Tomcat classes are absent, Jetty's are present, so a Jetty web server factory bean is created.
  4. Spring MVC code doesn't change — it only talks to the Servlet API — and generic settings like server.port still apply.
Undertow support was removed in Spring Boot 4 because it doesn't yet support Servlet 6.1 — use Tomcat or Jetty.

Spring core essentials

What is the Spring Framework, and what problem does it solve?

Spring is a lightweight framework for building Java applications. Its core is an IoC container that creates your objects (beans) and wires their dependencies, plus modules for web (MVC/WebFlux), data access, transactions, security, messaging, AOP and testing.

The main problem it solves is tight coupling. Without Spring, classes create their own dependencies, so they're hard to test and change:

🧠 How this works

  1. In the first version new CardPaymentService() hard-codes the implementation, so a test can't swap in a fake.
  2. In the second, component scanning registers OrderService as a bean. Because it has a single constructor, Spring uses it for injection (no @Autowired needed).
  3. Spring resolves the PaymentService parameter by type, creates that bean first if necessary, and passes it in.
  4. No matching bean → startup fails with NoSuchBeanDefinitionException; two matches → NoUniqueBeanDefinitionException unless @Primary/@Qualifier is used.
  5. In a unit test you skip Spring entirely: new OrderService(fakePayment).

Benefits: loose coupling, easy testing (inject mocks), declarative cross-cutting concerns (@Transactional, security, caching via AOP), and a huge ecosystem.

How do you create a Spring Boot project, and what is the standard project structure?

Use Spring Initializr (start.spring.io, or the IntelliJ / VS Code wizard): choose Maven or Gradle, Java version, Boot version, group/artifact and dependencies (Web, Data JPA, Validation, Security, Actuator…), then download and open it.

🧠 How this works

  1. The @SpringBootApplication class sits in com.example.students, so component scanning covers controller, service, repository, config… automatically.
  2. The same base package is used by auto-configuration to find @Entity classes and Spring Data repository interfaces.
  3. Everything in src/main/resources lands at the classpath root: application.yml is loaded at startup, and application-dev.yml is added on top when the dev profile is active.
  4. If Flyway is on the classpath, its auto-configuration runs the scripts in classpath:db/migration at startup, before JPA uses the database.
  5. Tests mirror the package layout so @SpringBootTest can find the main configuration by searching up the package tree.
Keep the main class in the root package: component scanning starts there, so beans in sibling packages outside it won't be found.
application.properties vs application.yml?

Both configure the same properties; Boot loads either (if both exist, .properties wins for duplicate keys). Choose one style per project.

🧠 How this works

  1. At startup Boot loads application.properties from the classpath into the Environment as a property source.
  2. server.port is bound to ServerProperties and used when the embedded server is created; spring.datasource.* is bound to DataSourceProperties, from which auto-configuration builds a HikariCP DataSource.
  3. ${DB_USER} is a placeholder resolved from other sources such as an environment variable; if nothing provides it, startup fails with a "Could not resolve placeholder" error.
  4. ddl-auto=validate makes Hibernate compare entity mappings with the real schema at startup and fail fast on a mismatch; logging.level.com.example=DEBUG sets that logger's level.

🧠 How this works

  1. Boot parses the YAML tree and flattens it into the same dotted keys (server.port, spring.datasource.url…), so it configures exactly the same beans as the properties file.
  2. Indentation defines nesting — a wrong indent silently puts a key under the wrong parent.
  3. Relaxed binding maps ddl-auto to the ddlAuto field of the properties class; under logging.level, com.example is a logger name.
  4. If both files define the same key, the .properties value wins.
  • YAML is easier for nested config and lists, and can hold several profile documents separated by ---; but indentation errors are easy to make.
  • Never commit real credentials — use ${ENV_VAR} placeholders or a secrets manager.
  • Use ddl-auto=validate (or none) with Flyway/Liquibase in production, never update/create.

REST API essentials

What is REST? Explain the HTTP methods, and PUT vs PATCH.

REST (Representational State Transfer) is an architectural style for APIs: resources are identified by URLs, manipulated with standard HTTP methods, represented as JSON, and every request is stateless (it carries all the information needed, e.g. a token).

MethodPurposeExampleSafe?Idempotent?
GETReadGET /students/10YesYes
POSTCreate (or trigger an action)POST /studentsNoNo
PUTReplace the whole resourcePUT /students/10NoYes
PATCHPartial updatePATCH /students/10NoNot guaranteed
DELETERemoveDELETE /students/10NoYes
  • Safe = doesn't change server state. Idempotent = repeating the request has the same effect as sending it once (important for retries).
  • PUT sends the complete representation; omitted fields are cleared/reset. PATCH sends only the fields to change (e.g. {"email": "new@x.com"}).
  • To make POST retry-safe (payments), accept an Idempotency-Key header and store processed keys.
@PathVariable vs @RequestParam vs @RequestBody vs @RequestHeader?

🧠 How this works

  1. At startup RequestMappingHandlerMapping registers each method, combining the class-level /api/students with the method path and HTTP verb.
  2. A request reaches DispatcherServlet, which finds the matching handler and resolves each parameter with an argument resolver.
  3. @PathVariable takes the {id} segment and converts it to Long (/abc → MethodArgumentTypeMismatchException → 400). @RequestParam reads the query string: required = false gives null, defaultValue fills in 0.
  4. @RequestBody uses Jackson to turn the JSON into StudentRequest (malformed JSON → 400); @Valid then validates it, and on failure MethodArgumentNotValidException is thrown before the method runs.
  5. A missing required header throws MissingRequestHeaderException (400). Return values are written as JSON by Jackson because of @RestController.

@RequestParamQuery string / form fieldFilters, paging, optional inputs

@RequestHeaderHTTP headerCorrelation IDs, API versions, idempotency keys
What is ResponseEntity? Which HTTP status codes should an API return?

By default a controller method returns 200 OK. ResponseEntity gives full control over the status, headers and body.

🧠 How this works

  1. When a handler returns ResponseEntity, Spring MVC uses its status and headers as given and writes the body through an HttpMessageConverter (Jackson for objects).
  2. created(uri) sets 201 plus a Location header pointing at the new resource; noContent()/notFound() + build() send no body.
  3. The converter is chosen by content negotiation (the client's Accept header), so the same object can be served as JSON or another supported format.
  4. If you return a plain object instead, Spring writes it with 200 (or the status from @ResponseStatus).

What are REST API design best practices?
  • Nouns, not verbs, plural collections: GET /students/10, not /getStudent?id=10 or /createStudent.
  • Let the HTTP method express the action; nest only for clear ownership: GET /students/10/courses.
  • Return correct status codes and a consistent error format (RFC 9457 ProblemDetail).
  • Paginate collections (?page=0&size=20&sort=name) and cap page sizes.
  • Use DTOs, never expose entities; validate input.
  • Version the API (/api/v1/... or a header) and evolve compatibly.
  • Use lowercase, hyphenated URLs; ISO-8601 dates; consistent field naming.
  • Secure everything (HTTPS, auth), add rate limits, and document with OpenAPI (springdoc → Swagger UI).

Other common Jakarta Bean Validation constraints: @Size(min, max), @Min/@Max, @Positive, @Email, @Pattern(regexp), @Past/@Future, @Digits, and @Valid to cascade into nested objects.

🧠 How this works

  1. Jackson creates the StudentRequest record from the JSON through its canonical constructor.
  2. @Valid on the parameter makes Spring run Hibernate Validator (from spring-boot-starter-validation) over every constraint on the record components.
  3. List<@NotBlank String> checks each element; @Valid on address cascades into the constraints of AddressRequest.
  4. All violations are collected (not just the first). If there are any, MethodArgumentNotValidException is thrown before the method body runs → 400, which your @RestControllerAdvice can turn into a readable error body.
Requires spring-boot-starter-validation. Validate early at the API boundary, before business logic or the database.
What is a DTO, and why shouldn't you return JPA entities from controllers?

A Data Transfer Object is a simple object (ideally a Java record) that defines exactly what data goes in or out of the API.

🧠 How this works

  1. Inbound: Jackson converts the JSON into the request DTO, validation runs, and the controller passes the DTO to the service.
  2. The service maps the DTO to an entity and the repository persists it inside a transaction.
  3. Outbound: the service maps the entity to a response DTO while still inside the transaction, so any lazy fields it needs are loaded deliberately.
  4. Jackson only ever sees the DTO — no lazy-loading exceptions, no infinite recursion, and no internal fields leaking to the client.
  • Security: entities can expose internal fields (password hashes, internal flags) and allow mass assignment if bound directly from requests.
  • Decoupling: you can change the database schema without breaking API clients, and vice versa.
  • Avoids JPA problems: lazy-loading exceptions and infinite recursion in bidirectional relationships during JSON serialisation.
  • Tailored shapes: different DTOs per use case (summary vs detail), validation annotations on request DTOs only.

🧠 How this works

  1. The record gives you an immutable DTO with constructor, accessors, equals/hashCode/toString generated.
  2. from() copies only the fields you choose from the entity — anything else (e.g. a password hash) can never be serialised.
  3. Jackson serialises a record through its accessors id(), name(), email() → {"id":…,"name":…,"email":…}.
  4. MapStruct does the same mapping with an annotation processor: it generates plain Java mapper code at compile time (no runtime reflection) and can register it as a Spring bean.
What is the difference between REST and SOAP? When would you use each?

REST is an architectural style built on plain HTTP: resources have URLs, you use the HTTP methods and status codes, and the payload is usually JSON. SOAP is a protocol: every message is an XML envelope described by a machine-readable WSDL contract, and it comes with a family of WS-* standards for enterprise needs.

AspectRESTSOAP
NatureArchitectural style (constraints: stateless, uniform interface, cacheable…)Protocol with a strict message format (SOAP 1.1 / 1.2)
PayloadAny representation — usually JSON, also XML, CSV, binaryAlways XML (Envelope → optional Header → Body)
ContractOptional — OpenAPI is the de-facto standardMandatory WSDL + XSD; clients are usually generated from it
TransportHTTP onlyMostly HTTP, but transport-independent (JMS, SMTP…)
OperationsHTTP verbs on resources (GET /orders/42)Named operations (getOrder), almost always sent with HTTP POST
ErrorsHTTP status codes (+ ProblemDetail body)<soap:Fault> element in the body (SOAP 1.1 over HTTP returns 500)
CachingNative HTTP caching for GET (Cache-Control, ETag)No HTTP caching (everything is a POST)
Security / QoSTransport-level: HTTPS + OAuth2/JWTMessage-level WS-Security (signing/encrypting parts of the XML), WS-ReliableMessaging, WS-AtomicTransaction
WeightLightweight, easy from browsers and mobile appsVerbose XML, heavier tooling
  • Use REST for public/partner APIs, web and mobile front-ends, and microservice-to-microservice calls — it is simpler, faster to consume and cache-friendly.
  • Use SOAP when the other side mandates it (SAP, banking, telecom, government portals), when you need a strict, versioned contract with generated clients, or message-level security that survives intermediaries.
  • In Spring: REST via spring-boot-starter-web (@RestController, RestClient); SOAP via spring-boot-starter-web-services (Spring Web Services: contract-first @Endpoints and the WebServiceTemplate client), or Apache CXF for JAX-WS.

🧠 How this works

  1. The REST controller maps GET /api/countries/India straight to get("India"); Jackson writes the returned DTO as JSON and the HTTP status tells the client the outcome.
  2. In SOAP every request is an HTTP POST to the same endpoint URL (Spring WS's MessageDispatcherServlet, by default under /services/*). The dispatcher picks the method by the namespace + local name of the first element inside <soap:Body> — that is what @PayloadRoot declares.
  3. @RequestPayload unmarshals the body XML into the JAXB class generated from the XSD (contract-first); @ResponsePayload marshals the returned object back into the response envelope.
  4. On the client side WebServiceTemplate.marshalSendAndReceive does the reverse: marshals the request object, wraps it in an envelope, POSTs it, and unmarshals the response body — or throws SoapFaultClientException if the server returned a SOAP Fault.

🧠 How this works

  1. This is the SOAP 1.1 request the client above sends; the REST equivalent is just GET /api/countries/India with no body.
  2. The Header is where WS-Security tokens/signatures go; it is empty here.
  3. c:getCountryRequest in namespace http://example.com/countries is the payload root that @PayloadRoot(namespace = NS, localPart = "getCountryRequest") matches.
  4. The structure of getCountryRequest is fixed by the XSD in the WSDL, so a missing or misspelled element fails validation instead of being silently ignored as an unknown JSON field might be.
Interview angle: "We expose REST to our web/mobile clients, but integrate with SAP over SOAP because SAP publishes its services as WSDL — we generate JAXB classes from the WSDL and call them with WebServiceTemplate, with timeouts and a circuit breaker around the call."

Idempotent vs non-idempotent operations

What does idempotent mean? What is the difference between idempotent and non-idempotent operations?

An operation is idempotent if performing it once or many times leaves the system in the same state. Repeating it has no additional effect. A non-idempotent operation changes the state again every time it runs.

Idempotent ✅Non-idempotent ❌
"Set the email to asha@x.com""Add ₹500 to the balance"
"Delete order 42""Create a new order"
"Mark invoice 7 as PAID""Increment the retry counter"
Math.abs(x), Set.add(x), map.put(k, v)list.add(x), counter++, sending an email
UPDATE account SET status = 'CLOSED' WHERE id = 7UPDATE account SET balance = balance - 500 WHERE id = 7

Why it matters: in distributed systems, requests are retried all the time — a mobile client on a flaky network, a load balancer, a message broker redelivering a message, a user double-clicking "Pay". If the operation is idempotent, a retry is harmless. If it isn't, a retry means a duplicate order, a double charge or a doubled stock reduction.

Idempotent means the server state is the same after repeats — the response may differ. Deleting an order returns 204 the first time and 404 the second, but the state (order gone) is identical, so DELETE is still idempotent.
Which HTTP methods are safe, idempotent, or neither? Why are PUT and DELETE idempotent but POST and PATCH not?
MethodSafe (no state change)IdempotentWhy
GET, HEAD, OPTIONS✅✅Only read data
PUT❌✅Replaces the resource with the complete representation sent — sending it twice gives the same final resource
DELETE❌✅After the first call the resource is gone; further calls change nothing
POST❌❌Typically creates a new resource or triggers an action each time — two calls create two orders
PATCH❌Not guaranteedDepends on the patch: {"email":"x"} is idempotent, {"op":"increment","path":"/qty"} is not

🧠 How this works

  1. Safe is stricter than idempotent: a safe method doesn't change state at all, so every safe method is automatically idempotent.
  2. PUT and DELETE describe the target state ("make it look like this", "make it not exist") — reaching a state twice is the same as reaching it once.
  3. POST and "relative" PATCH operations describe an action ("create another", "add one more") — every repeat performs the action again.
  4. HTTP clients, proxies and gateways may automatically retry idempotent methods on network errors; they must never automatically retry POST without an idempotency mechanism.
How do you make a non-idempotent POST (e.g. a payment) safe to retry? Implement an Idempotency-Key in Spring Boot.

The client generates a unique key (a UUID) per logical operation and sends it in an Idempotency-Key header. The server stores the key with the result of the first execution; any retry with the same key returns the stored result instead of charging again. A unique constraint on the key makes this safe even when two retries arrive at the same time.

🧠 How this works

  1. The key is the primary key, so the database itself guarantees that only one row per key can ever exist — even if two retries hit two different app instances at the same moment.
  2. status distinguishes a request that is still running (IN_PROGRESS) from one that finished (COMPLETED), so a concurrent retry isn't answered with an empty result.
  3. response_body and http_status store exactly what the first request returned, so retries can be answered identically; created_at lets a cleanup job delete keys older than the retry window (e.g. 24 hours).

🧠 How this works

  1. The first request inserts the key with status IN_PROGRESS; because the key is the primary key, a second concurrent request with the same key fails with DuplicateKeyException instead of charging twice.
  2. A retry after completion finds the stored record and gets the same 201 response body back (with Idempotent-Replayed: true), so the client can't tell the difference — but the gateway was called only once.
  3. The request hash catches a buggy client reusing a key for a different payment (→ 422) instead of silently returning the wrong result.
  4. If a retry arrives while the first request is still running it gets 409; the client waits and retries. Production systems also expire old keys (e.g. after 24 h) and handle crashes that leave a record stuck IN_PROGRESS.
  5. This is the same pattern Stripe and most payment APIs expose. Clients generate the key once per user action (e.g. per "Pay" button press) and reuse it for all retries of that action.
What is an idempotent consumer? How do you handle duplicate Kafka/RabbitMQ messages?

Most brokers guarantee at-least-once delivery: if a consumer crashes after doing the work but before committing the offset (or acknowledging the message), the message is delivered again. "Exactly-once" processing in practice means at-least-once delivery + an idempotent consumer.

🧠 How this works

  1. Each event carries a unique eventId set by the producer. The consumer tries to insert it into processed_message; the primary key rejects a second insert of the same id.
  2. The insert and ledger.credit run in one database transaction: either both happen or neither does. If the app crashes before commit, the redelivered message is processed normally; if it crashes after commit, the redelivery is detected and skipped.
  3. Without this, a redelivered "payment completed" event would credit the merchant twice.
  4. Alternatives: make the change naturally idempotent (an upsert keyed by payment id, or "set status = SETTLED" instead of "add amount"), or use Kafka transactions for Kafka-to-Kafka flows. On the producer side, enable.idempotence=true (the default since Kafka 3.0) prevents duplicates caused by producer retries.
How do you write idempotent database operations (upserts, conditional updates)?

Prefer statements that describe the final state or are guarded by a condition, so running them twice has no extra effect.

🧠 How this works

  1. balance = balance - 500 is relative to the current value, so each execution moves money again — the classic double-charge bug on retry.
  2. The guarded update only matches while the invoice is PENDING; after the first run the row is PAID, so a retry updates 0 rows. Checking the affected row count also tells you whether this call did the work.
  3. Upserts (ON CONFLICT … DO UPDATE / ON DUPLICATE KEY UPDATE) rely on a unique index: the first run inserts, later runs update the row to the same values.
  4. Ledger-style designs store each movement once, keyed by a business id (transfer_id), and derive the balance from the entries — duplicates are rejected by the unique key instead of being applied twice.
How do retries, timeouts and idempotency fit together in microservices?
  • A timeout doesn't tell you whether the operation happened — the server may have processed it and only the response was lost. So the client must be able to retry safely.
  • Retry only idempotent operations automatically (GET, PUT, DELETE, or POST with an idempotency key). Configure retries for those calls only.
  • Use exponential backoff with jitter and a small maximum number of attempts, so retries don't overload a struggling service (a "retry storm").
  • Combine with a circuit breaker so that when a dependency is clearly down, calls fail fast instead of retrying.
  • Propagate the idempotency key downstream (to the payment gateway, to events), so the whole chain is retry-safe.

🧠 How this works

  1. With these settings a failing call is tried up to 3 times, waiting 200 ms and then 400 ms (doubled each time). In high-traffic systems also add jitter (random variation in the wait) so thousands of clients don't retry at the same instant.
  2. Only I/O and timeout errors are retried — a 400 validation error would fail the same way again, so retrying it is pointless.
  3. Attach this retry only to idempotent calls; for a POST, retry only if the request carries an idempotency key the server honours.

Logging, async & scheduling

How does logging work in Spring Boot? Explain log levels and configuration.

Spring Boot uses SLF4J (the API you code against) with Logback (the implementation) by default; you can swap in Log4j2. Levels, from most to least verbose: TRACE < DEBUG < INFO < WARN < ERROR. Setting a level shows that level and everything above it.

🧠 How this works

  1. LoggerFactory.getLogger is the SLF4J API; Boot's default logging starter binds it to Logback, which does the actual output.
  2. One static final logger per class, named after the class, so its level is controlled by logging.level.com.example….
  3. log.debug("…{}", id) first checks whether DEBUG is enabled; if not it returns immediately and the message is never formatted.
  4. The orElseThrow lambda runs only when the Optional is empty: it logs a WARN and throws, and the exception travels up to your exception handler.

🧠 How this works

  1. Boot's logging system applies these settings very early in startup, before most beans are created.
  2. logging.level works on the logger-name hierarchy: everything defaults to INFO, com.example and its children log DEBUG, and org.hibernate.SQL at DEBUG prints every SQL statement.
  3. logging.file.name adds a file appender next to the console; Boot's default Logback setup rolls the file when it grows (10 MB by default).
  4. logging.structured.format.console: ecs (Boot 3.4+) switches console output to JSON in Elastic Common Schema, so log shippers can parse fields instead of text.
  • Use placeholders, never string concatenation; log the exception as the last argument to get the stack trace.
  • Add a correlation/trace ID to every log line (MDC; Micrometer Tracing adds traceId automatically).
  • Never log passwords, tokens or personal data. Change levels at runtime via /actuator/loggers.
How does @Async work, and what are its pitfalls?

@EnableAsync + @Async makes Spring run the method on a separate thread (through a proxy), so the caller returns immediately. Return void or CompletableFuture<T>.

🧠 How this works

  1. @EnableAsync registers a bean post-processor that wraps every bean having @Async methods in a proxy.
  2. Other beans get the proxy injected. Calling generate(42) on it submits the real call to a TaskExecutor (Boot's auto-configured applicationTaskExecutor) and returns a CompletableFuture immediately.
  3. The method runs on a pool thread; when it returns, the future the caller holds is completed with the Report. If it throws, that future completes exceptionally.
  4. The caller can continue and later join() or chain thenApply. A call through this skips the proxy and simply runs synchronously.
  • Self-invocation doesn't work: calling an @Async method from the same class bypasses the proxy (same as @Transactional).
  • The method must be public and on a Spring bean.
  • Exceptions from void methods are lost unless you configure an AsyncUncaughtExceptionHandler.
  • Boot auto-configures a ThreadPoolTaskExecutor (tune spring.task.execution.pool.*), or virtual threads with spring.threads.virtual.enabled=true.
  • Security context, MDC and transactions don't automatically flow to the new thread.
How do you schedule tasks with @Scheduled? Explain Spring cron expressions.

🧠 How this works

  1. @EnableScheduling registers a post-processor that finds @Scheduled methods on beans and registers them with a TaskScheduler (Boot auto-configures one with a single thread by default).
  2. fixedRate triggers every 60 s measured from each start; on a single thread a long run delays the next one rather than overlapping it.
  3. fixedDelay waits 30 s after the previous run finishes; initialDelay postpones the first run by 10 s after startup.
  4. The cron expression is evaluated in the given zone, independent of the server's clock zone.
  5. If a run throws, the error is logged and the task is still scheduled for its next run.

Spring cron has six fields (it includes seconds): second minute hour day-of-month month day-of-week.

ExpressionRuns
0 0 0 * * *Every day at midnight

With several app instances, every instance runs the job. Use ShedLock (or Quartz in clustered mode) to run it on only one node. By default all scheduled tasks share a single thread — configure spring.task.scheduling.pool.size if jobs can overlap.
What are Spring Boot best practices you follow in production code?
  • Constructor injection, final fields; no field @Autowired.
  • Layered structure: thin controllers, business logic in services, data access in repositories; single responsibility per class.
  • DTOs at the API boundary, validation on input, centralised exception handling with ProblemDetail.
  • Externalised config with profiles and type-safe @ConfigurationProperties; secrets from env vars / Vault, never in git.
  • Transactions on service methods; keep them short; no remote calls inside them.
  • Database migrations with Flyway/Liquibase; open-in-view=false; avoid N+1 queries.
  • Observability: structured logs with trace IDs, Actuator health/metrics, alerts.
  • Resilience: timeouts on every outbound call, retries with backoff, circuit breakers.
  • Testing: unit tests, slice tests, Testcontainers integration tests in CI.
  • Security: Spring Security defaults, least privilege, dependency scanning, keep Boot and libraries up to date.
  • Build & run: ./mvnw clean verify, executable jar (java -jar app.jar), container images via buildpacks or a layered Dockerfile.

DI & Beans

What is IoC and Dependency Injection? Why prefer constructor injection?

Inversion of Control: the container, not your code, creates and wires objects. DI is how it supplies dependencies. Constructor injection is preferred because:

  • Dependencies can be final → immutable, thread-safe.
  • Object is never in a half-initialised state; missing deps fail at startup.
  • Easy to unit test without Spring (new OrderService(mockRepo)).
  • Too many constructor parameters makes a design smell visible.

🧠 How this works

  1. Component scanning finds @Service; the class has one constructor, so Spring uses it without @Autowired.
  2. Before calling it, Spring resolves OrderRepository (a Spring Data proxy) and PaymentClient by type, creating them first if needed.
  3. If a dependency is missing, startup fails with UnsatisfiedDependencyException — you find out at boot, not on the first request.
  4. Fields are final and set once, so the singleton is safely shared by all request threads.

How does Spring handle circular dependencies?

Since Spring Boot 2.6 circular references are prohibited by default and startup fails with BeanCurrentlyInCreationException. With constructor injection, they can never be resolved. Fixes, best first:

  1. Redesign — extract the shared logic into a third bean, or use events (ApplicationEventPublisher).
  2. Inject lazily: @Lazy on the constructor parameter or ObjectProvider<T>.
  3. Last resort: spring.main.allow-circular-references=true (only works with setter/field injection).

Isolation (READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE…) defaults to the database's level. Use readOnly = true on queries — Hibernate skips dirty checking.

Why does @Transactional sometimes not work? (self-invocation)

@Transactional is applied via an AOP proxy. Calls that don't go through the proxy aren't intercepted:

  • Self-invocation — this.save() from another method in the same class.
  • Method is private or final (CGLIB can't override it).
  • Bean not managed by Spring (created with new).
  • Exception is caught and swallowed inside the method.

🧠 How this works

  1. Because ReportService has a @Transactional method, Spring wraps it in a proxy at startup, and other beans are injected with that proxy.
  2. A caller invokes generateAll() on the proxy; it has no @Transactional, so the proxy just forwards to the real object.
  3. Inside, this.generate(id) is a plain Java call on the real object — the proxy and its TransactionInterceptor never see it, so no REQUIRES_NEW transaction is started.
  4. The fix moves generate() into another bean, so each call goes through that bean's proxy; or TransactionTemplate.execute(…) starts the transaction explicitly in code.
What are the default rollback rules?

By default Spring rolls back on unchecked exceptions (RuntimeException, Error) and commits on checked exceptions.

🧠 How this works

  1. The transactional proxy starts a transaction before transfer() runs and decides commit vs rollback when it exits.
  2. Normal return → commit.
  3. InsufficientFundsException is checked, which would normally commit, but rollbackFor makes it roll back; the exception is still rethrown to the caller.
  4. NotificationFailedException matches noRollbackFor, so the transaction commits even though the exception propagates.
  5. Any other RuntimeException/Error rolls back; other checked exceptions commit. The most specific matching rule wins.

What is Spring Boot Actuator? Which endpoints are most useful?

Actuator exposes operational endpoints: /actuator/health (with Kubernetes liveness/readiness groups), /info, /metrics, /prometheus, /env, /loggers (change log levels at runtime), /threaddump, /heapdump, /conditions, /beans, /mappings.

What is a GraalVM native image and what are its trade-offs?

Spring AOT processing generates bean definitions at build time, then GraalVM compiles the app ahead-of-time to a native executable.

🧠 How this works

  1. -Pnative activates the native profile, which runs Spring AOT at build time: it evaluates the configuration and generates Java code for bean definitions plus reflection/proxy hints.
  2. native:compile runs GraalVM's native-image: it analyses everything reachable from main and compiles only that into a platform-specific executable.
  3. spring-boot:build-image with the same profile uses Cloud Native Buildpacks to do the native compilation inside a container, so you don't need GraalVM installed locally; the result is an OCI image.
  4. Because conditions and beans are fixed at build time, the classpath and bean set cannot change at runtime.

How does a circuit breaker work? Show Resilience4j usage.

States: CLOSED (calls flow, failures counted) → OPEN when failure rate exceeds threshold (calls fail fast to a fallback) → after a wait, HALF_OPEN lets trial calls through and closes again if they succeed.

🧠 How this works

  1. The Resilience4j Spring Boot starter registers aspects, so InventoryClient is proxied and every call to check() passes through retry and circuit-breaker logic named inventory.
  2. Success: the HTTP call returns and the result is recorded as a success in the breaker's sliding window.
  3. Failure: the exception is recorded and @Retry may re-attempt the call according to its config.
  4. When the failure rate crosses the threshold the breaker opens: calls are rejected immediately without hitting the network.

🧠 How this works

Scenario & design questions

A REST endpoint is called 10,000 times an hour and reads product categories that change once a day. How do you optimise it?

First, size the problem: 10,000 calls/hour is only ~3 requests per second. The database copes easily, so the aim is lower latency and less pointless DB work — not heroic infrastructure. Because the data changes once a day, it is an ideal caching candidate. Work through the layers, cheapest first:

  1. Application cache (Spring Cache + Caffeine) — cache the whole list under one key; a hit costs a map lookup instead of a DB round-trip.
  2. Explicit eviction — evict when an admin changes a category (@CacheEvict on the update path) plus a TTL / nightly eviction as a safety net, so staleness is bounded.
  3. HTTP caching — Cache-Control: public, max-age=3600 lets browsers, CDNs and gateways answer without even reaching the service; an ETag turns re-validations into cheap 304 Not Modified responses.
  4. Distributed cache (Redis) only when you run many instances and need them all to see an update immediately — per-instance Caffeine caches can each serve old data until their own TTL/eviction.
  5. Query hygiene regardless of caching: return a DTO projection, select only the needed columns, and index the sort/filter columns.

🧠 How this works

  1. @EnableCaching wraps CategoryService in a proxy. The first findAll() misses, runs the SELECT and stores the result under the fixed key 'all' (a SpEL string literal); every later call returns that list without touching the DB.
  2. The cached value is an immutable list (Stream.toList()) of immutable records — safe to share between threads. Caching JPA entities instead would hand out detached objects with lazy associations and let callers mutate the cached state.
  3. rename() is annotated with @CacheEvict(allEntries = true): after it returns successfully the whole categories cache is cleared, so the next read reloads fresh data. Both advices sit on the same proxy, so the eviction can happen just before the commit; a concurrent read in that tiny window could re-cache the old list (the 1 h TTL bounds the damage). If that matters, wrap the cache manager in TransactionAwareCacheManagerProxy so evictions are deferred until after commit.
  4. The nightly @Scheduled job calls evictAll() through another bean: calling this.evictAll() from inside CategoryService would bypass the proxy and evict nothing. Spring cron has six fields — 0 0 0 * * * = second 0, minute 0, hour 0, every day.
  5. The controller adds Cache-Control: max-age=3600, public, so clients and any CDN in between reuse the response for an hour without calling the service at all.

🧠 How this works

  1. type: caffeine (with com.github.ben-manes.caffeine:caffeine on the classpath) makes Boot create a CaffeineCacheManager; cache-names pre-creates the categories cache.
  2. expireAfterWrite=1h is the safety net: even if an eviction is missed (e.g. someone updates the table directly in SQL), data is at most one hour stale.
  3. Caffeine lives inside each JVM. With three pods, an evict on pod A does not clear pods B and C — they serve old data until their TTL. Redis gives one shared cache, at the cost of a network hop and serialisation.
What about the Hibernate second-level cache? It caches entities by id, so repo.findAll() would still run its SELECT unless the query cache is also enabled. With a Spring cache already in front of the method, an L2 cache adds little here; it is more useful for findById-style lookups and for entities reached through associations.
Also mention: a ShallowEtagHeaderFilter adds an ETag header computed from the response body so clients can revalidate with If-None-Match and get 304. It saves bandwidth, not server work — the response is still generated.
Your service calls an external SAP SOAP endpoint that sometimes takes 10+ seconds, and other requests are blocked waiting. What do you do?

The real problem is that a slow dependency is consuming your request threads: every caller stuck on SAP holds a Tomcat worker (200 by default), and once they are all waiting, even requests that never touch SAP queue up. The fix is to bound how long and how many calls can wait, and to fail fast when SAP is unhealthy:

  1. Timeouts on the SOAP client (connect + read). Without them a socket read can wait for a very long time.
  2. Bulkhead — cap the number of concurrent SAP calls (e.g. 10), so SAP can occupy at most 10 threads; extra callers are rejected immediately instead of piling up.
  3. Circuit breaker — count failures and slow calls; when too many, open the circuit and fail fast for a while instead of waiting 10 s per call.
  4. Fallback — return last-known-good data (e.g. cached prices) or a clear 503 "SAP unavailable" error.
  5. Decouple — if the caller does not need the answer immediately (posting an invoice, creating a purchase order), put the request on a queue / outbox, reply 202 Accepted, and let a background worker talk to SAP at its own pace.
  6. Retry carefully — only for idempotent reads, few attempts, with backoff. Retrying a call that already took 8 s multiplies the waiting and adds load to a struggling SAP.

🧠 How this works

  1. Jaxb2Marshaller converts between the generated JAXB classes and the SOAP body XML.
  2. HttpUrlConnectionMessageSender is Spring WS's JDK-based HTTP transport. The connect timeout bounds the TCP handshake (3 s); the read timeout bounds how long the socket waits for data (8 s) — so a hung SAP call now fails with an exception instead of holding the thread indefinitely.
  3. A timeout surfaces as a Spring WS WebServiceIOException, which the circuit breaker below records as a failure.
  4. For connection pooling you can plug in the Apache HttpClient 5 based message sender instead; the timeout principle is the same.

🧠 How this works

  1. The Resilience4j Spring Boot starter (plus AOP support: spring-boot-starter-aop, renamed spring-boot-starter-aspectj in Boot 4) proxies SapPriceGateway. Its default aspect order is Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead → your method, so here the circuit breaker wraps the bulkhead.
  2. Bulkhead (semaphore-based by default): if 10 SAP calls are already in flight, the 11th caller gets BulkheadFullException at once instead of blocking — SAP can never occupy more than 10 request threads.
  3. Circuit breaker: each call's outcome and duration go into a sliding window. When the failure rate or the slow-call rate crosses the threshold, the circuit opens and calls are rejected with CallNotPermittedException in microseconds, without contacting SAP.
  4. Any of these exceptions — timeout, bulkhead full, circuit open — is routed to priceFallback, which returns the last good price (flagged stale) or throws a domain exception that a @RestControllerAdvice turns into 503 Service Unavailable.
  5. The ConcurrentHashMap keeps the example short; in production use a real cache (Caffeine/Redis) with a TTL so stale data does not live forever.

🧠 How this works

  1. The bulkhead allows 10 concurrent calls; max-wait-duration: 0 means an 11th caller does not wait for a free slot.
  2. The circuit breaker looks at the last 20 calls (but only after at least 10 have been recorded). It opens if ≥ 50% failed or ≥ 50% took longer than 5 s — so a SAP that is merely slow, not failing, still trips the breaker.
  3. While open it rejects calls for 30 s, then goes half-open and lets 3 trial calls through; if they succeed it closes, otherwise it opens again.
  4. These numbers are starting points — tune them from real latency percentiles (Actuator/Micrometer exposes resilience4j_* metrics).
Resilience4j's @TimeLimiter only works on asynchronous return types (CompletableFuture, reactive types); for a blocking SOAP call the socket timeouts above are what actually bound the wait. Virtual threads (spring.threads.virtual.enabled=true) stop blocked calls from exhausting platform threads, but they do not make SAP faster or protect it from overload — you still need timeouts, a bulkhead and a circuit breaker.

Hands-on tasks interviewers ask you to write live or as a take-home. Imports are omitted for brevity; code targets Spring Boot 3.4+ / 4.x.

Build a CRUD REST API for Product with validation (controller → service → repository).

Keep the layers thin and clear: records as DTOs, the entity never leaves the service, 201 Created with a Location header on create.

🧠 How this works

  1. Startup: Hibernate maps Product; Spring Data generates an implementation of ProductRepository at runtime (backed by SimpleJpaRepository); ProductService is wrapped in a transactional proxy.
  2. POST /api/products: DispatcherServlet routes to create, Jackson builds ProductRequest, and @Valid checks it. Invalid → MethodArgumentNotValidException → 400, and the service is never called.
  3. Valid → the proxy opens a read-write transaction (the method-level @Transactional overrides the class-level readOnly = true); save() inserts the row, the id is generated, the transaction commits, and the controller returns 201 with a Location header.
  4. update: the loaded entity is managed, so the setters just change it in memory; at commit Hibernate's dirty checking flushes an UPDATE automatically.
  5. Unknown id → ProductNotFoundException (unchecked, so the transaction rolls back) propagates out of the controller; a @RestControllerAdvice maps it to 404 (without one it becomes a 500). DELETE success returns 204 via @ResponseStatus.
Write a global exception handler that returns RFC 9457 ProblemDetail responses, including validation errors.

🧠 How this works

  1. ProductNotFoundException extends RuntimeException, so services can throw it without throws clauses and it also triggers transaction rollback.
  2. When a controller call throws, Spring looks for an @ExceptionHandler in the advice whose type is the closest match: ProductNotFoundException → notFound; Exception.class only catches what nothing more specific handles.
  3. MethodArgumentNotValidException is raised during @Valid argument validation, before the controller method runs; invalid collects each field error into an ordered errors map.
  4. Each handler returns a ProblemDetail, which Spring writes as application/problem+json using the status inside it; if instance isn't set, Spring fills it with the request path.
  5. fallback turns any unexpected error into a generic 500, so internal details never leak — log the exception there for debugging.

🧠 How this works

  1. type: "about:blank" is the default, meaning "no extra semantics beyond the HTTP status"; title defaults to the status reason phrase.
  2. status repeats the HTTP status code and detail comes from forStatusAndDetail(…).
  3. instance was not set in code, so Spring filled it with the request path.
  4. errors is the custom property added with setProperty; Jackson writes such properties as top-level fields. Every error in the API now has the same shape for clients.
Alternatively extend ResponseEntityExceptionHandler, or set spring.mvc.problemdetails.enabled=true so Spring's built-in exceptions use ProblemDetail too.

Add pagination, sorting and filtering to a list endpoint.

🧠 How this works

  1. Spring Data parses the method name: findBy + NameContainingIgnoreCase becomes a case-insensitive LIKE '%name%' query.
  2. With a Pageable argument it adds ORDER BY and LIMIT/OFFSET, and runs a separate count query to fill in the total pages and elements of the Page.

Write an AOP aspect that logs the execution time of methods annotated with @LogExecutionTime.

Requires the AOP starter (spring-boot-starter-aop; renamed spring-boot-starter-aspectj in Boot 4).

🧠 How this works

  1. @Aspect + @Component makes TimingAspect a bean; AOP auto-configuration registers a bean post-processor that checks every bean against the aspect's pointcuts.
  2. ReportService.generate() carries @LogExecutionTime, so Spring creates a CGLIB proxy subclass and injects that proxy wherever ReportService is used.
  3. A call to generate() enters time() first: it records the start time and pjp.proceed() invokes the real method.

Cache a slow lookup with @Cacheable and evict it on update.

🧠 How this works

  1. @EnableCaching turns on the caching infrastructure, and Boot auto-configures a CacheManager from spring.cache.* and the classpath.
  2. CountryService is wrapped in a proxy. On find("IN") the proxy evaluates the key #code and checks the countries cache: hit → returns the cached value without running the method; miss → runs it and stores the result.
  3. @CachePut always runs update() and then stores the returned value under country.code(), so the next find sees fresh data.

🧠 How this works

  1. type: caffeine makes Boot create a CaffeineCacheManager (Caffeine must be on the classpath).
  2. The spec applies to each cache: at most 1000 entries (older, less-used ones are evicted) and each entry expires 10 minutes after it was written.
  3. Caches like countries are created on first use.
  4. Caffeine is in-memory per instance, so each pod has its own copy; type: redis gives one shared cache across instances, with values serialised to Redis.
Publish a domain event after an order is saved, and send an email only if the transaction commits.

@TransactionalEventListener(phase = AFTER_COMMIT) guarantees the listener does not run if the transaction rolls back; add @Async so the email does not slow down the request.

🧠 How this works

  1. place() runs inside the transactional proxy: save() writes the order and publishEvent hands OrderPlaced to Spring's event multicaster.
  2. Because a transaction is active, the @TransactionalEventListener doesn't run yet — Spring registers it to run when the current transaction completes.
  3. The method returns and the proxy commits. Only after a successful commit is the listener invoked; @Async hands it to a pool thread, so the HTTP response isn't delayed by the email.
  4. If place() throws and the transaction rolls back, the listener never runs, so no email goes out for an order that doesn't exist.
  5. If the event is published with no transaction active, the listener is skipped by default (fallbackExecution = false). An email failure can't undo the committed order, so log and retry it separately.
For guaranteed delivery across services (e.g. Kafka), use the transactional outbox pattern instead — an in-memory event is lost if the app crashes after commit.

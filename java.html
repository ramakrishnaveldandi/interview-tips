OOP & basics

What is the contract between equals() and hashCode()?
  • If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true.
  • Equal hash codes do not imply equality (collisions are allowed).
  • equals must be reflexive, symmetric, transitive, consistent, and x.equals(null) is false.

Overriding equals without hashCode breaks HashMap/HashSet: two "equal" keys land in different buckets.

🧠 How this works

  1. this == o is a cheap shortcut: an object is always equal to itself.
  2. instanceof rejects null and other types, so the cast on the next line can never throw ClassCastException.
  3. Two points are equal when both coordinates match, and Objects.hash(x, y) is built from exactly those same fields, so equal points always get equal hash codes.
  4. The class is final with final fields, so the hash can never change after the object is put in a HashSet/HashMap.
Use fields that never change in hashCode(). Mutating a key after inserting it into a HashMap makes it unreachable.
Why is String immutable, and what is the String pool?

The String pool (in the heap since Java 7) stores one copy of each literal. Immutability makes that sharing safe and also gives:

  • Security — class names, file paths, URLs and DB credentials cannot be changed after validation.
  • Thread safety — no synchronization needed.
  • Cached hash code — ideal as HashMap keys.

🧠 How this works

  1. String literals are interned at class-load time, so a and b point to the same pooled object and a == b is true.
  2. new String("java") always allocates a fresh heap object, so a == c compares two different references and is false (even though the text is equal).
  3. c.intern() returns the canonical pooled instance for that text, which is the same object as a, so the last line prints true.
  4. Lesson: == compares references; use equals() to compare text.
Use StringBuilder for concatenation in loops; it is mutable and not synchronized (StringBuffer is the synchronized legacy version).
What is the difference between == and equals()?

== compares references for objects (and values for primitives). equals() compares logical content as defined by the class — Object.equals defaults to ==.

🧠 How this works

  1. Integer x = 127 is autoboxed via Integer.valueOf(127), which returns a cached object for values -128..127.
  2. So x and y refer to the same cached object and x == y is true.
  3. 128 is outside the cache, so valueOf creates two separate objects and p == q is false.
  4. p.equals(q) compares the wrapped int values (128 vs 128), so it is true. Always use equals() for wrapper types.
Explain final, finally and finalize().
  • final — keyword: a final variable cannot be reassigned, a final method cannot be overridden, a final class cannot be extended.
  • finally — block that always runs after try/catch (unless the JVM exits), used for cleanup.
  • finalize() — Object method called by GC before reclaiming; unpredictable, deprecated since Java 9 and deprecated for removal since 18 (JEP 421). Use try-with-resources or java.lang.ref.Cleaner.

Is Java pass-by-value or pass-by-reference?

Always pass-by-value. For objects, the value passed is a copy of the reference. You can mutate the object through it, but reassigning the parameter does not affect the caller.

🧠 How this works

  1. Java copies the reference value into the parameter sb; caller variable s and sb now point to the same object.
  2. sb.append(" world") mutates that shared object, so the caller sees the change.
  3. sb = new StringBuilder("x") only re-points the local copy of the reference; s still points to the original object.
  4. Therefore the output is hello world: Java is always pass-by-value, and for objects the value passed is a reference.

Collections Framework: overview

What is the Java Collections Framework? Explain the interface hierarchy.

The Collections Framework (in java.util and java.util.concurrent) is a set of interfaces that describe data structures, implementations of those interfaces, and algorithms (sorting, searching, shuffling) in the Collections utility class. Programming to the interface (List<String> names = new ArrayList<>()) lets you swap implementations without changing the rest of your code.

🧠 How this works

  1. List, Set and Queue all extend Collection, which extends Iterable, so all of them work in a for-each loop.
  2. Java 21 inserted the Sequenced* interfaces for types with a defined encounter order, giving them getFirst(), getLast() and reversed().
  3. Map is a separate hierarchy because it stores key/value pairs; you iterate it through keySet(), values() or entrySet().
  • List — ordered by index, allows duplicates.
  • Set — no duplicates (decided by equals/hashCode, or by a comparator for sorted sets).
  • Queue / Deque — elements held for processing: FIFO, LIFO or by priority.
  • Map — unique keys mapped to values. It is part of the framework but does not extend Collection, because its basic unit is a pair, not a single element.

List: ArrayList, LinkedList, Vector, CopyOnWriteArrayList

How does ArrayList work internally? How does it grow?

ArrayList is a resizable array. It keeps an internal Object[] elementData and an int size.

  • Lazy allocation: new ArrayList<>() starts with a shared empty array. The first add allocates the default capacity of 10.
  • Growth: when the array is full, it creates a new array about 1.5× bigger (newCapacity = old + (old >> 1)) and copies the elements across with Arrays.copyOf. Because growth is proportional, add at the end is amortised O(1).
  • Access: get(i) is a direct array index — O(1). It implements the RandomAccess marker interface.
  • Insert / remove in the middle: elements after the index are shifted with System.arraycopy — O(n).
  • It never shrinks automatically; call trimToSize() to release unused capacity.
  • If you know the size in advance, use new ArrayList<>(expectedSize) or ensureCapacity(n) to avoid repeated copying.

🧠 How this works

  1. add(2, "X") inserts at index 2, so c and d are copied one slot right (an O(n) array copy) giving [a, b, X, c, d].
  2. remove("b") finds the first element equal to "b" (O(n) scan) and shifts the rest left, giving [a, X, c, d].
  3. get(1) is O(1) direct array access, so it returns X; indexOf("d") is 3 because indexes start at 0; contains("z") is false after a full scan.
How does LinkedList work, and when is it actually better than ArrayList?

LinkedList is a doubly linked list. Each element lives in a Node object with three references: item, prev and next. The list keeps references to first and last. It implements both List and Deque.

  • Adding or removing at the head or tail is O(1) — just relink nodes.
  • get(i) is O(n): it walks from the nearer end (the first half from first, the second from last).
  • Inserting "in the middle" is O(1) only if you are already there with a ListIterator; finding the position is O(n).
  • Memory: each element costs a whole node object (roughly 24–32 bytes of overhead), and nodes are scattered in memory, so iteration is cache-unfriendly.

  3. it.next() == 3 works because the Integer is unboxed when compared to the int literal 3.
  4. it.add(99) inserts right after 3 (before 4) by relinking nodes; the iterator then continues to 4 without visiting 99, so the result is [2, 3, 99, 4] and no ConcurrentModificationException is thrown.
What is the remove(int) vs remove(Object) trap in List<Integer>?

List has two overloads. With an int argument the compiler picks remove(int index) — no boxing is needed — so it removes by position, not by value.

🧠 How this works

  1. nums.remove(1): the compiler picks remove(int index) because an exact primitive match beats autoboxing, so it removes index 1 (the value 20) giving [10, 30, 1].
  2. Integer.valueOf(1) is an object, so remove(Object) is chosen; it removes the first element equal to 1, giving [10, 30].
Vector, Stack and Collections.synchronizedList vs CopyOnWriteArrayList — which thread-safe list should you use?
  • Vector (Java 1.0) is like ArrayList but every method is synchronized, and it grows by 2× instead of 1.5×. All threads contend on one lock, and compound actions ("check, then add") are still not atomic. Legacy — avoid.
  • Stack extends Vector (synchronized, and it exposes index methods a stack shouldn't have). Use ArrayDeque with push/pop instead.
  • Collections.synchronizedList(list) wraps any list with one lock. You must still lock manually while iterating, otherwise you can get ConcurrentModificationException.
  • CopyOnWriteArrayList makes a fresh copy of the array on every write. Reads need no lock, and iterators work on a snapshot, so they never throw ConcurrentModificationException. Writes are O(n) and generate garbage, so it suits read-mostly data: event listeners, configuration, plug-in registries.

🧠 How this works

  1. synchronizedList locks each single method call, but a for-each loop is many calls (hasNext/next), so you must hold the list's own lock for the whole loop yourself.
  2. CopyOnWriteArrayList iterators walk a snapshot of the array taken when the loop started (2 elements).
  3. Each add("sms") copies the array and appends, but the running loop still sees only the old 2-element snapshot, so it runs exactly twice: [audit, email, sms, sms].
  4. Writes cost O(n) copies, so COW suits read-mostly lists such as listeners.

Set: HashSet, LinkedHashSet, TreeSet, EnumSet

How does HashSet guarantee uniqueness? How do LinkedHashSet and TreeSet differ?
  • HashSet is backed by a HashMap: each element is stored as a key, with a dummy shared value (PRESENT). add(e) is map.put(e, PRESENT) == null, so uniqueness comes from the map's key rules — hashCode() picks the bucket, then equals() decides whether it's a duplicate. No ordering guarantee.
  • LinkedHashSet is backed by a LinkedHashMap: same O(1) operations, plus a doubly linked list through the entries, so iteration follows insertion order. Ideal for "remove duplicates but keep order".
  • TreeSet is backed by a TreeMap (red-black tree). Elements are kept sorted by natural order (Comparable) or a Comparator, operations are O(log n), and it adds navigation methods. Uniqueness is decided by compareTo/compare returning 0 — not by equals.
  • EnumSet stores enum constants as bits in a long (a bit vector) — extremely fast and compact. Use it instead of a HashSet of enums.

🧠 How this works

  1. Duplicates are dropped because add on a set ignores an element that is already equal to one present. HashSet order depends on hash buckets and is not guaranteed (it just happens to match here); LinkedHashSet keeps insertion order; TreeSet sorts, giving [apple, banana, cherry].
  2. In the sorted scores {40, 55, 62, 75, 90}: floor(60) is the greatest <= 60 (55), ceiling(60) the least >= 60 (62), and higher(90) must be strictly greater than 90, so it is null.
  3. headSet(62) excludes 62, tailSet(62) includes it, and descendingSet() is a reversed view.
  4. A TreeSet uses its comparator, not equals(), to detect duplicates: case-insensitively "JAVA" compares as 0 to "Java", so it is rejected and the first one stays.
  5. EnumSet.range is a bit-vector set that always iterates in enum declaration order.
Why must equals() and hashCode() be overridden together? What happens with a mutable key?

Hash-based collections first use hashCode() to find the bucket, then equals() to compare within it. The contract: equal objects must have equal hash codes. If you override only equals, two "equal" objects land in different buckets and the set keeps both. If a key's fields change after it was inserted, its hash code changes, and the map looks in the wrong bucket — the entry becomes unreachable (a memory leak).

🧠 How this works

  1. BadPoint overrides equals but inherits Object.hashCode(), which is identity-based, so the two equal points land in different buckets.
  2. HashSet only calls equals on entries in the same bucket, so it never notices the duplicate: size is 2.
  3. A record generates equals and hashCode from its components, so a new Point(1, 2) hashes to the same bucket and contains is true.
  4. For the mutable key, adding "b" changes the list's hashCode; get(key) now looks in a different bucket and returns null, while the stale entry is still stored, so size is 1.
Use immutable keys: String, boxed numbers, records with immutable fields, or enums.

Map: HashMap, LinkedHashMap, TreeMap and friends

Explain the internal working of HashMap in detail (hashing, buckets, collisions, resizing, treeification).

A HashMap is an array of buckets (Node<K,V>[] table). Each node holds hash, key, value and next.

  1. Hashing: put(k, v) computes h = k.hashCode(), then spreads it: hash = h ^ (h >>> 16). Mixing the high bits into the low bits matters because the index uses only the low bits.
  2. Index: index = (n - 1) & hash, where n (the table length) is always a power of two, so this is a fast replacement for hash % n.
  3. Empty bucket → a new node is placed there.
  4. Collision (bucket already used) → walk the chain: if a node has the same hash and equals the key, replace its value; otherwise append a new node to the end of the list.
  5. Treeification (Java 8+): when one bucket's chain reaches 8 nodes (TREEIFY_THRESHOLD) and the table has at least 64 buckets, the chain is converted to a red-black tree, making worst-case lookup O(log n) instead of O(n). If the table is smaller than 64, it resizes instead. A tree shrinks back to a list at 6 nodes.
  6. Resizing: default capacity 16, load factor 0.75 → when size > capacity × 0.75 (12 for the default) the table doubles. Because the size is a power of two, each node either stays at its index or moves to index + oldCapacity — decided by one bit of the hash — so no full rehash is needed.
  7. Nulls: one null key is allowed (its hash is 0, so it goes to bucket 0), and any number of null values.

🧠 How this works

  1. The bucket index is computed from the key's hash (spread as h ^ (h >>> 16)) AND (capacity - 1); a null key always goes to bucket 0.
  2. "Aa" and "BB" have the same hashCode, so they share a bucket and are chained; equals() tells them apart on lookup.
  3. When one bucket's chain reaches 8 entries (and the table has at least 64 slots) it is converted into a red-black tree, making worst-case lookups O(log n) instead of O(n).

🧠 How this works

  1. String hash is s[0]*31 + s[1]: 'A'(65)*31 + 'a'(97) = 2112 and 'B'(66)*31 + 'B'(66) = 2112, a real collision.
  2. "BB" goes into the same bucket as "Aa", but equals is false, so both entries are kept.
  3. put("Aa", 10) finds an equal key and replaces the value (returning the old value 1); size does not grow.
  4. HashMap allows one null key, so the map holds Aa, BB and null: output 10 2 0 3.
  5. HashMap.newHashMap(1000) picks a capacity big enough that 1000 entries fit under the 0.75 load factor, so no resizing happens while filling it.
HashMap is not thread-safe. Concurrent puts can lose entries or corrupt the structure (in Java 7, concurrent resizing could even create a cycle and an infinite loop). Use ConcurrentHashMap for shared maps.

How does LinkedHashMap work? How do you build an LRU cache with it?

LinkedHashMap extends HashMap and additionally threads a doubly linked list through all entries (each entry has before/after pointers). Lookups stay O(1), but iteration follows a predictable order:

  • Insertion order (default) — re-inserting an existing key does not change its position.
  • Access order (new LinkedHashMap<>(cap, 0.75f, true)) — every get/put moves the entry to the end, so the first entry is the least recently used.

Overriding removeEldestEntry turns it into a bounded LRU cache. Since Java 21 it also implements SequencedMap: firstEntry(), lastEntry(), pollFirstEntry(), reversed(), putFirst().

🧠 How this works

  1. The third constructor argument true switches to access order: every get/put moves that entry to the end of the internal linked list.
  2. After inserting a, b, c the order is a, b, c; get("a") moves a to the end, so the order is b, c, a.
  3. put("d") makes size 4; removeEldestEntry is called after the insert, returns true, and the head (b, the least recently used) is evicted: {c=3, a=1, d=4}.
  4. The second map uses the default insertion order; Java 21 firstEntry(), lastEntry() and reversed() come from SequencedMap.
How does TreeMap work, and what navigation methods does it offer?

TreeMap is a red-black tree — a self-balancing binary search tree. Keys are kept sorted by their natural order or by a Comparator passed to the constructor. get, put and remove are O(log n). It implements NavigableMap, which makes it ideal for "nearest", "range" and "ranking" questions.

  • No null keys with natural ordering (compareTo(null) throws NullPointerException); null values are fine.
  • The comparator should be consistent with equals; keys that compare as 0 are treated as the same key.
  • Typical uses: price/tax slabs, time-series lookups ("value at or before time T"), leaderboards, scheduling.

🧠 How this works

  1. Keys are kept sorted in a red-black tree, so every navigation call is O(log n).
  2. floorEntry(850_000) gives the greatest key <= 850000, i.e. the 700000 slab with 10%; ceilingKey gives the next slab start, 1000000.
  3. headMap(k) excludes k, tailMap(k, true) includes it, and subMap(from, to) is from-inclusive, to-exclusive, which is why 1000000 is not in the subMap output.
  4. The custom comparator sorts by length descending, then alphabetically, giving kotlin(6), scala(5), java(4), go(2). Keys that compare as 0 would be treated as duplicates.

What are WeakHashMap, IdentityHashMap and EnumMap used for?
  • WeakHashMap holds its keys through weak references. When a key is no longer strongly referenced anywhere else, the garbage collector may reclaim it and the entry disappears automatically. It's used to attach metadata to objects you don't own without causing a memory leak. Caveats: string literals and small boxed integers are cached by the JVM and never collected; for real caches use Caffeine.
  • IdentityHashMap compares keys with == (reference identity) and System.identityHashCode instead of equals/hashCode. It's used in serialisation and deep-copy algorithms to track "objects already visited". It deliberately breaks the general Map contract.
  • EnumMap stores values in an array indexed by the enum's ordinal(): very fast, compact, and iterated in enum declaration order. Always prefer it over HashMap for enum keys.

🧠 How this works

  1. k1 and k2 are equal strings but different objects. IdentityHashMap compares keys with ==, so it stores both: size 2.
  2. A normal HashMap uses equals(), so looking up k2 finds the entry stored under k1: true.
  3. EnumMap is backed by an array indexed by ordinal(), so it always prints in declaration order (NEW before SHIPPED) no matter the insertion order.

ConcurrentHashMap & HashMap vs ConcurrentHashMap

How does ConcurrentHashMap work internally (Java 7 vs Java 8+)?

Java 7 used lock striping: the map was divided into 16 segments (by default), each a small hash table guarded by its own ReentrantLock. Up to 16 threads could write at once — one per segment.

Java 8+ redesigned it completely (segments are gone; concurrencyLevel is now only a sizing hint):

  1. Same layout as HashMap: a volatile array of bins holding nodes, with long bins converted to trees (TreeBin).
  2. Reads are lock-free: get() uses volatile reads, so it never blocks, even while other threads are writing.
  3. Inserting into an empty bin uses a CAS (compare-and-swap) — no lock at all.
  4. Writing to a non-empty bin locks only that bin, by synchronized on the bin's first node. Threads writing to different bins never block each other, so concurrency is effectively "number of bins", not 16.
  5. Resizing is cooperative: when the table grows, other threads that try to write help transfer bins to the new table. Moved bins are marked with a ForwardingNode, so readers know to look in the new table.
  6. Size counting uses a baseCount plus an array of CounterCells (the same idea as LongAdder), so many threads can increment the count without contending on one variable. size() is therefore an estimate while updates are in flight; mappingCount() returns a long.

🧠 How this works

  1. An empty bin is filled with a lock-free CAS (compare-and-swap); if two threads race, one CAS fails and that thread retries.
  2. A non-empty bin is locked by synchronizing on its first node only, so threads writing to different bins (B and C) never block each other.
  3. Reads use volatile reads of the table and nodes, so get never takes a lock and always sees a fully published node.

Is every operation on a ConcurrentHashMap safe? Explain the check-then-act problem.

Each individual method is atomic, but a sequence of calls is not. Between containsKey and put, another thread can insert the same key — a race condition even with a thread-safe map. Use the atomic compound methods instead.

🧠 How this works

  1. Each single CHM call is atomic, but containsKey followed by put is two calls: two threads can both see "absent" and both open a connection.
  2. computeIfAbsent does the check and insert as one atomic step, running the function at most once per key (keep that function short; it runs while the bin is locked).
  3. Same for counting: get then put can lose increments, while merge(word, 1, Integer::sum) is atomic.
  4. replace(word, 5, 6) changes the value only if it is still 5, the same idea as CAS on an AtomicInteger.
  • Keep the function passed to compute*/merge short and never modify the same map inside it — the bin stays locked while it runs (doing so can throw IllegalStateException: Recursive update).
  • Operations spanning several keys (e.g. transfer from key A to key B) are not atomic; you need external locking or a different design.
  • For high-contention counters, store LongAdder values: map.computeIfAbsent(k, x -> new LongAdder()).increment().

Explain the Queue and Deque method families. Why prefer ArrayDeque?

Each operation exists in two forms: one throws an exception on failure, the other returns a special value (false/null).

A Deque (double-ended queue) adds offerFirst/offerLast, pollFirst/pollLast, peekFirst/peekLast, and stack methods push/pop.

ArrayDeque is a resizable circular array with head and tail indices: O(1) at both ends, no per-element node objects, no synchronization. It is faster than Stack (synchronized) for stacks and faster than LinkedList for queues. It does not allow null (because null is the "empty" signal from poll).

🧠 How this works

  1. push adds to the head, so after a, b, c the deque is [c, b, a]; pop removes the head (c), and peek looks at the new head (b) without removing it, leaving [b, a].
  2. offer adds to the tail and poll removes from the head, so a queue returns items in FIFO order: first, then second.
  3. The third poll() on an empty queue returns null instead of throwing (remove() would throw NoSuchElementException).
How does PriorityQueue work?

PriorityQueue is a binary min-heap stored in an array: the smallest element (by natural order or a Comparator) is always at the head. offer and poll are O(log n) (sift up / sift down); peek is O(1). It's used for scheduling, Dijkstra's algorithm, merging sorted streams and "top K" problems.

Iterating or printing a PriorityQueue does not give sorted order — only repeated poll() does. It is not thread-safe; use PriorityBlockingQueue for that.

🧠 How this works

  1. A PriorityQueue is a binary min-heap: poll() always removes the smallest element in O(log n), so draining gives sorted order [3, 7, 19, 25, 42] (printing the queue directly would not be sorted).
  2. For the top 3, keep a min-heap of size 3: after each offer, if size exceeds 3, drop the smallest. What remains are the 3 largest (12, 9, 8). Time O(n log k), space O(k).
  3. The heap is copied to a TreeSet only to print it in descending order.
  4. The reversed comparator turns it into a max-heap on priority, so outage (10) comes out first.

Fail-fast vs fail-safe (weakly consistent) iterators — how do they work?
  • Fail-fast (ArrayList, HashMap, …): the collection keeps a modCount that increases on every structural change. The iterator records it at creation and checks it on each next(); if it differs, it throws ConcurrentModificationException. This is a best-effort bug detector, not a thread-safety guarantee — it also fires in a single thread.
  • Fail-safe / weakly consistent (CopyOnWriteArrayList, ConcurrentHashMap, concurrent queues): iterate over a snapshot or tolerate concurrent changes, so they never throw ConcurrentModificationException; they may or may not show changes made after the iterator was created.

🧠 How this works

  1. nums.remove(n) (with an Integer, so remove(Object)) changes modCount when it removes 2; the hidden iterator's next next() detects this and throws CME.

  4. Fail-fast detection is best-effort, not a thread-safety mechanism.

Checked vs unchecked exceptions?

What does volatile guarantee — and what doesn't it?

🧠 How this works

  1. Writing a volatile field makes the new value visible to other threads, so the worker loop reading running sees false soon after stop() is called and exits.
  2. Without volatile, the JIT may hoist the read out of the loop and spin forever.

What is a deadlock and how do you prevent it?

Two or more threads wait forever for locks held by each other. Required conditions: mutual exclusion, hold-and-wait, no preemption, circular wait.

🧠 How this works

  1. A deadlock needs a circular wait: thread 1 locks A then waits for B while thread 2 locks B then waits for A.
  2. Here both threads compute the same order (lower id first) no matter which direction the transfer goes, so they always lock in the same sequence and a cycle is impossible.
  3. The second thread simply waits on the first lock until the first thread finishes both blocks. This assumes account ids are unique.

Other techniques: tryLock with timeout, minimise lock scope, prefer higher-level concurrency utilities. Detect with jstack <pid> ("Found one Java-level deadlock").

How do you size a thread pool?
  • CPU-bound (hashing, image processing): threads ≈ cores (or cores + 1). More threads only add context switches.
  • I/O-bound (Brian Goetz's formula): threads = cores × target utilisation × (1 + wait time / compute time). E.g. 8 cores, task waits 90 ms and computes 10 ms → 8 × 1 × (1 + 9) = 80 threads.
  • The real limit is often a downstream resource: no point running 200 threads against a 20-connection DB pool.
  • Measure under load (queue size, active count, latency percentiles), then tune. Or for I/O-bound work on Java 21+, use virtual threads and limit only the scarce resource.

🧠 How this works

  1. availableProcessors() returns the CPUs the JVM may use, and respects container CPU limits, so it is the starting point for sizing.
  2. For CPU-bound work use about that many threads; for I/O-bound work use more, roughly cores × (1 + wait time / compute time).
execute() vs submit() — where do exceptions go?
  • execute(Runnable): an exception kills the worker thread (the pool replaces it) and goes to the thread's UncaughtExceptionHandler — you see a stack trace.
  • submit(...): the exception is captured in the Future. If nobody calls get(), it is silently swallowed — a very common production bug.

🧠 How this works

  1. With submit, the thrown exception is captured inside the Future instead of reaching the thread's uncaught-exception handler, so nothing is logged unless you call get.
  2. get rethrows it wrapped in ExecutionException; getCause() is the original IllegalStateException.
  3. On timeout, cancel(true) interrupts the worker; on InterruptedException we restore the interrupt flag so callers can still see it.
  4. Java 19 added state() and exceptionNow() to inspect a completed future without the try/catch.

🧠 How this works

  1. shutdown() rejects new tasks but lets running and queued ones finish; awaitTermination waits up to 30 s for that.

What is ForkJoinPool and work stealing? How is it different from ThreadPoolExecutor?

Each ForkJoinPool worker has its own double-ended queue. A task fork()s subtasks onto its own deque (LIFO, cache-friendly); idle workers steal from the tail of other workers' deques (FIFO). This suits recursive divide-and-conquer work. ThreadPoolExecutor has one shared queue and suits independent tasks.

🧠 How this works

  1. If the range has at most 10,000 elements, the task sums it directly; otherwise it splits the range in half (>>> 1 avoids int overflow when computing the midpoint).
  2. left.fork() pushes the left half onto this worker's deque, where idle workers can steal it; the right half is computed directly on the current thread.
  3. left.join() waits for (or runs) the left half, and the two partial sums are added.
  4. Total work is O(n); with P workers the time is about O(n / P + log n). The threshold avoids creating too many tiny tasks.
Parallel streams and CompletableFuture's default use the common pool. Virtual threads are also scheduled by a dedicated ForkJoinPool of carrier threads.
What goes wrong with ThreadLocal in thread pools, and how do you propagate context (e.g. MDC, security)?

Pool threads live forever, so a ThreadLocal that is set but not removed leaks into the next task (user A's tenant ID seen by user B) and retains memory. Always clear it in finally, and copy context explicitly when handing work to another thread.

🧠 How this works

  1. MDC is backed by a ThreadLocal, so a pool worker does not see the submitter's values (and may see leftovers from a previous task).
  2. withMdc copies the context on the submitting thread at wrap time.
  3. Inside the worker it saves the worker's current context, installs the captured one, runs the task, and in finally restores the previous context, so nothing leaks to the next task on that thread.
Spring offers TaskDecorator for ThreadPoolTaskExecutor, and DelegatingSecurityContextExecutorService for the security context. With virtual threads on Java 25, prefer ScopedValue — immutable and automatically scoped.

What is a virtual thread and how does it work internally?

A virtual thread is a java.lang.Thread managed by the JVM, not the OS. Many virtual threads are multiplexed onto a small pool of carrier platform threads (a ForkJoinPool, parallelism = CPU count by default).

  • When a virtual thread blocks on I/O, sleep, a lock or a BlockingQueue, the JVM unmounts it: its stack frames are copied to the heap as a continuation, and the carrier is free to run another virtual thread.
  • When the I/O completes, the virtual thread is mounted again on any free carrier and continues.
  • Cost: a few hundred bytes to a few KB of heap that grows as needed, versus ~1 MB reserved stack for a platform thread. Millions are practical.

🧠 How this works

  1. Virtual threads are ordinary Java objects on the heap, so millions can exist; only a few carrier (platform) threads, by default about one per core, actually run them.
  2. When a virtual thread blocks on I/O or sleep, its stack is saved to the heap and the carrier is freed to run another virtual thread.
  3. When the I/O completes, the virtual thread is scheduled again, possibly on a different carrier.
Virtual threads improve throughput (more concurrent requests), not the latency of a single request. They make the simple blocking, thread-per-request style scale like reactive code.

🧠 How this works

What is pinning? What changed in Java 24/25?

A virtual thread is pinned when it cannot unmount while blocking, so it holds its carrier thread hostage. With few carriers, a handful of pinned threads can stall the whole application.

  • Java 21–23: blocking inside a synchronized block/method pinned the thread. Advice was to replace synchronized with ReentrantLock around blocking calls.
  • Java 24+ (JEP 491): virtual threads can acquire, hold and release monitors independently of their carrier, so synchronized no longer pins. On Java 25 you don't need to rewrite synchronized code.
  • Still pins: blocking while a native method or foreign (FFM) call is on the stack, and some class-initialization cases.
  • Detect: the JFR event jdk.VirtualThreadPinned (the old -Djdk.tracePinnedThreads flag was removed in Java 24).

🧠 How this works

  1. The first command starts the app with Java Flight Recorder enabled and writes events to app.jfr.
  2. jfr print --events jdk.VirtualThreadPinned lists each time a virtual thread could not unmount from its carrier while blocking, with stack traces showing where.
  3. Since Java 24 (JEP 491), synchronized no longer pins; remaining causes include native code/JNI frames.
Why must you not pool virtual threads? How do you limit concurrency instead?

Pools exist to amortise the cost of expensive threads. Virtual threads are cheap, so pooling adds nothing — and a fixed pool of virtual threads silently reintroduces the throughput cap you wanted to remove. Instead, create one per task and limit the scarce resource with a Semaphore.

🧠 How this works

  1. A fixed pool of 50 virtual threads only runs 50 tasks at a time, throwing away the main benefit of virtual threads.
  2. Instead, create one virtual thread per task and protect the scarce resource with a Semaphore of 20 permits.
  3. acquire() blocks (cheaply, on a virtual thread) once 20 calls are in flight; release() in finally returns the permit even if the call throws, so permits never leak.
ThreadLocal vs ScopedValue (final in Java 25) — why does it matter for virtual threads?

ThreadLocal is mutable, unbounded in lifetime (until remove()), and costly when inherited by millions of threads. ScopedValue (JEP 506) is immutable, bound only for the duration of a call, and cheap to share with child threads in structured concurrency.

🧠 How this works

  1. ScopedValue.newInstance() creates a key; where(USER, value).run(...) binds the value only for the duration of that run call.
  2. Any code called inside run, however deep, reads it with USER.get(); when run returns the binding disappears automatically, so nothing needs cleaning up (unlike ThreadLocal.remove()).
  3. The value is immutable for the scope, and child threads forked in a StructuredTaskScope inherit it cheaply.
  4. get() throws NoSuchElementException when unbound, so orElse is the safe read.
What is structured concurrency (preview in Java 25)? Show an example.

StructuredTaskScope (JEP 505, 5th preview) treats a group of subtasks as one unit: they are forked inside a scope, the scope waits for them, and if one fails the others are cancelled. No leaked threads, and thread dumps show the parent–child relationship.

🧠 How this works

  1. StructuredTaskScope.open() creates a scope whose default policy needs all subtasks to succeed; each fork starts a subtask in a new virtual thread.
  2. scope.join() waits for both; if one fails, the other is cancelled and join throws FailedException.
  3. After a successful join, user.get() and orders.get() return results, and leaving the try block guarantees no subtask outlives the method.
  4. With anySuccessfulResultOrThrow, the first mirror to succeed wins, the others are cancelled, and join() returns that result.
The API changed between previews (Java 21–24 used new StructuredTaskScope.ShutdownOnFailure()); in interviews, mention that it is still preview in 25.

When should you NOT use virtual threads?
  • CPU-bound work — there are only ~#cores carriers; use a fixed platform pool or parallel streams.
  • Low concurrency — if you only ever run 20 tasks at a time, a small platform pool is equally good.
  • Already-reactive code (WebFlux/Netty event loops) — there is no blocking to hide.
  • Heavy native / JNI blocking — pins carriers.
  • Tasks that rely on thread priority or on pooled-thread ThreadLocal caches (e.g. expensive objects cached per thread).

JVM internals

Describe the JVM memory areas.
  • Heap — all objects; shared; managed by GC (young gen: Eden + survivors, old gen).
  • Metaspace (Java 8+, replaced PermGen) — class metadata in native memory.
  • Stack — one per thread: frames with local variables and partial results. Overflow → StackOverflowError.
  • PC register and native method stack — per thread.
  • Code cache — JIT-compiled native code.

🧠 How this works

  1. -Xms512m/-Xmx2g set the initial and maximum heap; -XX:MaxMetaspaceSize caps class metadata, which lives in native memory outside the heap.
  2. -Xss1m sets each thread's stack size; deep recursion beyond it causes StackOverflowError.
  3. -XX:+HeapDumpOnOutOfMemoryError writes a heap dump when the heap runs out, so you can find the leak afterwards.
How does class loading work? What is the parent delegation model?

Phases: Loading → Linking (verify, prepare, resolve) → Initialization (static initializers run on first active use).

Loaders: Bootstrap (core java.base) → Platform → Application/System (classpath). A loader first delegates to its parent and only loads the class itself if the parent cannot, which prevents user code from replacing java.lang.String. Application servers and Spring Boot's fat-jar loader add custom loaders.

How does garbage collection work at a high level?

GC finds objects unreachable from GC roots (stack locals, static fields, JNI refs, active threads) and reclaims them. The generational hypothesis — most objects die young — means new objects go to Eden; survivors are copied between survivor spaces and promoted to the old generation after several cycles.

  • Minor GC — young gen, frequent and fast.
  • Major/Full GC — old gen / whole heap, expensive.
  • Collectors: Serial, Parallel, G1 (default since Java 9), ZGC, Shenandoah.
Memory leaks in Java are objects that are still reachable but no longer needed — e.g. growing static maps, unremoved listeners, ThreadLocals in pooled threads.

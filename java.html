OOP & basics

What is the contract between equals() and hashCode()?
  • If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true.
  • Equal hash codes do not imply equality (collisions are allowed).
  • equals must be reflexive, symmetric, transitive, consistent, and x.equals(null) is false.

Overriding equals without hashCode breaks HashMap/HashSet: two "equal" keys land in different buckets.

🧠 How this works

  1. this == o is a cheap shortcut: an object is always equal to itself.
  2. instanceof rejects null and other types, so the cast on the next line can never throw ClassCastException.
  3. Two points are equal when both coordinates match, and Objects.hash(x, y) is built from exactly those same fields, so equal points always get equal hash codes.
  4. The class is final with final fields, so the hash can never change after the object is put in a HashSet/HashMap.
Use fields that never change in hashCode(). Mutating a key after inserting it into a HashMap makes it unreachable.
Why is String immutable, and what is the String pool?

The String pool (in the heap since Java 7) stores one copy of each literal. Immutability makes that sharing safe and also gives:

  • Security — class names, file paths, URLs and DB credentials cannot be changed after validation.
  • Thread safety — no synchronization needed.
  • Cached hash code — ideal as HashMap keys.

🧠 How this works

  1. String literals are interned at class-load time, so a and b point to the same pooled object and a == b is true.
  2. new String("java") always allocates a fresh heap object, so a == c compares two different references and is false (even though the text is equal).
  3. c.intern() returns the canonical pooled instance for that text, which is the same object as a, so the last line prints true.
  4. Lesson: == compares references; use equals() to compare text.
Use StringBuilder for concatenation in loops; it is mutable and not synchronized (StringBuffer is the synchronized legacy version).
What is the difference between == and equals()?

== compares references for objects (and values for primitives). equals() compares logical content as defined by the class — Object.equals defaults to ==.

🧠 How this works

  1. Integer x = 127 is autoboxed via Integer.valueOf(127), which returns a cached object for values -128..127.
  2. So x and y refer to the same cached object and x == y is true.
  3. 128 is outside the cache, so valueOf creates two separate objects and p == q is false.
  4. p.equals(q) compares the wrapped int values (128 vs 128), so it is true. Always use equals() for wrapper types.
Explain final, finally and finalize().
  • final — keyword: a final variable cannot be reassigned, a final method cannot be overridden, a final class cannot be extended.
  • finally — block that always runs after try/catch (unless the JVM exits), used for cleanup.
  • finalize() — Object method called by GC before reclaiming; unpredictable, deprecated since Java 9 and deprecated for removal since 18 (JEP 421). Use try-with-resources or java.lang.ref.Cleaner.

Is Java pass-by-value or pass-by-reference?

Always pass-by-value. For objects, the value passed is a copy of the reference. You can mutate the object through it, but reassigning the parameter does not affect the caller.

🧠 How this works

  1. Java copies the reference value into the parameter sb; caller variable s and sb now point to the same object.
  2. sb.append(" world") mutates that shared object, so the caller sees the change.
  3. sb = new StringBuilder("x") only re-points the local copy of the reference; s still points to the original object.
  4. Therefore the output is hello world: Java is always pass-by-value, and for objects the value passed is a reference.

What is the difference between static and instance members?
  • static (class level): one copy per class, shared by all instances. Initialised when the class is initialised. Accessed as ClassName.member. A static method has no this, so it cannot touch instance fields directly.
  • Instance (object level): each object has its own copy. Needs an object reference. Instance methods can use both instance and static members.
  • Static methods are not polymorphic: they are bound at compile time and can only be hidden, not overridden.

🧠 How this works

  1. Each new Counter() increments the single shared total and stores the current value in that object's own id: c1.id is 1, c2.id is 2.
  2. When c1.describe() runs, it reads its own id (1) but the shared total, which is already 2 after c2 was created, so it prints "Counter #1 of 2".
  3. getTotal() is static, so it is called on the class and can only read static state; writing id inside it would not compile.
Mutable static state is shared by every thread, so total++ here is not thread-safe (use AtomicInteger). Static fields are also a common cause of memory leaks, because they live as long as the class is loaded.
this() vs super() in constructors — how does constructor chaining work?
  • this(...) calls another constructor of the same class, so initialisation code lives in one place.
  • super(...) calls a constructor of the parent class. If you write neither, the compiler inserts super(); if the parent has no no-arg constructor, that is a compile error.
  • Before Java 25 both had to be the first statement, so a constructor can use one or the other, never both. Java 25 (JEP 513, flexible constructor bodies) allows statements such as argument validation before the call, as long as they do not read the object being built (no this.method(), no reading fields; assigning its fields is allowed).
  • Parent constructors always finish before the child's constructor body continues.

🧠 How this works

  1. new Car("Tesla") enters the one-argument constructor, whose first action is this("Tesla", 0).
  2. The two-argument constructor immediately calls super(0), so Vehicle(0) runs and prints first.
  3. Control returns to Car(String, int), which sets brand and prints Car(Tesla, 0).
  4. Finally the rest of Car(String) runs and prints Car(Tesla): construction always goes parent first, then back down the chain.
Composition vs inheritance — why is "favor composition over inheritance" the usual advice?
  • Inheritance ("is-a"): the subclass depends on the parent's implementation, not just its API. A change in the parent, or an internal self-call you did not know about, can break the subclass (the fragile base class problem). Java allows only one superclass.
  • Composition ("has-a"): the class holds a reference to another object and delegates to it. It depends only on the public API, can swap the implementation at runtime (strategy pattern), and is easy to mock in tests.
  • Use inheritance only for a genuine "is-a" relationship where the parent was designed for extension (Effective Java, Item 18: "Favor composition over inheritance").

🧠 How this works

  1. CountingSet.addAll adds 3 to the counter and then calls super.addAll.
  2. HashSet inherits addAll from AbstractCollection, which calls add() for each element. Because of dynamic dispatch that is our overridden add, which counts each element again: 3 + 3 = 6.
  3. The composed version calls delegate.addAll; the delegate's internal calls to its own add never reach our wrapper, so the count is the correct 3.
  4. The subclass was broken by an implementation detail of its parent that is not part of the API. Composition depends only on the API, so it does not have this problem.
What is a covariant return type?

Since Java 5, an overriding method may declare a return type that is a subtype of the overridden method's return type. Callers that know the subclass get the more specific type without a cast. This works only for reference types; primitive return types must match exactly.

🧠 How this works

  1. Dog.copy() returns Dog while Animal.copy() returns Animal; it is still a valid override because Dog is an Animal.
  2. Through a Dog reference the compiler sees the return type Dog, so d.copy().bark() compiles without a cast.
  3. Through an Animal reference the static type is Animal, but dispatch still runs Dog.copy(), so the runtime class is Dog.
  4. Under the hood javac generates a synthetic bridge method Animal copy() in Dog that calls the Dog version.

Common uses: clone() overrides returning the concrete type, fluent builders in class hierarchies, and factory methods.

Can you override a private or static method? What does this code print?
  • private methods cannot be overridden: they are not visible to subclasses. A method with the same signature in the subclass is a brand-new method; putting @Override on it is a compile error.
  • static methods cannot be overridden, only hidden: the method that runs is chosen from the reference type at compile time, not from the object.
  • final methods cannot be overridden or hidden at all.

🧠 How this works

  1. p.greet(): greet is static, so the compiler binds it to the declared type of p, which is Parent. The object being a Child does not matter (IDEs warn that a static method is called through an instance).
  2. p.callSecret(): inside Parent, the call to the private secret() is bound directly to Parent.secret; Child.secret is an unrelated method that just happens to share the name.
  3. p.hello() is a normal instance method, so dynamic dispatch picks Child.hello.
  4. Child.greet() names the class explicitly, so the hiding method in Child runs.
Shallow copy vs deep copy — what is the difference?
  • Shallow copy: a new outer object whose fields are copied as-is. Reference fields still point to the same nested objects, so mutating a nested object is visible through both. Object.clone(), new ArrayList<>(list) and List.copyOf are all shallow.
  • Deep copy: nested mutable objects are copied too, so the copy is fully independent.
  • Ways to deep copy: copy constructors or static factory methods (preferred), a mapper such as MapStruct, or serialize/deserialize (slow, and the class must be Serializable). Immutable nested objects (String, records of immutable values, LocalDate) never need copying.

🧠 How this works

  1. super.clone() copies each field value. For address that value is a reference, so shallow and original share one Address: changing its city to Delhi shows up in original.
  2. deepCopy() builds a new Address with the copy constructor, so deep keeps "Pune" and the references are not ==.
  3. shallow.name = "Bob" re-points the copy's own field; it does not change the shared object, so original.name stays "Ann". Shallow copies only leak mutations of nested objects.
  4. new ArrayList<>(list) copies the list but not the arrays inside it, so writing 99 is visible in the original. Cloning each array (int[]::clone) gives independent arrays, so writing -1 to the deep copy leaves 99 untouched.
Effective Java (Item 13) advises avoiding Cloneable/clone(): it is a shallow copy by default, bypasses constructors and works badly with final fields. Prefer copy constructors, or make nested objects immutable so a shallow copy is enough.
What are autoboxing and unboxing? What are the pitfalls and performance costs?

Autoboxing converts a primitive to its wrapper automatically (the compiler inserts Integer.valueOf(5)); unboxing converts back (it inserts intValue()). It happens on assignment, method calls, arithmetic, and whenever primitives go into collections or generics.

  • NPE on unboxing null — e.g. int qty = map.get(key) when the key is missing, or a ternary that mixes int and Integer.
  • == on wrappers compares references. Integer.valueOf caches -128..127 (the upper bound can be raised with -XX:AutoBoxCacheMax), so == "works" for small values and fails for larger ones.
  • Performance — boxing in a hot loop allocates objects and adds GC pressure; boxed collections use far more memory than primitive arrays. Use primitives, IntStream/LongStream, or primitive arrays in hot paths.
  • Overload surprises — List<Integer>.remove(0) removes by index, not by value.
  • The wrapper constructors (new Integer(5)) are deprecated for removal since Java 16; use Integer.valueOf or plain autoboxing.

🧠 How this works

  1. 127 is inside the Integer cache, so a and b are the same object; 128 is outside it, so c and d are two objects and == is false even though equals is true.
  2. stock.get("apple") returns null; assigning it to an int makes the compiler call null.intValue(), which throws NullPointerException. Use getOrDefault(key, 0).
  3. slow += i on a Long means unbox, add, then box a new Long on every iteration. Both totals are correct (499500), but the boxed loop does far more allocation.
  4. remove(Integer.valueOf(10)) removes the value 10; remove(0) uses the exact int overload and removes index 0 (the value 20), leaving [30].
  5. In flag ? 1 : x one operand is a primitive int, so the whole expression has type int and x is unboxed; with x == null that throws an NPE.
What is pattern matching for instanceof (Java 16), and how does it lead to pattern matching in switch?

Pattern matching for instanceof (preview in 14 and 15, final in Java 16, JEP 394) tests the type and binds a typed variable in one step, so the separate cast disappears.

  • No redundant cast, so there is no chance of casting to the wrong type.
  • The binding variable is in scope only where the match is certain (flow scoping): after &&, inside the if, or after an early return on !(x instanceof T t).
  • It was the first step towards pattern matching for switch and record patterns (both final in Java 21).

🧠 How this works

  1. "interview" matches String s and is longer than 5, so s is used directly as a String without a cast.
  2. "hi" fails the length check, then fails instanceof Integer, so the negated test returns "not an integer".
  3. For 21 the negated test is false, so execution continues and the compiler knows n is definitely bound after the if; that is why n * 2 compiles.
  4. In area, the switch matches on type; because Shape is sealed with exactly two implementations, the switch is exhaustive without a default. Square(double side) is a record pattern that pulls out the component directly.

equals() vs equalsIgnoreCase() vs compareTo() for strings?
  • equals(Object) — true if the content is identical, character by character. Case-sensitive. Returns false (never throws) for null.
  • equalsIgnoreCase(String) — same, but ignores upper/lower case.
  • compareTo(String) — lexicographic ordering: 0 if equal, negative if this string sorts first, positive if it sorts after. It compares UTF-16 char values, so all upper-case letters sort before lower-case. If one string is a prefix of the other, the result is the length difference. Throws NullPointerException for null.
  • compareToIgnoreCase / String.CASE_INSENSITIVE_ORDER — case-insensitive ordering. For human-language sorting (accents, locale rules) use java.text.Collator.

🧠 How this works

  1. "Hello".compareTo("hello") stops at the first differing character: 'H' (72) minus 'h' (104) = -32.
  2. "apple" vs "banana": 'a' (97) − 'b' (98) = -1. "app" is a prefix of "apple", so the result is the length difference 3 − 5 = -2.
  3. Natural (compareTo) order puts "Alice" and "Dave" first because upper-case letters have smaller char values than lower-case ones; CASE_INSENSITIVE_ORDER gives the alphabetical order people expect.
  4. Writing the literal first ("yes".equals(input)) is null-safe: it returns false instead of throwing. Objects.equals(a, b) is null-safe on both sides.
Only rely on the sign of compareTo, never on the exact number; the -32 and -2 are implementation details.

How does string concatenation work under the hood? Why is += in a loop slow?
  • Compile-time constants are folded: "Hello" + " " + "World" (and expressions using static final String constants) become one literal in the class file, so the result is the interned pool string.
  • Runtime concatenation, Java 5–8: javac translated a + b + c into new StringBuilder().append(a).append(b).append(c).toString().
  • Java 9+ (JEP 280): javac emits an invokedynamic call to StringConcatFactory, and the JVM generates an optimised strategy at runtime (pre-sizing the result, avoiding extra copies). You get faster code without recompiling when the JVM improves.
  • Loops are still slow: each result += s is a separate expression that creates a new String and copies everything built so far, so n iterations cost O(n²) character copies, on every Java version. Use one StringBuilder for the whole loop, or String.join/Collectors.joining.

🧠 How this works

  1. b is made only of literals, so the compiler folds it into the literal "Hello World", the same pooled object as a: a == b is true.
  2. GREETING is a static final String initialised with a literal, which makes it a constant variable; c is folded the same way, so a == c is also true.
  3. w is a normal (non-final) variable, so d is built at runtime into a new heap object: == is false, while equals is true.
  4. The loop appends into one growing buffer (amortised O(n) total), and setLength removes the last comma; String.join does the same job in one call.

Collections Framework: overview

A detailed tour of the Java Collections Framework — how each implementation works internally, its complexity, and when to choose it. Code outputs shown with // => are real results from Java 25.

What is the Java Collections Framework? Explain the interface hierarchy.

The Collections Framework (in java.util and java.util.concurrent) is a set of interfaces that describe data structures, implementations of those interfaces, and algorithms (sorting, searching, shuffling) in the Collections utility class. Programming to the interface (List<String> names = new ArrayList<>()) lets you swap implementations without changing the rest of your code.

🧠 How this works

  1. List, Set and Queue all extend Collection, which extends Iterable, so all of them work in a for-each loop.
  2. Java 21 inserted the Sequenced* interfaces for types with a defined encounter order, giving them getFirst(), getLast() and reversed().
  3. Map is a separate hierarchy because it stores key/value pairs; you iterate it through keySet(), values() or entrySet().
  • List — ordered by index, allows duplicates.
  • Set — no duplicates (decided by equals/hashCode, or by a comparator for sorted sets).
  • Queue / Deque — elements held for processing: FIFO, LIFO or by priority.
  • Map — unique keys mapped to values. It is part of the framework but does not extend Collection, because its basic unit is a pair, not a single element.

How does ArrayList work internally? How does it grow?

ArrayList is a resizable array. It keeps an internal Object[] elementData and an int size.

  • Lazy allocation: new ArrayList<>() starts with a shared empty array. The first add allocates the default capacity of 10.
  • Growth: when the array is full, it creates a new array about 1.5× bigger (newCapacity = old + (old >> 1)) and copies the elements across with Arrays.copyOf. Because growth is proportional, add at the end is amortised O(1).
  • Access: get(i) is a direct array index — O(1). It implements the RandomAccess marker interface.
  • Insert / remove in the middle: elements after the index are shifted with System.arraycopy — O(n).
  • It never shrinks automatically; call trimToSize() to release unused capacity.
  • If you know the size in advance, use new ArrayList<>(expectedSize) or ensureCapacity(n) to avoid repeated copying.

🧠 How this works

  1. add(2, "X") inserts at index 2, so c and d are copied one slot right (an O(n) array copy) giving [a, b, X, c, d].
  2. remove("b") finds the first element equal to "b" (O(n) scan) and shifts the rest left, giving [a, X, c, d].
  3. get(1) is O(1) direct array access, so it returns X; indexOf("d") is 3 because indexes start at 0; contains("z") is false after a full scan.
How does LinkedList work, and when is it actually better than ArrayList?

LinkedList is a doubly linked list. Each element lives in a Node object with three references: item, prev and next. The list keeps references to first and last. It implements both List and Deque.

  • Adding or removing at the head or tail is O(1) — just relink nodes.
  • get(i) is O(n): it walks from the nearer end (the first half from first, the second from last).
  • Inserting "in the middle" is O(1) only if you are already there with a ListIterator; finding the position is O(n).
  • Memory: each element costs a whole node object (roughly 24–32 bytes of overhead), and nodes are scattered in memory, so iteration is cache-unfriendly.

  2. String concatenation evaluates left to right: removeFirst() returns 1, then removeLast() returns 5, and only then is the list printed as [2, 3, 4].
  3. it.next() == 3 works because the Integer is unboxed when compared to the int literal 3.
  4. it.add(99) inserts right after 3 (before 4) by relinking nodes; the iterator then continues to 4 without visiting 99, so the result is [2, 3, 99, 4] and no ConcurrentModificationException is thrown.
What is the remove(int) vs remove(Object) trap in List<Integer>?

List has two overloads. With an int argument the compiler picks remove(int index) — no boxing is needed — so it removes by position, not by value.

🧠 How this works

  1. nums.remove(1): the compiler picks remove(int index) because an exact primitive match beats autoboxing, so it removes index 1 (the value 20) giving [10, 30, 1].
  2. Integer.valueOf(1) is an object, so remove(Object) is chosen; it removes the first element equal to 1, giving [10, 30].
Vector, Stack and Collections.synchronizedList vs CopyOnWriteArrayList — which thread-safe list should you use?
  • Vector (Java 1.0) is like ArrayList but every method is synchronized, and it grows by 2× instead of 1.5×. All threads contend on one lock, and compound actions ("check, then add") are still not atomic. Legacy — avoid.
  • Stack extends Vector (synchronized, and it exposes index methods a stack shouldn't have). Use ArrayDeque with push/pop instead.
  • Collections.synchronizedList(list) wraps any list with one lock. You must still lock manually while iterating, otherwise you can get ConcurrentModificationException.
  • CopyOnWriteArrayList makes a fresh copy of the array on every write. Reads need no lock, and iterators work on a snapshot, so they never throw ConcurrentModificationException. Writes are O(n) and generate garbage, so it suits read-mostly data: event listeners, configuration, plug-in registries.

🧠 How this works

  1. synchronizedList locks each single method call, but a for-each loop is many calls (hasNext/next), so you must hold the list's own lock for the whole loop yourself.
  2. CopyOnWriteArrayList iterators walk a snapshot of the array taken when the loop started (2 elements).
  3. Each add("sms") copies the array and appends, but the running loop still sees only the old 2-element snapshot, so it runs exactly twice: [audit, email, sms, sms].
  4. Writes cost O(n) copies, so COW suits read-mostly lists such as listeners.

Set: HashSet, LinkedHashSet, TreeSet, EnumSet

How does HashSet guarantee uniqueness? How do LinkedHashSet and TreeSet differ?
  • HashSet is backed by a HashMap: each element is stored as a key, with a dummy shared value (PRESENT). add(e) is map.put(e, PRESENT) == null, so uniqueness comes from the map's key rules — hashCode() picks the bucket, then equals() decides whether it's a duplicate. No ordering guarantee.
  • LinkedHashSet is backed by a LinkedHashMap: same O(1) operations, plus a doubly linked list through the entries, so iteration follows insertion order. Ideal for "remove duplicates but keep order".
  • TreeSet is backed by a TreeMap (red-black tree). Elements are kept sorted by natural order (Comparable) or a Comparator, operations are O(log n), and it adds navigation methods. Uniqueness is decided by compareTo/compare returning 0 — not by equals.
  • EnumSet stores enum constants as bits in a long (a bit vector) — extremely fast and compact. Use it instead of a HashSet of enums.

🧠 How this works

  1. Duplicates are dropped because add on a set ignores an element that is already equal to one present. HashSet order depends on hash buckets and is not guaranteed (it just happens to match here); LinkedHashSet keeps insertion order; TreeSet sorts, giving [apple, banana, cherry].
  2. In the sorted scores {40, 55, 62, 75, 90}: floor(60) is the greatest <= 60 (55), ceiling(60) the least >= 60 (62), and higher(90) must be strictly greater than 90, so it is null.
  3. headSet(62) excludes 62, tailSet(62) includes it, and descendingSet() is a reversed view.
  4. A TreeSet uses its comparator, not equals(), to detect duplicates: case-insensitively "JAVA" compares as 0 to "Java", so it is rejected and the first one stays.
  5. EnumSet.range is a bit-vector set that always iterates in enum declaration order.
Why must equals() and hashCode() be overridden together? What happens with a mutable key?

Hash-based collections first use hashCode() to find the bucket, then equals() to compare within it. The contract: equal objects must have equal hash codes. If you override only equals, two "equal" objects land in different buckets and the set keeps both. If a key's fields change after it was inserted, its hash code changes, and the map looks in the wrong bucket — the entry becomes unreachable (a memory leak).

🧠 How this works

  1. BadPoint overrides equals but inherits Object.hashCode(), which is identity-based, so the two equal points land in different buckets.
  2. HashSet only calls equals on entries in the same bucket, so it never notices the duplicate: size is 2.
  3. A record generates equals and hashCode from its components, so a new Point(1, 2) hashes to the same bucket and contains is true.
  4. For the mutable key, adding "b" changes the list's hashCode; get(key) now looks in a different bucket and returns null, while the stale entry is still stored, so size is 1.
Use immutable keys: String, boxed numbers, records with immutable fields, or enums.

Map: HashMap, LinkedHashMap, TreeMap and friends

Explain the internal working of HashMap in detail (hashing, buckets, collisions, resizing, treeification).

A HashMap is an array of buckets (Node<K,V>[] table). Each node holds hash, key, value and next.

  1. Hashing: put(k, v) computes h = k.hashCode(), then spreads it: hash = h ^ (h >>> 16). Mixing the high bits into the low bits matters because the index uses only the low bits.
  2. Index: index = (n - 1) & hash, where n (the table length) is always a power of two, so this is a fast replacement for hash % n.
  3. Empty bucket → a new node is placed there.
  4. Collision (bucket already used) → walk the chain: if a node has the same hash and equals the key, replace its value; otherwise append a new node to the end of the list.
  5. Treeification (Java 8+): when one bucket's chain reaches 8 nodes (TREEIFY_THRESHOLD) and the table has at least 64 buckets, the chain is converted to a red-black tree, making worst-case lookup O(log n) instead of O(n). If the table is smaller than 64, it resizes instead. A tree shrinks back to a list at 6 nodes.
  6. Resizing: default capacity 16, load factor 0.75 → when size > capacity × 0.75 (12 for the default) the table doubles. Because the size is a power of two, each node either stays at its index or moves to index + oldCapacity — decided by one bit of the hash — so no full rehash is needed.
  7. Nulls: one null key is allowed (its hash is 0, so it goes to bucket 0), and any number of null values.

🧠 How this works

  1. The bucket index is computed from the key's hash (spread as h ^ (h >>> 16)) AND (capacity - 1); a null key always goes to bucket 0.
  2. "Aa" and "BB" have the same hashCode, so they share a bucket and are chained; equals() tells them apart on lookup.
  3. When one bucket's chain reaches 8 entries (and the table has at least 64 slots) it is converted into a red-black tree, making worst-case lookups O(log n) instead of O(n).

🧠 How this works

  1. String hash is s[0]*31 + s[1]: 'A'(65)*31 + 'a'(97) = 2112 and 'B'(66)*31 + 'B'(66) = 2112, a real collision.
  2. "BB" goes into the same bucket as "Aa", but equals is false, so both entries are kept.
  3. put("Aa", 10) finds an equal key and replaces the value (returning the old value 1); size does not grow.
  4. HashMap allows one null key, so the map holds Aa, BB and null: output 10 2 0 3.
  5. HashMap.newHashMap(1000) picks a capacity big enough that 1000 entries fit under the 0.75 load factor, so no resizing happens while filling it.
HashMap is not thread-safe. Concurrent puts can lose entries or corrupt the structure (in Java 7, concurrent resizing could even create a cycle and an infinite loop). Use ConcurrentHashMap for shared maps.

How does LinkedHashMap work? How do you build an LRU cache with it?

LinkedHashMap extends HashMap and additionally threads a doubly linked list through all entries (each entry has before/after pointers). Lookups stay O(1), but iteration follows a predictable order:

  • Insertion order (default) — re-inserting an existing key does not change its position.
  • Access order (new LinkedHashMap<>(cap, 0.75f, true)) — every get/put moves the entry to the end, so the first entry is the least recently used.

Overriding removeEldestEntry turns it into a bounded LRU cache. Since Java 21 it also implements SequencedMap: firstEntry(), lastEntry(), pollFirstEntry(), reversed(), putFirst().

🧠 How this works

  1. The third constructor argument true switches to access order: every get/put moves that entry to the end of the internal linked list.
  2. After inserting a, b, c the order is a, b, c; get("a") moves a to the end, so the order is b, c, a.
  3. put("d") makes size 4; removeEldestEntry is called after the insert, returns true, and the head (b, the least recently used) is evicted: {c=3, a=1, d=4}.
  4. The second map uses the default insertion order; Java 21 firstEntry(), lastEntry() and reversed() come from SequencedMap.
How does TreeMap work, and what navigation methods does it offer?

TreeMap is a red-black tree — a self-balancing binary search tree. Keys are kept sorted by their natural order or by a Comparator passed to the constructor. get, put and remove are O(log n). It implements NavigableMap, which makes it ideal for "nearest", "range" and "ranking" questions.

  • No null keys with natural ordering (compareTo(null) throws NullPointerException); null values are fine.
  • The comparator should be consistent with equals; keys that compare as 0 are treated as the same key.
  • Typical uses: price/tax slabs, time-series lookups ("value at or before time T"), leaderboards, scheduling.

What are WeakHashMap, IdentityHashMap and EnumMap used for?

ConcurrentHashMap & HashMap vs ConcurrentHashMap

How does ConcurrentHashMap work internally (Java 7 vs Java 8+)?

Java 7 used lock striping: the map was divided into 16 segments (by default), each a small hash table guarded by its own ReentrantLock. Up to 16 threads could write at once — one per segment.

Java 8+ redesigned it completely (segments are gone; concurrencyLevel is now only a sizing hint):

  1. Same layout as HashMap: a volatile array of bins holding nodes, with long bins converted to trees (TreeBin).
  2. Reads are lock-free: get() uses volatile reads, so it never blocks, even while other threads are writing.
  3. Inserting into an empty bin uses a CAS (compare-and-swap) — no lock at all.
  4. Writing to a non-empty bin locks only that bin, by synchronized on the bin's first node. Threads writing to different bins never block each other, so concurrency is effectively "number of bins", not 16.
  5. Resizing is cooperative: when the table grows, other threads that try to write help transfer bins to the new table. Moved bins are marked with a ForwardingNode, so readers know to look in the new table.
  6. Size counting uses a baseCount plus an array of CounterCells (the same idea as LongAdder), so many threads can increment the count without contending on one variable. size() is therefore an estimate while updates are in flight; mappingCount() returns a long.

🧠 How this works

  1. An empty bin is filled with a lock-free CAS (compare-and-swap); if two threads race, one CAS fails and that thread retries.
  2. A non-empty bin is locked by synchronizing on its first node only, so threads writing to different bins (B and C) never block each other.
  3. Reads use volatile reads of the table and nodes, so get never takes a lock and always sees a fully published node.

🧠 How this works

  1. push adds to the head, so after a, b, c the deque is [c, b, a]; pop removes the head (c), and peek looks at the new head (b) without removing it, leaving [b, a].

How does PriorityQueue work?

PriorityQueue is a binary min-heap stored in an array: the smallest element (by natural order or a Comparator) is always at the head. offer and poll are O(log n) (sift up / sift down); peek is O(1). It's used for scheduling, Dijkstra's algorithm, merging sorted streams and "top K" problems.

Iterating or printing a PriorityQueue does not give sorted order — only repeated poll() does. It is not thread-safe; use PriorityBlockingQueue for that.

🧠 How this works

  1. A PriorityQueue is a binary min-heap: poll() always removes the smallest element in O(log n), so draining gives sorted order [3, 7, 19, 25, 42] (printing the queue directly would not be sorted).
  2. For the top 3, keep a min-heap of size 3: after each offer, if size exceeds 3, drop the smallest. What remains are the 3 largest (12, 9, 8). Time O(n log k), space O(k).

Fail-fast vs fail-safe

What are fail-fast and fail-safe iterators? Explain the difference in detail.

When a collection is modified while it is being iterated, an iterator can react in two ways:

  • Fail-fast iterators detect the change and immediately throw ConcurrentModificationException (CME) instead of continuing with possibly inconsistent data. They belong to the regular java.util collections: ArrayList, LinkedList, HashMap, HashSet, TreeMap, ArrayDeque, etc.
  • Fail-safe iterators never throw CME. They come from the concurrent collections in java.util.concurrent, and work in one of two ways:
    • Snapshot (CopyOnWriteArrayList, CopyOnWriteArraySet): the iterator walks a copy of the array as it was when the iterator was created; later changes are invisible to it.
    • Weakly consistent (ConcurrentHashMap, ConcurrentLinkedQueue, ConcurrentSkipListMap, LinkedBlockingQueue…): the iterator walks the live structure and may or may not show changes made after it was created, but never fails and never returns an element twice.

🧠 How this works

  1. ArrayList: adding "d" bumps the list's modCount. On the next next() call the iterator sees it no longer matches its recorded expectedModCount and throws ConcurrentModificationException.
  2. CopyOnWriteArrayList: add("d") creates a new internal array, but the for-each loop holds the old array, so it visits only a, b, c — while the list itself now has four elements.
  3. ConcurrentHashMap: its iterator is weakly consistent, so inserting "z" mid-loop is allowed; the loop may or may not visit "z", and the map ends with 3 entries.
How does a fail-fast iterator work internally (modCount and expectedModCount)?
  1. Every fail-fast collection has an int modCount field (inherited from AbstractList, or declared in HashMap). It is incremented on every structural modification: add, remove, clear, resizing… but not on set(i, x) or map.put of an existing key, which only replace a value.
  2. When you call iterator(), the iterator copies the current value into expectedModCount.
  3. Every call to next() (and remove()) first runs checkForComodification(): if modCount != expectedModCount it throws ConcurrentModificationException.
  4. iterator.remove() removes the element and resets expectedModCount = modCount — that's why it's the one safe way to remove while iterating.

🧠 How this works

  1. The iterator never locks anything — it just compares two integers on each step, so the check costs O(1).
  2. Any structural change made outside the iterator increments modCount but not expectedModCount, so the very next next() detects the mismatch.
  3. remove() goes through the list but then copies the new modCount into expectedModCount, which keeps the two in sync.
  4. Because modCount isn't volatile or synchronized, another thread's change may not be seen in time — that's why fail-fast is "best effort", not a concurrency guarantee.
Can ConcurrentModificationException happen in a single thread? Show the correct ways to remove while iterating.

Yes — despite its name, CME has nothing to do with threads. It happens whenever the collection is structurally modified by anything other than the iterator itself, most commonly by calling list.remove() inside a for-each loop.

🧠 How this works

  1. In the first loop, removing 2 increments modCount; the next next() call detects it and throws — with only one thread involved.
  2. The "surprise" case: after removing "b" the size drops to 2 and the cursor is already 2, so hasNext() returns false and the loop ends before next() can check modCount. No exception, but "c" was never visited — a silent bug. Never rely on CME being thrown.
  3. Iterator.remove() and removeIf modify the list in a way the iteration knows about. ArrayList.removeIf also compacts the array in a single O(n) pass, whereas calling remove(i) repeatedly shifts elements each time (O(n²) worst case).
  4. For maps, removing through entrySet()/keySet()/values() views is safe because those views use the map's own iterator.
What is fail-fast as a design principle? How do you apply it in Java and Spring Boot code?

A fail-fast system detects an invalid state as early as possible and stops immediately with a clear error, instead of continuing and failing later in a confusing place (or silently corrupting data). The earlier a bug surfaces, the cheaper it is to find and fix.

  • Validate arguments at the start of methods and constructors.
  • Validate request input at the API boundary (@Valid) before any business logic or database call.
  • Validate configuration at startup, so a missing URL or bad timeout stops the app on deploy instead of breaking the first customer request at 3 a.m.
  • Use timeouts on every remote call, so a slow dependency fails quickly instead of tying up threads.
  • Prefer immutability (records, List.of) so objects can't drift into an invalid state later.

🧠 How this works

  1. The record's compact constructor runs before any field is set, so an invalid Transfer can never exist — every later method can trust its data without re-checking.
  2. Objects.requireNonNull throws a NullPointerException with the parameter name right at the boundary, instead of an anonymous NPE many calls later.
  3. With @Validated on a @ConfigurationProperties record, Spring Boot validates the bound values while creating the bean; a blank URL or a 0 ms timeout makes the application fail to start with a "Binding validation errors" report.
  4. Connect/read timeouts turn "wait forever" into a fast, handleable exception that a retry or circuit breaker can act on.
Fail-fast vs fail-safe in distributed systems — which do you choose, and what is "fail-open"?

Both are valid strategies; the right one depends on what failure costs.

They are often combined: a circuit breaker fails fast (no waiting on a dead service) and then returns a fail-safe fallback.

🧠 How this works

  1. @TimeLimiter caps how long the call may take; @CircuitBreaker counts failures and, past the threshold, opens — further calls skip the network entirely and fail in microseconds (fail-fast), protecting threads and the struggling service.
  2. Every failure or rejected call is routed to popularProducts, so users still see a sensible list (fail-safe). After a wait period the breaker goes half-open and lets a few trial calls through to test recovery.
  3. For authorization, the "safe" state is deny. Returning true on error would be fail-open: an outage of the permission service would let everyone approve invoices.
  4. Rule of thumb: fail-safe for availability of non-critical features, fail-fast (and fail-closed) wherever a wrong answer is worse than no answer.

Exceptions

Checked vs unchecked exceptions?
  • Checked (subclasses of Exception but not RuntimeException): must be caught or declared — e.g. IOException, SQLException. Represent recoverable conditions.
  • Unchecked (RuntimeException and Error): programming bugs or unrecoverable states — NullPointerException, IllegalArgumentException, OutOfMemoryError.

Spring favors unchecked exceptions (e.g. it translates SQLException into DataAccessException), and @Transactional rolls back on unchecked exceptions by default.

How does try-with-resources work? What are suppressed exceptions?

Any AutoCloseable declared in the header is closed automatically in reverse order. If both the body and close() throw, the body's exception is thrown and the close exception is attached via getSuppressed().

🧠 How this works

  1. Resources declared in the try(...) header are closed automatically in reverse order: rs first, then ps, then con, even if an exception or return happens.
  2. If the body throws and a close() also throws, the close exception is attached to the main one as a suppressed exception instead of replacing it; getSuppressed() reads them.
  3. The SQLException is wrapped in a domain exception with the original as its cause, so the stack trace is preserved.
throw vs throws?
  • throw is a statement inside a method body that actually throws one exception object: throw new IllegalArgumentException("...").
  • throws is part of the method signature. It declares which checked exceptions the method may throw, so callers must catch or re-declare them. It throws nothing by itself.
  • Checked exceptions must be declared with throws (or caught); unchecked exceptions (RuntimeException, Error) may be declared for documentation but do not have to be.
  • An overriding method may declare fewer or narrower checked exceptions than the parent, never broader ones.

🧠 How this works

  1. ConnectionException extends Exception, so it is checked: connect must list it in throws, and main must catch it, otherwise the code does not compile.
  2. "db.local" passes both checks and prints "Connected to db.local".
  3. " " is blank, so the throw statement creates and throws a ConnectionException, caught by the first catch.
  4. null triggers IllegalArgumentException, which is unchecked: it did not need to appear in throws, yet it can still be caught.
What is exception chaining? Why pass the cause?

When you catch a low-level exception and throw a higher-level one (e.g. SQLException → ServiceException), pass the original as the cause. Otherwise the root cause and its stack trace are lost, and production debugging becomes guesswork.

  • Pass it through the constructor (super(message, cause)) or call initCause() once.
  • Read it with getCause(); stack traces print it as Caused by: ....
  • Translate exceptions at layer boundaries (repository → service → controller) so callers see exceptions that make sense at their level. Spring does this for you with DataAccessException.

🧠 How this works

  1. queryDb throws a checked SQLException; loadUser catches it and throws an unchecked ServiceException, passing e as the cause.
  2. The caller only deals with the service-level exception, but getCause() still returns the original SQLException with its message.
  3. The while loop walks the cause chain to the deepest exception, the real root cause.
  4. If this were logged with log.error("...", e), the stack trace would show both exceptions, the second under "Caused by:".
Do not log and rethrow at every layer (the same error then appears in the logs many times). Wrap and rethrow with the cause, and log once at the boundary (e.g. a @ControllerAdvice).
What is a multi-catch block, and what are its rules?

Since Java 7 one catch can handle several unrelated exception types: catch (IOException | ParseException e). Use it when the handling is identical; it removes duplicated catch blocks.

  • The parameter is implicitly final: you cannot assign to e.
  • The static type of e is the closest common supertype (here Exception), so you can only call methods of that type.
  • The alternatives must not be subclasses of each other: catch (FileNotFoundException | IOException e) is a compile error ("Alternatives in a multi-catch statement cannot be related by subclassing"). Just catch the parent.
  • When the handling differs, keep separate catch blocks, most specific first.

🧠 How this works

  1. "x" throws nothing, so "ok: x" is printed.
  2. "io" and "parse" throw two unrelated checked exceptions; the single multi-catch block handles both.
  3. getClass() returns the runtime class, so the output still shows which exception actually occurred.
  4. The compiler also does precise rethrow: throw e; inside this block would only require the method to declare IOException and ParseException, not plain Exception.
What happens if an exception is thrown (or a return executes) inside a finally block?

If finally completes abruptly — by throwing or by return/break/continue — that outcome replaces whatever the try/catch was doing. The original exception is silently lost: it is not chained and not added as suppressed.

🧠 How this works

  1. The try throws "Original"; before it propagates, finally runs and throws its own exception. The JVM drops the pending exception and propagates the new one.
  2. getSuppressed() is empty: unlike try-with-resources, a plain finally does not keep the lost exception anywhere.
  3. In returnFromFinally, the return 42 in finally discards the pending exception completely, so the caller gets 42 and never learns anything failed. javac -Xlint:finally warns about this.
Never throw or return from finally. Use try-with-resources for cleanup (failures in close() become suppressed exceptions); if you must clean up by hand, wrap it: finally { try { res.close(); } catch (Exception e) { log.warn("close failed", e); } }.

Generics

What is type erasure? What can't you do with generics because of it?

Generic type arguments exist only at compile time. javac checks them, then erases them: T becomes its bound (Object if unbounded), casts are inserted where values are read, and bridge methods are generated where needed. At runtime List<String> and List<Integer> are the same class. This kept Java 5 generics binary-compatible with older code.

Consequences:

  • No new T(), new T[n] or T.class — pass a Class<T> or a Supplier<T> instead.
  • No obj instanceof List<String> (only List<?>), and no primitive type arguments (List<int>).
  • You cannot overload methods whose parameters differ only in type arguments: process(List<String>) and process(List<Integer>) give "name clash: ... have the same erasure".
  • Static fields are shared by all parameterisations, and a generic class cannot extend Throwable.
  • Heap pollution: raw types or unchecked casts can put the wrong type into a collection; the error only appears later, at the compiler-inserted cast.

🧠 How this works

  1. After erasure both lists are plain ArrayList objects, so their Class objects are identical.
  2. Through the raw List reference the compiler cannot check the element type, so raw.add(42) compiles with only a warning and the Integer really is stored in strings.
  3. strings.get(0) is compiled as (String) strings.get(0); that hidden cast fails, so the error shows up far from the line that caused it.
  4. Lesson: never ignore "unchecked" warnings and never use raw types in new code.
Not everything is erased: generic information in declarations (field types, method signatures, class Foo extends Bar<String>) is kept in the class file and can be read via reflection. Jackson's TypeReference and Spring's ParameterizedTypeReference rely on this.

What are bounded wildcards? Explain <? extends T> vs <? super T> and the PECS rule.

PECS: Producer extends, Consumer super (Effective Java, Item 31). Look at what the method does with the collection:

  • <? extends T> (upper bound) — the list holds T or some subtype. You can safely read elements as T, but you cannot add (except null) because the exact subtype is unknown. Use it when the collection produces values for you.
  • <? super T> (lower bound) — the list holds T or some supertype. You can safely add T values, but reads come back only as Object. Use it when the collection consumes values you give it.
  • Read and write the same collection? Use a plain <T>.

🧠 How this works

  1. sum only reads, so ? extends Number lets it accept a List<Integer> or a List<Double>; every element is guaranteed to be a Number.
  2. addNumbers only writes Integers; any list whose element type is Integer or a supertype (Number, Object) can safely hold them.
  3. In copy, src produces T (extends) and dest consumes T (super), so strings can be copied into a List<Object>; T is inferred as String.
  4. The JDK uses the same pattern: Collections.copy(List<? super T>, List<? extends T>), Collections.max(Collection<? extends T>) and Comparator<? super T> parameters.
What is a generic method, and how is it different from a generic class?
  • Generic class (class Box<T>): T is fixed when you create or declare an instance (Box<String>) and is shared by all its instance methods and fields. Static members cannot use the class's T.
  • Generic method (static <T> T first(List<T> l)): the type parameter is declared before the return type and is chosen fresh on each call, usually inferred from the arguments. It can be static and can live in a non-generic class (e.g. Collections, List.of).
  • Both can use bounds such as <T extends Comparable<? super T>> to call methods of the bound.

🧠 How this works

  1. Box<String> fixes T = String for that object. Its generic method map introduces a new R per call; with String::length, R is inferred as Integer, so the result is a Box<Integer> holding 5.
  2. firstOrDefault is static and infers T from its arguments: the first call returns "a", the second gets an empty list and returns the default.
  3. max is bounded by Comparable, which is what allows it to call compareTo; for [3, 9, 4] it returns 9.
  4. G29.<String>firstOrDefault(...) shows the rarely needed explicit type-argument syntax, used when inference has nothing to go on.

How do enums work in Java, and what can they contain?

An enum is a class with a fixed set of instances created when the class is initialised. Each enum implicitly extends java.lang.Enum (so it cannot extend another class), its constructor is always private, and the JVM guarantees exactly one instance per constant, even across serialization and reflection.

  • Enums can have fields, constructors, methods, implement interfaces, and give each constant its own constant-specific body (overriding an abstract method).
  • Built-in: values(), valueOf(String) (throws IllegalArgumentException for an unknown, case-sensitive name), name(), ordinal(), compareTo() (declaration order).
  • Because constants are singletons, comparing with == is correct and null-safe.
  • Use EnumMap/EnumSet for enum keys, and do not persist ordinal(): reordering the constants changes it (in JPA use @Enumerated(EnumType.STRING)).

🧠 How this works

  1. Each constant calls the constructor once, so HIGH stores weight 10. values() returns the constants in declaration order, and ordinal() is the zero-based position (MEDIUM → 1).
  2. valueOf matches the exact constant name; "high" is not "HIGH", so it throws IllegalArgumentException.
  3. ADD and MUL each have their own body implementing applyAsInt, so the same call computes 9 or 18: polymorphism without if/switch.
  4. The switch expression covers all three constants, so the compiler accepts it without a default.
  5. A constant with a body is compiled to an anonymous subclass, so ADD.getClass() is not Operation.class; use getDeclaringClass() to get the enum type.
A single-element enum is the simplest thread-safe singleton (see "Write a thread-safe Singleton" in Coding questions).
@Override vs @Deprecated vs @SuppressWarnings (and @FunctionalInterface)?
  • @Override — asks the compiler to verify the method really overrides or implements a supertype method. A typo or wrong parameter type becomes a compile error instead of a silent overload.
  • @Deprecated — marks an API that should no longer be used; callers get a compiler warning. Since Java 9 it has since and forRemoval elements; forRemoval = true produces a stronger "removal" warning. Pair it with a Javadoc @deprecated tag that names the replacement.
  • @SuppressWarnings — silences specific compiler warnings: "unchecked", "rawtypes", "deprecation", "removal", "unused" (the last is IDE-specific). Put it on the smallest possible scope.
  • @FunctionalInterface — makes the compiler check that an interface has exactly one abstract method.

🧠 How this works

  1. The Javadoc comment comes before the annotation, because a doc comment must precede the whole declaration (including its annotations) to be picked up by Javadoc.
  2. Calling oldMethod() still works. Code in other top-level classes gets a "deprecated and marked for removal" warning (uses inside the same top-level class, as in this one-file demo, are exempt); @SuppressWarnings("removal") is how such a caller silences it on purpose.
  3. Money.equals(Object) is a real override, so HashSet.contains finds the equal object (true). Without @Override, an accidental equals(Money) would compile and contains would return false.
  4. fromLegacy uses a raw list and an unchecked cast; the annotation hides those two warnings for that method only.
  5. Validator has one abstract method, so it can be the target of a lambda; adding a second abstract method would fail to compile because of @FunctionalInterface.
These are all compile-time annotations (@Override and @SuppressWarnings have SOURCE retention). Framework annotations such as @Transactional or @Entity have RUNTIME retention so they can be read by reflection.

Serialization & I/O

What is Java serialization? How do you control it (transient, serialVersionUID, writeObject), and why is it risky?

Serialization turns an object graph into bytes (ObjectOutputStream.writeObject) and deserialization rebuilds it (ObjectInputStream.readObject). A class opts in by implementing the marker interface java.io.Serializable; every non-transient field must itself be serializable.

  • transient fields are skipped and come back as default values (null, 0, false). static fields are never serialized.
  • serialVersionUID identifies the class version. If you do not declare it, the JVM computes one from the class structure, so almost any change makes old data fail with InvalidClassException. Declare it explicitly and change it only for incompatible changes.
  • Custom logic: private writeObject/readObject methods (mark them @Serial, Java 14+); readResolve to keep singletons unique; or Externalizable for full manual control.
  • Deserialization creates objects without running the class's constructors (only the no-arg constructor of the first non-serializable superclass runs), so constructor validation is bypassed.

🧠 How this works

  1. defaultWriteObject() writes the non-transient field name; our custom writeObject then writes the password in a transformed form (a real system would encrypt it, or better, never serialize it).
  2. On reading, defaultReadObject() restores name, and our readObject reads the extra value back in the same order and restores password.
  3. loginCount is transient and not written by our code, so it comes back as 0.
  4. The result is a new object (copy == original is false). The ObjectInputFilter (Java 9+) only allows User and java.base classes and rejects everything else (!*).
Security: never deserialize untrusted bytes with ObjectInputStream. Crafted "gadget chains" in classes on your classpath can lead to remote code execution. If you must, use an allow-list ObjectInputFilter (or the JVM-wide jdk.serialFilter). For APIs, messaging and caches prefer JSON, Protobuf or Avro. Records are a safer fit for serialization because deserialization goes through their canonical constructor.
FileInputStream vs BufferedInputStream — why should you buffer I/O?
  • FileInputStream reads straight from the file. Each read() call goes to the operating system (a native call), so reading one byte at a time is very slow.
  • BufferedInputStream is a decorator: it wraps any InputStream, fills an internal buffer (8 KB by default) with one large read, and serves the following read() calls from memory.
  • The same idea exists for text: BufferedReader (adds readLine()), and for output: BufferedOutputStream/BufferedWriter (remember to flush()/close).
  • Buffering matters for many small reads. If you already read big chunks (read(byte[8192]), Files.readAllBytes, InputStream.transferTo), an extra buffer adds little.

🧠 How this works

  1. Both loops call read() five million times and count the same number of bytes.
  2. Without a buffer, every read() is a native call into the OS, so the first loop makes about five million system calls.
  3. With BufferedInputStream, only about 5,000,000 / 8,192 ≈ 611 reads reach the OS; the rest are cheap array lookups, so it is roughly 80 times faster here.
  4. Files.newBufferedReader returns a BufferedReader (UTF-8 by default) whose readLine() returns one line at a time without the line terminator, and null at end of file.

What is the Builder pattern, and when should you use it?

A Builder creates a complex object step by step through a fluent API and builds it in one final build() call. It replaces telescoping constructors (many overloads with growing parameter lists) and JavaBeans-style setters (which leave the object mutable and half-initialised).

  • Use it when a class has many parameters, especially optional ones or several of the same type (easy to swap by mistake).
  • The product can be immutable: all fields final, set once from the builder.
  • build() is the single place to validate the combination of values.
  • Required values go into the builder's constructor (or factory method); optional values get defaults.
  • In practice, Lombok's @Builder generates this code. JDK examples: HttpRequest.newBuilder(), StringBuilder, Stream.builder(), Locale.Builder.

🧠 How this works

  1. HttpRequest's constructor is private, so the only way to get one is through the builder; the URL is required by the builder's factory method, and everything else has defaults.
  2. Each setter-like method changes the builder and returns this, which makes the fluent chain possible. The first request uses all defaults (GET, 5000 ms, no headers).
  3. build() validates the values once, then passes the builder to the private constructor, which copies them into final fields; Map.copyOf makes the headers immutable, so later builder changes cannot leak into a built request.
  4. timeout(0) is rejected in build() with a clear message, so an invalid request object can never exist.
For small, all-required data, a record is simpler than a builder. Builders shine when there are many optional values or when the object needs validation across fields.

Use Optional as a return type to signal "may be absent". Avoid it for fields, method parameters or collections, and never call get() without checking.

🧠 How this works

  3. orElse("Unknown") supplies the fallback; orElseThrow takes a supplier, so the exception object is only created when the value is missing.

Why is java.time better than Date/Calendar?

What does volatile guarantee — and what doesn't it?

volatile guarantees visibility (writes go to main memory and establish happens-before) and prevents reordering around the access. It does not make compound operations like count++ atomic — use AtomicInteger/LongAdder or a lock.

🧠 How this works

  1. Writing a volatile field makes the new value visible to other threads, so the worker loop reading running sees false soon after stop() is called and exits.
  2. Without volatile, the JIT may hoist the read out of the loop and spin forever.
  3. volatile does not make count++ atomic (it is read, add, write). AtomicInteger.incrementAndGet uses CAS to do the whole update atomically.

What is a deadlock and how do you prevent it?

Two or more threads wait forever for locks held by each other. Required conditions: mutual exclusion, hold-and-wait, no preemption, circular wait.

🧠 How this works

  1. A deadlock needs a circular wait: thread 1 locks A then waits for B while thread 2 locks B then waits for A.
  2. Here both threads compute the same order (lower id first) no matter which direction the transfer goes, so they always lock in the same sequence and a cycle is impossible.
  3. The second thread simply waits on the first lock until the first thread finishes both blocks. This assumes account ids are unique.

Other techniques: tryLock with timeout, minimise lock scope, prefer higher-level concurrency utilities. Detect with jstack <pid> ("Found one Java-level deadlock").

What happens to an exception thrown in a thread's run() method?

An uncaught exception terminates only that thread. It never propagates to the thread that called start(), so a try/catch around start() catches nothing. The JVM passes it to the thread's UncaughtExceptionHandler, then the thread group's, then the default handler, which by default prints the stack trace to System.err.

  • Plain thread: set t.setUncaughtExceptionHandler(...) or a global Thread.setDefaultUncaughtExceptionHandler(...) to log it.
  • executor.execute(task): same as above; the worker thread dies and the pool replaces it.
  • executor.submit(task): the exception is stored in the Future and rethrown, wrapped in ExecutionException, only when you call get(). If nobody calls get(), it is silently lost.
  • CompletableFuture: handle it in the pipeline with exceptionally/handle/whenComplete.

🧠 How this works

  1. The exception is thrown on worker-1's own stack. When it reaches the top of run(), the JVM calls the handler we installed on that thread, then the thread ends.
  2. main only waits in join(), which returns normally; that is why the catch block in main never runs.
  3. With submit, the executor catches the exception and stores it in the Future; get() rethrows it as ExecutionException with the original as the cause.
  4. supplyAsync completes the future exceptionally; exceptionally receives a CompletionException wrapping the original, so ex.getCause().getMessage() is "cf" and the pipeline recovers with a fallback value.

What are the atomic classes in java.util.concurrent.atomic? When do you use LongAdder instead of AtomicLong?

Atomic classes give lock-free, thread-safe updates of a single variable. They are built on the CPU's compare-and-swap (CAS) instruction: read the current value, compute the new one, and write it only if the value is still what was read — otherwise retry. Their fields are volatile, so they also give visibility.

  • AtomicInteger, AtomicLong, AtomicBoolean — get/set, incrementAndGet, getAndIncrement, addAndGet, compareAndSet(expected, new), and since Java 8 updateAndGet/accumulateAndGet with a lambda.
  • AtomicReference<V> — atomically swap an object reference (e.g. an immutable config snapshot). AtomicStampedReference adds a version stamp to avoid the ABA problem.
  • AtomicIntegerArray, AtomicLongArray, AtomicReferenceArray — atomic operations on individual array elements.
  • LongAdder, DoubleAdder, LongAccumulator (Java 8) — spread updates over several internal cells, so threads rarely collide; sum() adds the cells up. Much faster than AtomicLong under heavy write contention, but sum() is not an atomic snapshot and there is no compareAndSet.

🧠 How this works

  1. plain++ is three steps (read, add, write); two threads can read the same value and both write value+1, so increments are lost and the total is usually below 400000.
  2. incrementAndGet loops on CAS until its write succeeds, so all 400,000 increments land. LongAdder.increment also reaches 400,000, but threads mostly hit different cells, so they contend far less.
  3. compareAndSet(5, 4) succeeds because the value is 5; the second compareAndSet(5, 3) fails because it is now 4 — the basis of optimistic, lock-free algorithms.
  4. getAndIncrement returns the old value (4) then stores 5; updateAndGet(x -> x * 10) gives 50; accumulateAndGet(7, Math::max) keeps max(50, 7) = 50. The lambdas may be retried, so they must be side-effect free.
  5. AtomicReference.getAndUpdate swaps the whole reference atomically, and AtomicIntegerArray updates individual slots: [0, 1, 5].
Atomics protect one variable. If two values must change together (e.g. balance and history), use a lock, or put both in an immutable object behind one AtomicReference. Rule of thumb: AtomicLong for IDs/sequences and CAS logic, LongAdder for hot statistics counters that are read rarely.

What are the ways to run code on another thread, and why prefer an ExecutorService?

🧠 How this works

  1. Subclassing Thread works, but uses up your only superclass and mixes the task with the thread.
  2. A Runnable passed to new Thread separates task from thread, but cannot return a value or throw a checked exception, and creating an OS thread per task is expensive.

How do you size a thread pool?
  • CPU-bound (hashing, image processing): threads ≈ cores (or cores + 1). More threads only add context switches.
  • I/O-bound (Brian Goetz's formula): threads = cores × target utilisation × (1 + wait time / compute time). E.g. 8 cores, task waits 90 ms and computes 10 ms → 8 × 1 × (1 + 9) = 80 threads.
  • The real limit is often a downstream resource: no point running 200 threads against a 20-connection DB pool.
  • Measure under load (queue size, active count, latency percentiles), then tune. Or for I/O-bound work on Java 21+, use virtual threads and limit only the scarce resource.

🧠 How this works

  1. availableProcessors() returns the CPUs the JVM may use, and respects container CPU limits, so it is the starting point for sizing.
  2. For CPU-bound work use about that many threads; for I/O-bound work use more, roughly cores × (1 + wait time / compute time).
execute() vs submit() — where do exceptions go?
  • execute(Runnable): an exception kills the worker thread (the pool replaces it) and goes to the thread's UncaughtExceptionHandler — you see a stack trace.
  • submit(...): the exception is captured in the Future. If nobody calls get(), it is silently swallowed — a very common production bug.

🧠 How this works

  1. With submit, the thrown exception is captured inside the Future instead of reaching the thread's uncaught-exception handler, so nothing is logged unless you call get.
  2. get rethrows it wrapped in ExecutionException; getCause() is the original IllegalStateException.
  3. On timeout, cancel(true) interrupts the worker; on InterruptedException we restore the interrupt flag so callers can still see it.
  4. Java 19 added state() and exceptionNow() to inspect a completed future without the try/catch.
How do you shut down an executor correctly?
  • shutdown() — stop accepting new tasks; queued and running tasks finish.
  • shutdownNow() — interrupts running tasks and returns the queued ones that never started.
  • awaitTermination(timeout) — blocks until done or timeout.
  • close() (Java 19+) — shutdown() + wait until all tasks finish; enables try-with-resources.

🧠 How this works

  1. shutdown() rejects new tasks but lets running and queued ones finish; awaitTermination waits up to 30 s for that.
  2. If time runs out, shutdownNow() interrupts running tasks and returns the queued ones that never started, so you can log how many were dropped.
  3. If the waiting thread itself is interrupted, it forces shutdown and restores the interrupt flag.
  4. Since Java 19, ExecutorService is AutoCloseable: close() calls shutdown and waits for both tasks.
A pool of non-daemon threads that is never shut down keeps the JVM alive after main ends. Tasks must respond to interruption (check Thread.interrupted(), or use blocking calls that throw InterruptedException) for shutdownNow() to work.

  • invokeAll(tasks, timeout) — waits for all; tasks not finished in time are cancelled. Futures come back in submission order.
  • invokeAny(tasks) — returns the first successful result and cancels the rest (e.g. query 3 mirrors, use the fastest).
  • ExecutorCompletionService — hands you results in completion order, so you can process fast results while slow ones still run.

🧠 How this works

  1. Each provider call is submitted to the pool; the ExecutorCompletionService puts every finished future into an internal queue.
  2. cs.take() blocks until the next completed task, so quotes are displayed in completion order, fastest first, instead of submission order.
  3. The loop runs exactly providers.size() times, one take() per submitted task; get() would rethrow a failed task's exception.
Why should you pass your own executor to CompletableFuture?

Without an executor, supplyAsync uses ForkJoinPool.commonPool(), which has only cores − 1 threads and is shared with parallel streams across the whole JVM. One blocking HTTP call there can starve unrelated code.

🧠 How this works

  1. Without an executor argument, supplyAsync uses the shared ForkJoinPool.commonPool(), which has only about (cores - 1) threads; blocking I/O there starves everything else using it.
  2. Passing io runs both remote calls in parallel on a dedicated pool.
  3. thenCombine merges the two results; orTimeout fails after 2 s and exceptionally turns failure into an empty dashboard, so join() returns either a real or an empty result.
What is ForkJoinPool and work stealing? How is it different from ThreadPoolExecutor?

Each ForkJoinPool worker has its own double-ended queue. A task fork()s subtasks onto its own deque (LIFO, cache-friendly); idle workers steal from the tail of other workers' deques (FIFO). This suits recursive divide-and-conquer work. ThreadPoolExecutor has one shared queue and suits independent tasks.

🧠 How this works

  1. If the range has at most 10,000 elements, the task sums it directly; otherwise it splits the range in half (>>> 1 avoids int overflow when computing the midpoint).
  2. left.fork() pushes the left half onto this worker's deque, where idle workers can steal it; the right half is computed directly on the current thread.
  3. left.join() waits for (or runs) the left half, and the two partial sums are added.
  4. Total work is O(n); with P workers the time is about O(n / P + log n). The threshold avoids creating too many tiny tasks.
Parallel streams and CompletableFuture's default use the common pool. Virtual threads are also scheduled by a dedicated ForkJoinPool of carrier threads.
What goes wrong with ThreadLocal in thread pools, and how do you propagate context (e.g. MDC, security)?

Pool threads live forever, so a ThreadLocal that is set but not removed leaks into the next task (user A's tenant ID seen by user B) and retains memory. Always clear it in finally, and copy context explicitly when handing work to another thread.

🧠 How this works

  1. MDC is backed by a ThreadLocal, so a pool worker does not see the submitter's values (and may see leftovers from a previous task).
  2. withMdc copies the context on the submitting thread at wrap time.
  3. Inside the worker it saves the worker's current context, installs the captured one, runs the task, and in finally restores the previous context, so nothing leaks to the next task on that thread.
Spring offers TaskDecorator for ThreadPoolTaskExecutor, and DelegatingSecurityContextExecutorService for the security context. With virtual threads on Java 25, prefer ScopedValue — immutable and automatically scoped.

Virtual threads (Java 21 → 25)

Virtual threads were finalized in Java 21 (JEP 444). Java 24 removed most pinning (JEP 491), and Java 25 LTS adds final Scoped Values — making 25 the best release to adopt them on.

What is a virtual thread and how does it work internally?

A virtual thread is a java.lang.Thread managed by the JVM, not the OS. Many virtual threads are multiplexed onto a small pool of carrier platform threads (a ForkJoinPool, parallelism = CPU count by default).

  • When a virtual thread blocks on I/O, sleep, a lock or a BlockingQueue, the JVM unmounts it: its stack frames are copied to the heap as a continuation, and the carrier is free to run another virtual thread.
  • When the I/O completes, the virtual thread is mounted again on any free carrier and continues.
  • Cost: a few hundred bytes to a few KB of heap that grows as needed, versus ~1 MB reserved stack for a platform thread. Millions are practical.

🧠 How this works

  1. Virtual threads are ordinary Java objects on the heap, so millions can exist; only a few carrier (platform) threads, by default about one per core, actually run them.
  2. When a virtual thread blocks on I/O or sleep, its stack is saved to the heap and the carrier is freed to run another virtual thread.
  3. When the I/O completes, the virtual thread is scheduled again, possibly on a different carrier.
Virtual threads improve throughput (more concurrent requests), not the latency of a single request. They make the simple blocking, thread-per-request style scale like reactive code.

What is pinning? What changed in Java 24/25?

A virtual thread is pinned when it cannot unmount while blocking, so it holds its carrier thread hostage. With few carriers, a handful of pinned threads can stall the whole application.

  • Java 21–23: blocking inside a synchronized block/method pinned the thread. Advice was to replace synchronized with ReentrantLock around blocking calls.
  • Java 24+ (JEP 491): virtual threads can acquire, hold and release monitors independently of their carrier, so synchronized no longer pins. On Java 25 you don't need to rewrite synchronized code.
  • Still pins: blocking while a native method or foreign (FFM) call is on the stack, and some class-initialization cases.
  • Detect: the JFR event jdk.VirtualThreadPinned (the old -Djdk.tracePinnedThreads flag was removed in Java 24).

🧠 How this works

  1. The first command starts the app with Java Flight Recorder enabled and writes events to app.jfr.
  2. jfr print --events jdk.VirtualThreadPinned lists each time a virtual thread could not unmount from its carrier while blocking, with stack traces showing where.
  3. Since Java 24 (JEP 491), synchronized no longer pins; remaining causes include native code/JNI frames.
Why must you not pool virtual threads? How do you limit concurrency instead?

Pools exist to amortise the cost of expensive threads. Virtual threads are cheap, so pooling adds nothing — and a fixed pool of virtual threads silently reintroduces the throughput cap you wanted to remove. Instead, create one per task and limit the scarce resource with a Semaphore.

🧠 How this works

  1. A fixed pool of 50 virtual threads only runs 50 tasks at a time, throwing away the main benefit of virtual threads.
  2. Instead, create one virtual thread per task and protect the scarce resource with a Semaphore of 20 permits.
  3. acquire() blocks (cheaply, on a virtual thread) once 20 calls are in flight; release() in finally returns the permit even if the call throws, so permits never leak.
ThreadLocal vs ScopedValue (final in Java 25) — why does it matter for virtual threads?

ThreadLocal is mutable, unbounded in lifetime (until remove()), and costly when inherited by millions of threads. ScopedValue (JEP 506) is immutable, bound only for the duration of a call, and cheap to share with child threads in structured concurrency.

🧠 How this works

  1. ScopedValue.newInstance() creates a key; where(USER, value).run(...) binds the value only for the duration of that run call.
  2. Any code called inside run, however deep, reads it with USER.get(); when run returns the binding disappears automatically, so nothing needs cleaning up (unlike ThreadLocal.remove()).
  3. The value is immutable for the scope, and child threads forked in a StructuredTaskScope inherit it cheaply.
  4. get() throws NoSuchElementException when unbound, so orElse is the safe read.
What is structured concurrency (preview in Java 25)? Show an example.

StructuredTaskScope (JEP 505, 5th preview) treats a group of subtasks as one unit: they are forked inside a scope, the scope waits for them, and if one fails the others are cancelled. No leaked threads, and thread dumps show the parent–child relationship.

🧠 How this works

  1. StructuredTaskScope.open() creates a scope whose default policy needs all subtasks to succeed; each fork starts a subtask in a new virtual thread.
  2. scope.join() waits for both; if one fails, the other is cancelled and join throws FailedException.
  3. After a successful join, user.get() and orders.get() return results, and leaving the try block guarantees no subtask outlives the method.
  4. With anySuccessfulResultOrThrow, the first mirror to succeed wins, the others are cancelled, and join() returns that result.
The API changed between previews (Java 21–24 used new StructuredTaskScope.ShutdownOnFailure()); in interviews, mention that it is still preview in 25.

JVM internals

Describe the JVM memory areas.
  • Heap — all objects; shared; managed by GC (young gen: Eden + survivors, old gen).
  • Metaspace (Java 8+, replaced PermGen) — class metadata in native memory.
  • Stack — one per thread: frames with local variables and partial results. Overflow → StackOverflowError.
  • PC register and native method stack — per thread.
  • Code cache — JIT-compiled native code.

🧠 How this works

  1. -Xms512m/-Xmx2g set the initial and maximum heap; -XX:MaxMetaspaceSize caps class metadata, which lives in native memory outside the heap.
  2. -Xss1m sets each thread's stack size; deep recursion beyond it causes StackOverflowError.
  3. -XX:+HeapDumpOnOutOfMemoryError writes a heap dump when the heap runs out, so you can find the leak afterwards.
How does class loading work? What is the parent delegation model?

Phases: Loading → Linking (verify, prepare, resolve) → Initialization (static initializers run on first active use).

Loaders: Bootstrap (core java.base) → Platform → Application/System (classpath). A loader first delegates to its parent and only loads the class itself if the parent cannot, which prevents user code from replacing java.lang.String. Application servers and Spring Boot's fat-jar loader add custom loaders.

How does garbage collection work at a high level?

GC finds objects unreachable from GC roots (stack locals, static fields, JNI refs, active threads) and reclaims them. The generational hypothesis — most objects die young — means new objects go to Eden; survivors are copied between survivor spaces and promoted to the old generation after several cycles.

  • Minor GC — young gen, frequent and fast.
  • Major/Full GC — old gen / whole heap, expensive.
  • Collectors: Serial, Parallel, G1 (default since Java 9), ZGC, Shenandoah.
Memory leaks in Java are objects that are still reachable but no longer needed — e.g. growing static maps, unremoved listeners, ThreadLocals in pooled threads.

What is a memory leak in Java if there is a garbage collector? What causes one, and how do you find it?

The GC only frees objects that are unreachable from GC roots. A Java memory leak is an object your program no longer needs but still references — so the GC must keep it. Over time the old generation fills, Full GCs become frequent and long, and finally OutOfMemoryError: Java heap space (or Metaspace) is thrown.

Common causes:

  • Static or long-lived collections that only grow — a "cache" HashMap without size limit or eviction.
  • ThreadLocal values never removed in pooled threads — the thread lives forever, so does the value (and it leaks into the next request).
  • Listeners / callbacks / observers registered and never unregistered.
  • Non-static inner classes and lambdas capturing Outer.this, then stored somewhere long-lived (a scheduler, a static field).
  • Mutable keys in a HashMap/HashSet: changing a field used by hashCode() makes the entry unreachable via get/remove but still referenced.
  • Unclosed resources (streams, connections) — leak native memory or pool slots; use try-with-resources.
  • Classloader leaks on redeploy in app servers — a class from the old webapp is still referenced, so the whole classloader and its Metaspace stay alive.

🧠 How this works

  1. CACHE is static, so it is a GC root for as long as the class is loaded. Every unique key adds 1 KB that is never removed — 10,000 entries are ~10 MB that the GC can never reclaim. In production the keys are request IDs or user IDs and the map grows until OutOfMemoryError.
  2. A ThreadLocal value is stored in the thread's own map. The single pool thread survives between tasks, so the value set by task 1 is still there for task 2 — a memory leak and a data leak (request 2 sees "alice").
  3. Calling remove() in finally clears the thread's entry, so the next task on that thread sees null.
  4. Fixes for caches: bound the size and evict (Caffeine, or a LinkedHashMap with removeEldestEntry), or use WeakHashMap when entries should die with their keys.

How to find a leak:

  1. Symptom: heap usage after each Full GC keeps rising (a "sawtooth" whose floor climbs) — watch GC logs (-Xlog:gc), JFR, or your APM.
  2. Capture a heap dump: -XX:+HeapDumpOnOutOfMemoryError, or on a live JVM jcmd <pid> GC.heap_dump /tmp/heap.hprof.
  3. Open it in Eclipse MAT or VisualVM: look at the dominator tree / "Leak Suspects" report and follow the path to GC roots of the biggest retained objects — it shows exactly which static field, thread or listener is holding them.
  4. For a quick live view, jcmd <pid> GC.class_histogram taken a few minutes apart shows which classes keep growing.

Integer cache: what do a == b and c == d print for boxed values 127, 128, 100 and 200?

🧠 How this works

  1. Integer a = 127 compiles to Integer.valueOf(127). valueOf returns a cached object for -128..127, so a and b (and e, f with 100) are the same object and == is true.
  2. 128 and 200 are outside the cache, so each valueOf call creates a new object; == on two Integer references compares identity, so c == d and g == h are false.
  3. equals compares the wrapped values, so g.equals(h) is true. When one side is a primitive (c == 128) the wrapper is unboxed and numbers are compared: true.
  4. Long.equals(Object) returns true only for another Long. The literal 127 is boxed to an Integer, so big.equals(127) is false — a common bug with map keys of type Long.
  5. The upper bound of the Integer cache can be raised with -XX:AutoBoxCacheMax=<n>, so code relying on == may even behave differently between environments. Always compare wrappers with equals() (and beware of NullPointerException when unboxing null).
Field hiding vs method overriding: what does Parent obj = new Child() print for obj.x and obj.print()?

🧠 How this works

  1. Fields are not polymorphic. obj.x is resolved at compile time from the declared type Parent, so it reads Parent.x = 10. A Child object actually contains both fields.
  2. Instance methods are polymorphic: obj.print() is dispatched at run time on the actual object (Child). Inside Child.print(), x means Child.x = 20 and super.x is the hidden parent field = 10.
  3. Casting changes the compile-time type, so ((Child) obj).x reads Child.x = 20.
  4. Static methods are hidden, not overridden: obj.kind() is compiled as Parent.kind() based on the declared type, so it prints "Parent.kind" (calling a static method through an instance compiles, but IDEs warn about it).
This is one reason fields should be private and accessed through methods: methods can be overridden, fields can only be hidden — and hiding is almost always a bug.
Removing from an ArrayList inside a for-each loop: does it always throw ConcurrentModificationException?

The usual answer "it throws CME" is only sometimes true. Predict each line:

🧠 How this works

  1. A for-each loop over a list is compiled to Iterator it = list.iterator(); while (it.hasNext()) { s = it.next(); … }. hasNext() is just cursor != size; only next() checks modCount.
  2. Remove "A" (index 0): cursor is 1, size drops to 2, so hasNext() is true; the next next() sees modCount changed and throws CME. The removal itself already happened, so the list is [B, C].
  3. Remove "B" (second-to-last): cursor is 2 and the new size is 2, so hasNext() returns false and the loop ends quietly — no exception, but "C" was never visited. The result [A, C] happens to be right here, which hides the bug.
  4. Remove "C" (last): cursor is 3, size is 2, so 3 != 2 makes hasNext() true; next() then detects the modification and throws CME.
  5. Fix: list.removeIf(...), an explicit Iterator with it.remove(), or build a new list with a stream filter. Never rely on CME being thrown — it is best-effort bug detection, not a guarantee.

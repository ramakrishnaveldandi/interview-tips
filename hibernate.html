Core concepts

In Spring you inject EntityManager; unwrap with em.unwrap(Session.class) for Hibernate-specific APIs.

get() vs load() — and their modern equivalents?
  • get() / find() — queries immediately, returns null if not found.
  • load() / getReference() — returns an uninitialized proxy without a query; throws ObjectNotFoundException / EntityNotFoundException on first access if the row doesn't exist.
Session.load() is deprecated in Hibernate 6 — use getReference(). Likewise get() → find().

Spring Data's repository.save() calls persist() if the entity is new (id null or version null) else merge().
How does dirty checking work? What are flush modes?

When an entity is loaded, Hibernate stores a snapshot of its state. On flush it compares current values with the snapshot and issues UPDATEs for changed entities — no explicit save needed.

🧠 How this works

  1. findById runs one SELECT; the entity becomes managed and Hibernate stores a snapshot of its loaded values.
  2. setSalary() only changes the Java object — no SQL happens at that point.
  3. When @Transactional commits, Hibernate flushes: it compares each managed entity with its snapshot, finds salary changed and runs UPDATE employee SET ... WHERE id = ? (all columns by default; only changed ones with @DynamicUpdate).
  4. If the method threw a runtime exception, the transaction would roll back and the change would never reach the DB. Under readOnly = true the change would not be flushed.

Flush modes: AUTO (default — flush before commit and before queries that touch dirty tables), COMMIT (only at commit), ALWAYS (before every query), MANUAL (only on flush(); used by read-only transactions).

@Transactional(readOnly = true) sets flush mode to MANUAL and lets Hibernate skip snapshots — a real performance gain for read paths.
What are Hibernate proxies and when do they cause problems?

For lazy @ManyToOne / getReference(), Hibernate returns a generated subclass (via ByteBuddy) that loads data on first method call. Pitfalls:

  • getClass() returns the proxy class — use Hibernate.getClass(obj) or instanceof.
  • final classes/methods can't be proxied → association becomes eager.
  • Accessing a proxy after the session closes → LazyInitializationException.
  • Polymorphic proxies: a proxy of Payment is not an instanceof CardPayment — use Hibernate.unproxy().

How do you configure the second-level cache with JCache/Ehcache?

🧠 How this works

  1. hibernate-jcache is the bridge: it implements Hibernate's cache region SPI on top of the standard JCache (JSR-107) API.
  2. ehcache is the actual cache provider that implements JCache; the jakarta classifier selects the build that uses the Jakarta XML Binding namespace instead of the old javax one.
  3. No versions are given because Spring Boot's dependency management supplies compatible ones.

🧠 How this works

  1. use_second_level_cache turns on the SessionFactory-wide L2 cache, and region.factory_class: jcache tells Hibernate to store it through the JCache provider found on the classpath (Ehcache here).
  2. use_query_cache separately enables caching of query results; it still does nothing unless a query is marked cacheable.
  3. sharedCache.mode: ENABLE_SELECTIVE means only entities annotated @Cacheable are cached — everything else always goes to the DB.
  4. If no cache configuration (e.g. ehcache.xml) defines a region, Hibernate by default creates it on the fly with default settings and logs a warning.

🧠 How this works

  1. The first find(Country.class, "IN") in any session runs a SELECT and stores the entity's dehydrated state (column values, not the object) in the Country region.
  2. A later session asking for the same id checks its first-level cache, then L2 — and builds the entity from L2 with no SQL.
  3. READ_WRITE soft-locks the cache entry while a transaction updates the row and refreshes it after commit, so other sessions never read a half-updated value.
  4. The query hint caches findAllByOrderByName()'s result as a list of ids keyed by the query and its parameters; entities are then resolved from L2. Any insert/update/delete on the country table invalidates the cached query results.

Concurrency strategies: READ_ONLY (immutable data), NONSTRICT_READ_WRITE, READ_WRITE (soft locks), TRANSACTIONAL (JTA).

Fetching & the N+1 problem

What is the N+1 select problem? How do you detect it?

One query loads N parents, then accessing a lazy association on each fires N more queries.

🧠 How this works

  1. findAll() fires one SELECT * FROM department; each department's employees is a lazy, uninitialized collection wrapper.
  2. Calling size() forces Hibernate to initialize that collection: SELECT * FROM employee WHERE department_id = ? — once per department.
  3. With 100 departments that's 1 + 100 = 101 round trips — the N+1 problem. Each query is fast, so it often hides in development and hurts in production.
  4. With SQL logging on you'd see the same SELECT repeated with different parameter values — the telltale sign.

Detect: enable SQL logging, Hibernate statistics, or assert query counts in tests (e.g. with datasource-proxy or Hypersistence Utils' SQLStatementCountValidator).

What are the ways to fix N+1?

🧠 How this works

  1. left join fetch loads departments and employees in one SELECT with a LEFT JOIN, filling the collections from the joined rows. The join repeats each department once per employee; Hibernate 6 removes those duplicate parents from the result automatically (distinct was required in Hibernate 5).
  2. @EntityGraph does the same declaratively: Spring Data adds a fetch graph so employees and manager are joined into the derived query WHERE region = ?.
  3. @BatchSize(size = 50): when one lazy collection is first accessed, Hibernate also initializes up to 49 other pending department collections with WHERE department_id IN (?, ?, ...), so N departments cost about 1 + N/50 queries.
  4. The DTO projection asks the DB to aggregate: one SELECT d.name, count(e.id) ... GROUP BY d.name, no entities loaded or managed.
Don't combine JOIN FETCH on a collection with pagination — Hibernate paginates in memory and logs HHH90003004. Page the parent ids first, then fetch.
What causes MultipleBagFetchException and how do you fix it?

Hibernate can't JOIN FETCH two or more List ("bag") collections at once — the cartesian product makes duplicates indistinguishable.

  • Fetch one collection per query (two queries in the same transaction — the context merges results).
  • Change collections to Set (works, but still a cartesian product — watch row counts).
  • Use @BatchSize / default_batch_fetch_size for the second collection.
  • Use @OrderColumn to turn a bag into an indexed list.
What is LazyInitializationException? Should you enable Open Session in View?

It's thrown when a lazy association is accessed after the session is closed — e.g. in a controller or during JSON serialization.

Spring Boot enables Open Session in View (spring.jpa.open-in-view=true) by default and logs a warning. It keeps the session open during view rendering, hiding the exception but causing hidden queries outside transactions and holding DB connections longer.

🧠 How this works

  1. Spring Boot stops registering the OpenEntityManagerInViewInterceptor, so the EntityManager now closes when the @Transactional service method returns (and the startup warning disappears).
  2. The DB connection is released as soon as the transaction ends instead of being held while the controller and JSON serializer run.
  3. Any lazy association touched outside the transaction now throws LazyInitializationException — this exposes hidden queries so you fetch data explicitly in the service layer.

Better fixes: fetch what you need inside the service transaction (JOIN FETCH / entity graph), return DTOs instead of entities, or call Hibernate.initialize() deliberately. Avoid hibernate.enable_lazy_load_no_trans — it's an anti-pattern.

What is an EntityGraph and when should you use it?

An entity graph (standard JPA since 2.1) is a per-query fetch plan: it lists which associations to load together with the root entity, without changing the FetchType in the mapping. Keep every association LAZY in the entity, then let each use case ask for exactly what it needs — the list screen loads orders only, the detail screen loads orders + items + products — in one SQL statement instead of N+1.

  • Named graphs: declared on the entity with @NamedEntityGraph (+ @NamedSubgraph for nested levels) and referenced by name.
  • Ad-hoc graphs in Spring Data: @EntityGraph(attributePaths = {...}) on a repository method; dotted paths such as "items.product" reach nested associations.
  • Programmatic: em.createEntityGraph(Order.class) and pass it as a query/find hint.

🧠 How this works

  1. findByStatus has no graph, so the mapping applies: one SELECT on orders; customer and items stay lazy and would each trigger extra queries if touched (the N+1 risk).
  2. findWithItemsByStatus uses the named graph: Hibernate joins order_item and, through the subgraph, product into the same SELECT, so items and their products arrive fully initialised. The WithItems part of the method name is ignored by the query derivation — anything between find and By is just descriptive.
  3. findDetailedById declares the graph inline: "customer" adds a join for the to-one, "items.product" fetches the collection and each item's product.
  4. Spring Data applies these as a fetch graph by default (EntityGraphType.FETCH): listed attributes are loaded eagerly, unlisted ones are treated as lazy. type = EntityGraphType.LOAD instead keeps the mapped fetch type for unlisted attributes.

🧠 How this works

  1. createEntityGraph builds the same plan in code — useful when the fields to fetch are decided at runtime (e.g. an ?expand=customer,items API parameter).
  2. addSubgraph("items") returns a subgraph for OrderItem, on which product is added — equivalent to the dotted path items.product.
  3. The hint jakarta.persistence.fetchgraph applies fetch-graph semantics (jakarta.persistence.loadgraph would give load-graph semantics). Older code uses the javax.persistence.* names; since Jakarta Persistence 3.0 those are legacy — use the jakarta.* ones.
  4. The same graph works for find and for JPQL queries, so one fetch plan can be reused.
Limits are the same as JOIN FETCH: fetching two List (bag) collections at once throws MultipleBagFetchException; fetching a collection and paginating makes Hibernate paginate in memory (warning HHH90003004); and each joined collection multiplies the result rows. Use graphs mainly for to-one associations and at most one collection, and fall back to @BatchSize or a second query for the rest.

Performance tuning

How do you enable JDBC batching? Why doesn't it work with IDENTITY?

🧠 How this works

  1. batch_size: 50 makes Hibernate collect up to 50 identical INSERT/UPDATE statements and send them in one JDBC executeBatch() round trip instead of 50.
  2. A batch only holds one SQL string, so interleaving (Order, Line, Order, …) breaks it into tiny batches; order_inserts/order_updates sort statements by entity type (updates also by id) so batches stay full.
  3. batch_versioned_data: true allows batching UPDATEs of @Versioned entities; Hibernate still checks each statement's row count to detect optimistic-lock failures.

With IDENTITY the id is known only after the INSERT executes, and Hibernate must put the entity in the persistence context with its id immediately — so it executes each insert right away and silently disables insert batching. Use SEQUENCE with a pooled optimizer (allocationSize).

🧠 How this works

  1. persist() with a SEQUENCE id only assigns an id (from the pooled sequence) and queues the INSERT — no SQL per call.
  2. flush() sends the queued INSERTs, grouped into JDBC batches of up to batch_size; clear() then detaches everything so the persistence context — and the memory used for snapshots and dirty checking — stays small.
  3. Without the clear, all products remain managed and every flush dirty-checks an ever-growing set, making the import slower and slower.
  4. Remaining inserts are flushed at commit. The check is (i + 1) % 50 == 0, not i % 50 == 0, so the first flush happens after exactly 50 entities instead of after the very first one.

For PostgreSQL also add reWriteBatchedInserts=true to the JDBC URL.

What does @DynamicUpdate do? When is it useful?

By default Hibernate's UPDATE includes all columns (a statement it can cache and batch). @DynamicUpdate generates SQL with only the changed columns.

  • ✅ Useful for wide tables, reducing lock contention / triggers on unchanged columns, and with optimistic locking OptimisticLockType.DIRTY.
  • ❌ SQL generated per update — less statement caching and batching.
What is a StatelessSession?

A lightweight session with no persistence context: no first-level cache, no dirty checking, no cascades, no lazy loading. Each operation executes SQL directly — ideal for bulk imports/exports and ETL.

🧠 How this works

  1. openStatelessSession() gives a session with no persistence context: there is no first-level cache, no snapshot, and no dirty checking.
  2. Each ss.insert(p) is turned directly into an INSERT — there is no write-behind queue waiting for flush, and no cascade to associated entities.
  3. tx.commit() commits the JDBC transaction; afterwards the products are plain objects — changing them does nothing unless you call ss.update(p).
  4. try-with-resources closes the session and releases the connection. Memory stays flat no matter how many rows you insert.

Hibernate 6.3+ also adds insertMultiple()/upsert(), and stateless sessions are central to Hibernate 7's Jakarta Data repositories.

How do you log SQL and see Hibernate statistics?

🧠 How this works

  1. org.hibernate.SQL: DEBUG logs every SQL statement through your logging framework; org.hibernate.orm.jdbc.bind: TRACE adds the bound parameter values (the Hibernate 6 category name).
  2. format_sql: true pretty-prints the SQL across multiple lines for readability.
  3. generate_statistics: true makes Hibernate count queries, entity loads, flushes and cache hits/misses; with org.hibernate.stat: DEBUG it logs a per-session summary — a quick way to spot N+1.
  4. LOG_QUERIES_SLOWER_THAN_MS: 200 logs any query taking longer than 200 ms (via the org.hibernate.SQL_SLOW logger).
Prefer logger configuration over spring.jpa.show-sql=true — show-sql writes to stdout and bypasses your logging framework.

Modern Hibernate & best practices

What changed in Hibernate 6 and 7?
  • Jakarta namespace: javax.persistence → jakarta.persistence (6.0); JPA 3.1 in 6.x, JPA 3.2 in 7.
  • SQM (Semantic Query Model): a new HQL/Criteria parser — HQL now supports set operations (union), window functions, CTEs, filter clauses and more.
  • Read-by-position JDBC result handling → faster result processing.
  • Better type system: @JdbcTypeCode(SqlTypes.JSON) for JSON columns, native UUID, Instant/OffsetDateTime handling.
  • Default AUTO id generation uses sequences; hibernate_sequence replaced by per-entity sequences.
  • Hibernate 7 (2025): Java 17 baseline, legacy Session methods removed, Jakarta Data support, Apache License 2.0.

🧠 How this works

  1. @JdbcTypeCode(SqlTypes.JSON) tells Hibernate 6 to treat the field as a JSON value instead of trying to map Map as an association or collection.
  2. The dialect chooses the column type — jsonb on PostgreSQL, json on MySQL — when generating DDL.
  3. On write, Hibernate serializes the map to JSON (using Jackson if it's on the classpath) and binds it as a parameter; on read it parses the column back into a Map. No extra library is needed, unlike Hibernate 5.
How should you implement equals() and hashCode() for entities?

Requirements: consistent across all lifecycle states (transient → managed → detached) and work with proxies. Options:

  • Natural/business key (e.g. ISBN, email) annotated @NaturalId — best when one exists.
  • Generated id with a constant hashCode() — so an entity in a HashSet before persist isn't lost after the id is assigned.

🧠 How this works

  1. Hibernate.getClass() unwraps a proxy to its real entity class, so a lazy proxy and a loaded instance of the same row can compare equal (plain getClass() would see the proxy subclass).
  2. Comparing ids with id != null means two transient (not yet persisted) entities are equal only if they're the same instance.
  3. other.getId() uses the getter because on an uninitialized proxy the fields aren't populated, while the id getter returns the id the proxy was created with.
  4. The constant hashCode() never changes when the id gets assigned at persist/flush, so an entity added to a HashSet before saving can still be found afterwards. The trade-off is that all instances share one bucket — fine for typical entity collections.
Never use Lombok's @Data / @EqualsAndHashCode on entities — it includes lazy collections (triggering loads or stack overflows on bidirectional links) and mutable fields.
How does Hibernate support multi-tenancy?
ApproachIsolationHibernate support
Database per tenantStrongestMultiTenantConnectionProvider returns a connection per tenant
Schema per tenantStrongConnection provider switches schema (SET search_path)
Discriminator columnLogical@TenantId field (Hibernate 6) — filter added to every query automatically

🧠 How this works

  1. @TenantId marks the discriminator column. On persist, Hibernate fills tenantId from the current tenant identifier, so you never set it by hand.
  2. On every load and query of Invoice, Hibernate adds a restriction like WHERE tenant_id = ? with the current tenant, so one tenant can't read another's rows.
  3. CurrentTenantIdentifierResolver supplies that value when a session opens — here from TenantContext, typically a ThreadLocal set by a web filter from a header or JWT. Make sure Hibernate actually uses it (property hibernate.tenant_identifier_resolver, e.g. via a HibernatePropertiesCustomizer).
  4. validateExistingCurrentSessions() returning true makes Hibernate check that an already-open current session belongs to the same tenant.

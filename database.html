Explain the different types of JOIN.

Given employee(id, name, dept_id) and department(id, name):

🧠 How this works

  1. LEFT JOIN keeps every employee; when no department matches, the d.* columns are filled with NULL.
  2. Example: Asha (dept 1, exists) and Ravi (dept_id NULL) → Asha's row has d.id = 1, Ravi's has d.id = NULL.
  3. WHERE runs after the join, so d.id IS NULL keeps only the unmatched rows → Ravi.
  4. Putting d.id IS NULL in the ON clause instead would not filter anything — the outer join would still keep all employees. NOT EXISTS is an equivalent, often equally fast, alternative.
WHERE vs HAVING? And what is the logical order of SQL execution?

WHERE filters rows before grouping; HAVING filters groups after aggregation.

Logical order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET. That is why a SELECT alias can't be used in WHERE.

🧠 How this works

  1. Logical order: FROM employee → WHERE active = true drops inactive rows before grouping → GROUP BY dept_id forms one group per department.
  2. HAVING filters groups after aggregation, so it can use AVG(salary); WHERE cannot, because aggregates don't exist yet at that stage.
  3. Example: dept 1 salaries 40k, 70k (avg 55k) is kept; dept 2 with 30k, 40k (avg 35k) is dropped.
  4. SELECT computes avg_sal, then ORDER BY runs last, which is why it can use the alias avg_sal while WHERE/HAVING generally cannot (MySQL allows aliases in HAVING as an extension).
UNION vs UNION ALL? DELETE vs TRUNCATE vs DROP?

UNION removes duplicates (extra sort/hash); UNION ALL keeps all rows and is faster — prefer it when duplicates are impossible or acceptable.

Classic Queries

Find the 2nd (or Nth) highest salary — show multiple ways.

🧠 How this works

  1. Example data: salaries 900, 900, 800, 700. The correct "2nd highest" is 800.
  2. #1: the inner query finds the max (900); the outer query takes the max of everything below it → 800. Simple, but awkward for the Nth value.
  3. #2: DISTINCT collapses to 900, 800, 700; ORDER BY ... DESC then OFFSET 1 skips one row and LIMIT 1 takes 800. Without DISTINCT it would wrongly return 900.
  4. #3: DENSE_RANK assigns 1, 1, 2, 3 (no gaps after ties), so rnk = 2 is 800. RANK would give 1, 1, 3 (no rank 2), and ROW_NUMBER 1, 2, 3 (returns 900). The window function needs a subquery because WHERE runs before window functions.
  5. #4: for each salary, count distinct salaries greater than it; for 800 that count is 1 (only 900), so it matches. Generalise with N - 1 =; it is O(n²) without an index.
  6. All of these return nothing when there is no 2nd distinct salary (#1 returns a single NULL row).
Ask whether ties count — DENSE_RANK treats equal salaries as one rank, which is usually what's expected.
How do you find and delete duplicate rows?

🧠 How this works

  1. The first query groups rows by email and HAVING COUNT(*) > 1 keeps only emails that appear more than once.
  2. ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) numbers rows within each email: ids 3, 8, 12 for a@x.com get 1, 2, 3.
  3. rn > 1 selects ids 8 and 12 for deletion, keeping the lowest id 3.
  4. The extra derived table t matters in MySQL: it does not allow a subquery to read the same table being deleted from (error 1093), but a materialized derived table works.
  5. The MySQL self-join form deletes any u1 that has a duplicate u2 with a smaller id — same result. PostgreSQL would use DELETE ... USING instead.
The extra derived table is needed in MySQL, which doesn't allow selecting from the table being deleted in a direct subquery. Afterwards, add a UNIQUE constraint to prevent recurrence.
Find employees who earn more than their manager.

🧠 How this works

  1. A self-join uses the same table twice with different aliases: e is the employee row, m is the manager row.
  2. ON e.manager_id = m.id pairs each employee with their manager; an INNER JOIN drops employees with no manager (like the CEO).
  3. Example: Ravi (60k, manager Asha) + Asha (50k) form one joined row; WHERE e.salary > m.salary keeps it because 60k > 50k.
Top 3 earners in each department and a running total.

🧠 How this works

  1. Window functions run after WHERE/GROUP BY but before ORDER BY, and unlike GROUP BY they keep every row.
  2. PARTITION BY dept_id restarts ranking in each department; with salaries 900, 900, 800, 700 the ranks are 1, 1, 2, 3, so rnk <= 3 returns all four rows (top 3 distinct salaries). The CTE is needed because WHERE cannot reference a window result directly.
  3. Running total: the frame ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW sums from the first row to the current one: amounts 100, 50, 30 → 100, 150, 180.
  4. Writing ROWS explicitly avoids the default RANGE frame, which would add up all rows with the same order_date together.
  5. AVG(salary) OVER (PARTITION BY dept_id) with no ORDER BY uses the whole partition, so every employee row shows its department's average.
The source table has 1 lakh (100,000) records but the target has only 99,000. How do you find out what went wrong?

This is a data-reconciliation question (common in ETL, migration and integration roles). Don't guess — find exactly which 1,000 rows are missing, then look for what they have in common.

  1. Confirm the counts on the same scope (same date range, same snapshot) — a load may simply still be running.
  2. Find the missing rows by business key with an anti-join.
  3. Look for a pattern in the missing rows: nulls in a required column, a specific date or status, special characters, duplicate keys.
  4. Check the pipeline: WHERE filters, INNER JOINs that drop rows without a match, deduplication logic, type conversions that failed, rejected/error tables and job logs, unique constraints that silently skipped rows (INSERT IGNORE, ON CONFLICT DO NOTHING).
  5. Fix and re-load the missing rows, then add an automated count/checksum check after every load.

🧠 How this works

  1. The LEFT JOIN … WHERE t.order_no IS NULL keeps every source row and only those with no matching target row survive the filter — exactly the missing ones.
  2. EXCEPT returns keys present in the first query but not the second; it is shorter to write but returns only the selected columns.
  3. Grouping the missing rows by a column (status, date, region) usually exposes the cause immediately — e.g. all 1,000 are CANCELLED, so a pipeline filter or an inner join to a lookup table is dropping them.
  4. The duplicate check explains the other common cause: if 1,000 source keys appear twice, a dedup step or a unique constraint in the target collapses them, so 100,000 rows become 99,000 distinct keys.
  5. With an index (or hash join) on order_no, each query is roughly linear in the table sizes.

Other useful window functions: LAG/LEAD (previous/next row), FIRST_VALUE, NTILE(n), SUM/AVG OVER.

🧠 How this works

  1. LAG(revenue) returns the value from the previous row in the window order (ORDER BY month).
  2. Example: Jan 100, Feb 120, Mar 90 → change = NULL, 20, -30. The first row has no previous row, so LAG returns NULL and the subtraction is NULL.
  3. Use LAG(revenue, 1, 0) to default to 0, and LEAD to look at the next row instead. Percentage growth: divide by the previous value (guard against 0 with NULLIF).
What is a CTE? Write a recursive CTE for an org hierarchy.

A Common Table Expression (WITH) is a named temporary result set that makes queries readable. A recursive CTE has an anchor query and a recursive part joined with UNION ALL.

🧠 How this works

  1. The anchor query runs once and returns the root rows: employees with manager_id IS NULL (the CEO), with level = 1.
  2. The recursive part joins employee to the rows produced in the previous iteration (org), finding their direct reports at level + 1.
  3. It repeats until an iteration returns no rows: CEO (1) → VPs (2) → managers (3) → …; UNION ALL appends each level.
  4. ORDER BY level, name then sorts the full result. A cycle in the data (A manages B, B manages A) would loop forever; PostgreSQL 14+ offers a CYCLE clause, or you can track visited ids / cap the level.
Supported in PostgreSQL and MySQL 8+. SQL Server/Oracle omit the RECURSIVE keyword.

Schema Design

Explain normalization (1NF, 2NF, 3NF, BCNF) with an example.

Start with orders(order_id, customer_name, customer_city, products, product_price) where products = "pen, book".

  • 1NF — atomic values, no repeating groups: one row per product → order_items(order_id, product_id, qty).
  • 2NF — 1NF + no partial dependency on part of a composite key: product_price depends only on product_id → move to product(product_id, name, price).
  • 3NF — 2NF + no transitive dependency: customer_city depends on customer, not the order → customer(customer_id, name, city), and orders(order_id, customer_id, order_date).
  • BCNF — every determinant is a candidate key (a stricter 3NF).

Denormalization deliberately adds redundancy (e.g. storing order_total or a reporting table) to avoid expensive joins in read-heavy systems, at the cost of update complexity.

Primary, foreign, unique, composite and candidate keys? Surrogate vs natural keys?
  • Primary key — uniquely identifies a row; NOT NULL; one per table.
  • Candidate key — any column set that could be the primary key.
  • Unique key — unique values; NULLs allowed (multiple NULLs in PostgreSQL/MySQL).
  • Foreign key — references another table's key, enforcing referential integrity (ON DELETE CASCADE / SET NULL / RESTRICT).
  • Composite key — key made of multiple columns, e.g. (order_id, product_id).

Surrogate keys (auto-increment, UUID) have no business meaning and never change; natural keys (email, PAN, ISBN) carry meaning but can change. Common practice: surrogate PK + unique constraint on the natural key.

🧠 How this works

  1. GENERATED ALWAYS AS IDENTITY is the SQL-standard auto-increment in PostgreSQL; MySQL uses AUTO_INCREMENT. PRIMARY KEY implies NOT NULL + unique and creates an index.
  2. UNIQUE on email creates a unique index, so a second insert with the same email fails.
  3. ON DELETE SET NULL: deleting a department sets its employees' dept_id to NULL instead of blocking the delete. manager_id references the same table (self-referencing FK).
  4. CHECK (salary >= 0) rejects negative salaries (MySQL enforces CHECK from 8.0.16). Note: MySQL 8 silently ignores inline column-level REFERENCES — declare FOREIGN KEY (...) REFERENCES ... as a table constraint there.
What are views, materialized views, stored procedures and triggers?
  • View — a saved query; no data stored; used for abstraction and security.
  • Materialized view — stores the result physically; must be refreshed (PostgreSQL REFRESH MATERIALIZED VIEW; MySQL has none, emulate with tables).
  • Stored procedure — precompiled logic on the DB server; reduces round trips but harder to version and test.
  • Function — returns a value and can be used in SQL expressions.
  • Trigger — runs automatically on INSERT/UPDATE/DELETE (audit logs, derived columns). Overuse hides logic.

🧠 How this works

  1. A view stores only the query: SELECT * FROM high_earners runs the underlying SELECT each time, so it always reflects current data.
  2. The trigger function uses the special records OLD (row before the update) and NEW (row after) to write an audit row.
  3. AFTER UPDATE OF salary ... FOR EACH ROW fires once per updated row, and only when salary is in the SET list. An UPDATE touching 3 rows writes 3 audit rows.
  4. The audit insert runs in the same transaction, so if the update rolls back, so does the audit. $$ is PostgreSQL dollar-quoting for the function body; EXECUTE FUNCTION is PostgreSQL 11+ syntax.
Design the database schema for an e-Tendering platform with Tenders, Bids and Vendors.

Start from the business rules, because they become constraints: a buyer publishes a tender with a closing deadline and documents; registered vendors submit bids with line items until the deadline; one bid per vendor per tender; finally one bid is awarded. Then model the entities, relationships and the rules the database itself should enforce.

  • Entities: vendor, tender, tender_document (1:N), bid (N:1 tender, N:1 vendor — effectively the N:M between them), bid_item (1:N), plus tender_status_history for an audit trail.
  • Integrity in the DB: foreign keys, UNIQUE (tender_id, vendor_id), CHECK constraints on status values and amounts, NUMERIC (never floating point) for money.
  • Concurrency: a version column for optimistic locking when several officers edit the same tender.
  • Workflow rules in the service layer: allowed status transitions (DRAFT → PUBLISHED → CLOSED → AWARDED, or CANCELLED), "no bids after closes_at", "bid amounts hidden until opening" — they involve time and roles, so the application owns them, with the DB constraints as a backstop.

🧠 How this works

  1. Surrogate keys (GENERATED ALWAYS AS IDENTITY) identify rows; the business identifiers registration_no and reference_no get their own UNIQUE constraints so duplicates are impossible.
  2. UNIQUE (tender_id, vendor_id) enforces "one bid per vendor per tender" even if two submissions race each other — the second INSERT fails with a unique violation. Its index also serves "all bids of a tender" lookups through the leftmost column, so no separate bid(tender_id) index is needed; idx_bid_vendor covers "my bids" for a vendor.
  3. PostgreSQL does not index foreign-key columns automatically, hence the explicit indexes on tender_document(tender_id) etc. (bid_item's FK is covered by its (bid_id, line_no) unique index). tender(status, closes_at) serves the frequent "published tenders closing soon" query: equality on status, range on closes_at.
  4. The partial unique index uq_bid_one_award only contains rows whose status is AWARDED, so a tender can have many bids but at most one awarded bid.
  5. ON DELETE CASCADE is used only for pure child data (documents, bid lines). Bids are never cascaded away from a tender — in procurement you cancel, you don't delete; the status-history table keeps the audit trail.
  6. Money and quantities use NUMERIC, which is exact; total_amount is stored for fast ranking but must equal the sum of quantity * unit_price — compute it in the service when the bid is saved.

On the JPA side: Tender has @OneToMany(mappedBy = "tender") List<Bid> bids; Bid holds @ManyToOne(fetch = LAZY) Tender tender and @ManyToOne(fetch = LAZY) Vendor vendor (the owning sides, i.e. the FK columns); Vendor usually needs no bids collection at all — query bids by vendor instead. Map status with @Enumerated(EnumType.STRING) and version with @Version. Mirror the unique key with @Table(uniqueConstraints = @UniqueConstraint(columnNames = {"tender_id", "vendor_id"})) so schema-generation tools know it, and translate the resulting DataIntegrityViolationException into a 409 Conflict.

MySQL 8 differences: use BIGINT AUTO_INCREMENT instead of identity columns and DATETIME(6)/TIMESTAMP instead of TIMESTAMPTZ (store UTC); CHECK constraints are enforced from 8.0.16; InnoDB creates indexes on FK columns automatically; and there are no partial indexes — enforce "one awarded bid" in the service (lock the tender row with SELECT ... FOR UPDATE while awarding) or with a generated column such as awarded_tender_id = IF(status = 'AWARDED', tender_id, NULL) plus a unique index on it (NULLs don't collide).
Scaling notes worth mentioning: store documents in object storage (S3/Blob) with only the key and checksum in the DB; keep bid amounts sealed (encrypted or access-controlled) until the opening time; and move bids of long-closed tenders to archive tables if the hot tables grow too large.

Indexes

How does a B-tree index work? Clustered vs non-clustered?

A B+tree keeps keys sorted in a balanced tree; lookups, range scans and ORDER BY take O(log n) page reads. Leaf nodes hold the key plus a pointer to the row (or the row itself).

  • Clustered — table rows are physically stored in index order; only one per table. MySQL InnoDB clusters on the primary key, so secondary indexes store the PK value.
  • Non-clustered (secondary) — separate structure pointing to rows; many per table. PostgreSQL tables are heaps, so all indexes are effectively non-clustered (CLUSTER is a one-time reorder).

Other types: Hash (equality only), GIN (JSONB, arrays, full-text), GiST (geo), BRIN (huge append-only tables), partial and expression indexes.

What is a composite index and the leftmost-prefix rule? What is a covering index?

🧠 How this works

  1. A B-tree on (dept_id, status, salary) is sorted by dept_id first, then status within it, then salary — like a phone book sorted by last name, then first name.
  2. Filters on a leftmost prefix can jump directly to the matching range: dept_id = 10; dept_id = 10 AND status = 'ACTIVE'; plus a range on salary at the end.
  3. status = 'ACTIVE' alone cannot seek, because active rows are scattered across every dept_id — just as you cannot find all "Ravi"s quickly in a book sorted by last name.
  4. Put equality columns first and range columns last. Some optimizers can still use such an index via a full index scan or skip scan (MySQL 8.0.13+), but it is far less efficient than a prefix seek.

Order columns by: equality filters first, then range filters, then sort columns. A covering index contains every column the query needs, enabling an index-only scan without touching the table.

🧠 How this works

  1. The key (customer_id, created_at) lets PostgreSQL find all rows for customer 42 and read them already sorted by created_at — scanned backward for DESC, so no sort step is needed.
  2. INCLUDE (total) stores total in the index leaf pages without making it part of the key.
  3. Since every column the query needs is in the index, the planner can use an Index Only Scan and skip reading the table, provided the visibility map is up to date (VACUUM).
  4. MySQL InnoDB has no INCLUDE; you would add total as a trailing key column to get a covering index.
When does an index NOT help, or even hurt?
  • Functions on the column: WHERE LOWER(email) = ? or WHERE YEAR(created_at) = 2025 — use an expression index or a range (created_at >= '2025-01-01' AND created_at < '2026-01-01').
  • Leading wildcard: LIKE '%son'.
  • Implicit type conversion (comparing a VARCHAR column to a number).
  • Low selectivity columns (e.g. boolean) — a full scan is cheaper.
  • OR across different columns (may fall back to a scan).
  • Every index slows INSERT/UPDATE/DELETE and uses storage — don't over-index write-heavy tables.
How do you read an EXPLAIN plan?

🧠 How this works

  1. EXPLAIN shows the planner's chosen plan with estimates; adding ANALYZE actually executes the query and reports real times and row counts.
  2. Because it runs the statement, wrap EXPLAIN ANALYZE of an UPDATE/DELETE in BEGIN ... ROLLBACK.
  3. MySQL 8.0.18+ also supports EXPLAIN ANALYZE, printing a tree with actual times.

🧠 How this works

  1. Index Scan using idx_orders_cust: the index on customer_id was used to find matching rows, then the table rows were fetched.
  2. cost=0.43..8.45 is startup..total cost in planner units (not ms); rows=3 is the estimate, actual ... rows=2 the real count. Large gaps between estimate and actual hint at stale statistics (ANALYZE).
  3. Index Cond is applied inside the index; Filter: status = 'PAID' is checked afterwards on each fetched row, and Rows Removed by Filter: 1 shows 3 were read and 1 discarded.
  4. If a filter removes many rows, add the column to the index, e.g. (customer_id, status).
  • Seq Scan on a large table → missing or unusable index.
  • Index Scan / Index Only Scan / Bitmap Heap Scan → index used.
  • Join nodes: Nested Loop (small inputs), Hash Join (large equi-joins), Merge Join (sorted inputs).
  • Big gap between estimated and actual rows → stale statistics; run ANALYZE.
  • MySQL: EXPLAIN columns type (ALL = full scan, ref/range/const good), key, rows, Extra (Using filesort, Using temporary are warning signs).

Transactions & Concurrency

What does ACID mean?
  • Atomicity — all or nothing (undo log / rollback).
  • Consistency — constraints hold before and after the transaction.
  • Isolation — concurrent transactions don't see each other's partial work.
  • Durability — committed data survives crashes (write-ahead / redo log).

🧠 How this works

  1. BEGIN starts a transaction; both UPDATEs are applied as one atomic unit.
  2. If the second update fails (or the app crashes) before COMMIT, a ROLLBACK undoes the first one, so money is never debited without being credited.
  3. Each UPDATE takes a row lock on its account until commit, so a concurrent transfer on the same row waits. balance = balance - 500 computes from the current row value, avoiding lost updates from a read-then-write in app code.
  4. After COMMIT the change is durable (written to the WAL / redo log) and visible to other transactions.

What is MVCC and how are deadlocks handled?

Multi-Version Concurrency Control keeps multiple versions of a row so readers see a consistent snapshot and readers don't block writers (and vice versa). PostgreSQL stores old versions in the table (cleaned by VACUUM); InnoDB reconstructs them from undo logs.

A deadlock occurs when two transactions each hold a lock the other needs. The DB detects the cycle and aborts one (the victim) with an error — the application should retry.

  • Access tables/rows in a consistent order.
  • Keep transactions short; no user interaction inside them.
  • Index the columns used in UPDATE ... WHERE to lock fewer rows.

🧠 How this works

  1. Optimistic: the WHERE version = 3 clause makes the update succeed only if nobody changed the row since you read version 3; it then bumps the version to 4.
  2. If another user updated first (version is now 4), the statement matches 0 rows; the app sees the affected-row count is 0 and retries or reports a conflict (JPA @Version throws OptimisticLockException).
  3. Pessimistic: SELECT ... FOR UPDATE locks the row; any other transaction trying to lock or update it waits until this COMMIT, so stock cannot be oversold.
  4. SKIP LOCKED (PostgreSQL and MySQL 8) skips rows locked by others instead of waiting — ideal for workers pulling jobs from a queue table.

Performance & Scaling

A query is slow in production. How do you tune it?
  1. Find it: slow query log (MySQL), pg_stat_statements (PostgreSQL), APM traces.
  2. Run EXPLAIN ANALYZE and look for sequential scans, bad estimates, sorts and temp tables.
  3. Add or fix indexes (composite order, covering); make predicates sargable.
  4. Select only needed columns — avoid SELECT *.
  5. Rewrite: EXISTS instead of IN on large subqueries, avoid correlated subqueries, push filters down.
  6. Update statistics (ANALYZE), check for table bloat / locks.
  7. Fix the application side: N+1 queries, missing batching, pagination, caching.
What is the N+1 query problem at the database level?

Fetching a list (1 query) and then one extra query per row (N queries) — e.g. loading 100 orders and then each order's customer. It shows up as hundreds of tiny identical queries.

🧠 How this works

  1. N+1: one query fetches 100 orders, then the code issues one customer query per order → 101 round trips; latency adds up quickly.
  2. The JOIN fetches orders and their customer names in a single query, matching on c.id = o.customer_id.
  3. The batch alternative collects distinct customer ids and loads them with one IN (...) query → 2 queries total. In JPA this maps to JOIN FETCH, entity graphs or batch fetching.

In JPA/Hibernate use JOIN FETCH, @EntityGraph or @BatchSize.

Why use connection pooling? How do you size HikariCP?

Opening a DB connection is expensive (TCP + auth + session). A pool reuses a fixed set of connections. HikariCP is Spring Boot's default.

🧠 How this works

  1. maximum-pool-size: 10 caps open DB connections; beyond the DB's CPU/disk capacity, more connections add contention rather than throughput.
  2. minimum-idle equal to max gives a fixed-size pool (Hikari's recommended setup), avoiding connection churn under spikes.
  3. connection-timeout: 30000: a request waits up to 30 s for a free connection, then throws — a sign of a too-small pool or connections held too long.
  4. max-lifetime retires connections before the DB or a firewall drops them; leak-detection-threshold logs a stack trace when a connection is held longer than 20 s, pointing to the leaking code.
A common starting formula: connections = (CPU cores × 2) + effective spindles. Remember total = pool size × number of app instances — it must fit within the DB's max_connections.
OFFSET pagination vs keyset (seek) pagination?

OFFSET 100000 forces the DB to read and discard 100,000 rows, so deep pages get slower; rows can also shift between pages. Keyset pagination seeks directly using the last seen key.

🧠 How this works

  1. Offset: the database must still read and discard the first 1000 rows to return rows 1001–1020, so page 5000 gets slower and slower. Rows inserted meanwhile can also shift items between pages.
  2. Keyset: the client sends the last row's (created_at, id); the row comparison (created_at, id) < (x, y) means "earlier date, or same date with smaller id".
  3. With an index on (created_at, id), the database seeks straight to that position and reads 20 rows, so every page costs the same.
  4. id is included as a tie-breaker so rows with identical created_at are neither skipped nor repeated. The trade-off: no direct "jump to page 50".
Partitioning vs sharding vs replication?
  • Partitioning — splits one table into pieces inside one database (by range, list or hash), e.g. orders by month. Enables partition pruning and cheap archival (drop old partitions).
  • Sharding — splits data across multiple database servers by a shard key (e.g. tenant_id). Scales writes, but cross-shard joins and transactions become hard.
  • Replication — copies data to replicas. Primary-replica gives read scaling and failover; replicas can lag (asynchronous) so read-your-own-writes needs care. Synchronous replication trades latency for zero data loss.

🧠 How this works

  1. PARTITION BY RANGE (created_at) makes orders a parent table that stores no rows itself; rows are routed to child partitions by date.
  2. Range bounds are inclusive at FROM and exclusive at TO, so 2026-10-01 belongs to the next partition, not Q3.
  3. A query with WHERE created_at >= '2026-08-01' lets the planner prune partitions and scan only the relevant ones.
  4. Inserting a date with no matching partition fails unless a DEFAULT partition exists; dropping an old partition is an instant way to purge data.

CAP: during a network Partition, a distributed system must choose between Consistency (every read sees the latest write) and Availability (every request gets a response). CP examples: HBase, MongoDB (default majority writes); AP examples: Cassandra, DynamoDB (tunable). PACELC extends this: Else (no partition) trade Latency vs Consistency.

Explain Redis caching patterns and common cache problems.
  • Cache-aside (most common) — app reads cache; on miss reads DB and populates cache with a TTL; on write updates DB then evicts the key.
  • Read-through / write-through — the cache layer itself loads from / writes to the DB synchronously.
  • Write-behind — writes go to cache and are flushed to the DB asynchronously (fast, risk of loss).

🧠 How this works

  1. @Cacheable runs through a Spring proxy: on findById(5) it first looks up key 5 in cache products; on a hit the method body (and DB query) is skipped.
  2. On a miss, the method runs and its return value is stored under that key, so the next call is served from cache.
  3. @CacheEvict(key = "#p.id") removes the entry for the updated product (after the method succeeds by default), so the next read fetches fresh data.
  4. Because it is proxy-based, calling these methods from another method in the same class bypasses caching; caching also needs @EnableCaching.

🧩 Java 17 (LTS) Interview Questions

Java 17 (September 2021) is the LTS that most enterprises moved to from Java 8/11, and it is the minimum baseline for Spring Boot 3. These questions cover every feature finalized between Java 9 and 17, with examples.

Overview

Why is Java 17 such an important release?
  • Long-Term Support — the LTS after Java 11, with years of vendor updates.
  • Framework baseline — Spring Boot 3 / Spring Framework 6 and Jakarta EE 10 tooling require Java 17+.
  • Language modernisation — records, sealed classes, pattern matching for instanceof, text blocks and switch expressions are all final.
  • Strong encapsulation — JDK internals (e.g. sun.misc.* via reflection) are strongly encapsulated (JEP 403).
  • Performance — better G1/ZGC, faster startup and lower memory vs Java 8.

Records

What is a record and what does the compiler generate for it?

A record is a transparent, shallowly-immutable data carrier. For each component the compiler generates a private final field, a public accessor (name(), not getName()), a canonical constructor, and equals(), hashCode() and toString().

🧠 How this works

  1. The single line record Employee(String name, String dept, double salary) makes the compiler generate three private final fields, a canonical constructor taking all three in declaration order, accessors name(), dept(), salary(), plus equals(), hashCode() and toString() based on all components.
  2. new Employee("Asha", "IT", 95_000) calls that canonical constructor; the int literal 95_000 (underscores are just digit separators) is widened to double.
  3. e.name() is the generated accessor, so it prints Asha — note there is no get prefix.
  4. Printing e uses the generated toString(), format Employee[name=Asha, dept=IT, salary=95000.0]; the salary shows 95000.0 because the component is a double.
  5. Records were finalized in Java 16 (JEP 395), so they are fully available on Java 17.
Records are implicitly final, extend java.lang.Record, and cannot declare extra instance fields.
How do you add validation to a record? What is a compact constructor?

A compact constructor omits the parameter list; it runs before fields are assigned, so it is ideal for validation and normalisation.

🧠 How this works

  1. public Money { ... } has no parameter list: it is a compact form of the canonical constructor, and its parameters amount and currency are implicitly declared.
  2. The body runs first; Objects.requireNonNull and the signum() < 0 check reject invalid input before any object state exists.
  3. currency = currency.toUpperCase() reassigns the parameter. You may not write this.currency = ... in a compact constructor.
  4. After the body ends, the compiler inserts the field assignments (this.amount = amount; this.currency = currency;), so the normalised, uppercase value is what gets stored.
  5. The static factory inr(long) just calls the canonical constructor, so every Money goes through the same validation.
Can records be used as JPA entities? Where are they useful in Spring apps?

No — JPA entities need a no-arg constructor, mutable state and non-final classes for proxies. Records are great for:

  • REST request/response DTOs (Jackson supports records natively).
  • Spring Data projections and JPQL constructor expressions: select new com.x.EmpDto(e.name, e.salary) from Employee e.
  • @ConfigurationProperties classes (constructor binding is automatic).
  • Map keys / value objects (correct equals/hashCode for free).

Sealed classes

What are sealed classes and why would you use them?

Sealed classes/interfaces restrict which classes may extend them using permits. Each permitted subclass must be final, sealed or non-sealed. They model a closed hierarchy (algebraic data types), so the compiler can check exhaustiveness.

🧠 How this works

  1. sealed interface Payment permits Card, Upi, NetBanking tells the compiler these three are the only allowed direct subtypes; any other class trying to implement Payment fails to compile.
  2. Every permitted subtype must declare how it continues the hierarchy: final, sealed or non-sealed. Card and Upi are records, which are implicitly final, so they need no modifier.
  3. NetBanking is non-sealed, which re-opens that branch: anyone may subclass NetBanking, but the top level stays closed to exactly three cases.
  4. Permitted subclasses must be in the same module (or the same package, if the code is in the unnamed module). Sealed classes are final in Java 17 (JEP 409).
How do sealed types combine with records and pattern matching?

Together they give exhaustive, type-safe handling without a default branch. (Pattern matching for switch was preview in 17 and final in 21; on 17 you would use instanceof chains.)

🧠 How this works

  1. fee uses only Java 17 final features: each instanceof Card c tests the type and binds a typed variable, so c.number() works without a cast.
  2. The final else silently covers NetBanking and anything else. If someone adds a new permitted type, this code still compiles and returns 5.0 for it — a hidden bug.
  3. fee21 uses pattern matching for switch (final in Java 21, JEP 441). Because Payment is sealed, the compiler knows the full list of subtypes and checks the switch covers all of them, so no default is needed.
  4. If a fourth type is added to permits, fee21 stops compiling until a case is added — this compile-time exhaustiveness check is the main payoff of sealed hierarchies.
  5. case NetBanking n also matches any subclass of the non-sealed NetBanking, so the switch stays exhaustive.

Pattern matching, switch & text blocks

What is pattern matching for instanceof?

It combines the type test and the cast into one step and introduces a binding variable scoped by flow analysis.

🧠 How this works

  1. The "before" form repeats the type three times: test with instanceof String, then declare and cast with (String) obj.
  2. In obj instanceof String s, the compiler does the test and the cast together and introduces the binding variable s.
  3. s is in scope only where the match is definitely true (flow scoping). That is why !s.isBlank() can use it on the right of &&: it only runs if the test passed. With || it would not compile.
  4. If obj is null, instanceof is simply false, so no NPE. Final in Java 16 (JEP 394).
What are switch expressions and the arrow syntax?

Switch can now return a value, uses -> labels (no fall-through, no break), supports multiple labels per case, and uses yield for block bodies.

🧠 How this works

  1. The whole switch is an expression whose value is assigned to days, so each branch must produce an int.
  2. Arrow labels (->) never fall through, so no break is needed. case FEB -> leap ? 29 : 28 evaluates a single expression.
  3. case APR, JUN, SEP, NOV lists several constants on one label instead of stacking fall-through cases.
  4. The default branch is a block, so it uses yield 31 to return its value (return would exit the enclosing method instead).
  5. A switch expression must be exhaustive; here default guarantees that. Switch expressions are final since Java 14 (JEP 361).
What are text blocks? Give a practical example.

Multi-line string literals delimited by """. Incidental indentation is stripped; \ at line end joins lines and \s keeps a trailing space.

🧠 How this works

  1. A text block starts with """ followed by a line break; the content begins on the next line.
  2. The compiler strips incidental indentation: it finds the smallest common leading whitespace across content lines (and the closing """ line) and removes it, so SELECT starts at column 0 in the resulting string.
  3. Because the closing """ sits on its own line, each string ends with a trailing newline \n.
  4. .formatted(name, active) (an instance method added in Java 15) works like String.format: %s takes name and %b takes the boolean. Double quotes inside the JSON need no escaping.
  5. Text blocks are final since Java 15 (JEP 378) and produce an ordinary String at compile time, with no runtime cost.

APIs & JVM

Name useful API additions from Java 9–17.

🧠 How this works

  1. List.of / Map.of (Java 9) create immutable collections: add/put throw UnsupportedOperationException and null elements are rejected.
  2. Optional.ifPresentOrElse (Java 9) runs one action when a value exists and another when it is empty. var (Java 10) infers ArrayList<String> from the right-hand side; it works only for local variables.
  3. Java 11 string helpers: strip() is Unicode-aware (unlike trim()), isBlank() is true for empty or whitespace-only strings, and "ab".repeat(3) gives "ababab". Files.readString reads a whole file as UTF-8, and HttpClient (java.net.http) replaces HttpURLConnection.
  4. stream.toList() (Java 16) returns an unmodifiable list, a shorter alternative to collect(Collectors.toList()).
  5. Collectors.teeing (Java 12) feeds every element to two collectors (counting() and summingInt) and then merges their results with the lambda — here sum / count, i.e. the average, in a single pass.
What does strong encapsulation of JDK internals (JEP 403) mean for migration?

The --illegal-access flag is gone, so libraries reflecting into JDK internals fail with InaccessibleObjectException. Fix by upgrading the library (Lombok, Mockito, ByteBuddy, older Hibernate), or as a last resort use --add-opens java.base/java.lang=ALL-UNNAMED. Run jdeps --jdk-internals to find usages.

What was removed or deprecated in Java 17?
  • Removed: RMI Activation, experimental AOT and Graal JIT compiler, Nashorn (removed in 15), Applet API deprecated for removal.
  • Security Manager deprecated for removal (JEP 411) — permanently disabled in Java 24.
  • Java EE modules (JAXB, JAX-WS) were already removed in 11 — add them as Maven dependencies.
